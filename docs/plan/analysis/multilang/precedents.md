# Multi-language plugin mounting: precedents and lessons for rutis

Status: research input (not a decision), 2026-10-03. Scope: how mature multi-language plugin / extension systems are built, and what that implies for extending `rutis-interop` beyond Node/Cordis to Python, PowerShell, Bash and AppleScript/JXA. Per-language details are covered by separate reports; this one is about cross-cutting architecture.

## 0. Summary

About forty systems in seventeen groups were surveyed (§2): Neovim remote plugins, Azure Functions workers (+ custom handlers, Lambda), Pulumi, Nushell, Babashka pods, go-plugin/Terraform, osquery/Steampipe, Dapr, Telegraf execd / Erlang ports / Tauri, LSP/DAP/MCP, Jupyter, Bazel workers, VS Code / Sublime, Raycast/xbar/Stream Deck, Wasm components / wRPC / Extism / Zed, Cap'n Proto / Cap'n Web, Py4J / PowerShell remoting. The main conclusions:

- **rutis's current shape is where the field is heading.** Neovim is dismantling its one-host-per-language remote-plugin design (shared host, decorators, refreshed manifest) in favour of one process per plugin with bindings defined on the host side (§2.1). Pulumi derives one neutral schema from plugin source (Python annotations, the TS compiler) and generates typed SDKs from it — the same idea as rutis's build-time TS extraction (§2.3). Cap'n Web, a JSON object-capability protocol, looks very much like rutis protocol v1 (§2.16).
- **(a) Keep one protocol family, but layer it:** a small mandatory core (JSON lines off stdio, `hello` with runner identity + profile + features, invoke/return/throw with exactly one terminal frame per call, one error envelope, logs, dispose, exit-on-EOF) plus negotiated feature sets. For Bash and AppleScript/JXA, terminate the protocol in Rust and run scripts through a trivial, versioned calling convention (argv/stdin in, JSON on fd 3 out, stderr logs, exit status) — the Azure-custom-handler / Lambda / execd / bash_kernel pattern — instead of implementing the rich protocol in shell.
- **(b) Per-language extraction → one generated neutral interface model (IR) → Rust codegen**, with the IR digest embedded in the bindings and re-checked at mount. No hand-written IDL and no separately refreshed manifest. Python: introspection of decorators + type hints in the mount's own venv; PowerShell: its own parser over typed `param()` blocks; Bash/AppleScript: versioned comment headers or a sidecar manifest (Raycast-style).
- **(c) Keep one process per mount (group); never one host per language.** Add a "mount key" (interpreter, environment, runner version, profile) that members of a group must share. Script tiers run one short-lived interpreter per call (Bash ≈ 2 ms, osascript ≈ 37 ms cold start measured here).
- **(d) Three cumulative profiles** — P0 command (data-only unary calls), P1 service (persistent, host services, events, cooperative cancel, call-scoped callbacks), P2 objects (today's Node feature set) — checked at build time, at mount time and by a runtime `unsupported` backstop, using a closed typed feature set. Azure's silently undelivered cancellations and go-plugin's silent fallbacks are the cautionary tales.
- **(e) Lifecycle:** separate start-up timeout with precise failure categories; readiness = `mount` round-trip; declared cancellation mode per runner (cooperative / signal / none); shutdown ladder dispose → EOF → SIGTERM to the process group → SIGKILL; stderr captured with attribution and attached to crash errors; restarts stay off by default, opt-in only with OTP-style bounds.
- **(f) Environments:** pin the resolved interpreter at build time and verify it in `hello`; one lockfile per mount group (as with npm today); keep the runner stdlib-only and separate from the plugin's dependencies (Azure's grpcio/protobuf clash); version the protocol independently of rutis (Nushell's minor-locked protocol forces plugin rebuilds every six weeks). macOS still ships Bash 3.2.57.
- **(g) DX:** decorators + type hints for Python, typed advanced functions for PowerShell, comment headers for scripts; `describe`/`call` commands for a host-free loop; one tiered conformance corpus run against every runner (Pulumi's L1–L3).
- **Anti-patterns (§5)** include the abandoned rutis design's central broker, capability-security machinery without a security boundary, hand-maintained descriptor bundles, and roadmap/acceptance gates for nine languages before one worked.

## 1. Baseline: what rutis has, and what it already rejected

### 1.1 rutis-interop protocol v1 in one table

The facts below are from `docs/design-protocol-plugin-mount.md` (design), `docs/requirements-protocol-plugins.md` (requirements), `crates/rutis-interop/src/{process,protocol,rpc}.rs` and `interop/node/src/{runner,client,wire}.mjs`.

| Concern | v1 behaviour |
| --- | --- |
| Topology | One Node process per *mount* (a single plugin or a group sharing one Cordis Context); different mounts get different processes; "plugins that need isolation go into different mounts" (requirements §7). |
| Transport | Rust binds a Unix socket in a fresh temp dir and passes the path in argv; the runner connects. stdin is `/dev/null`, stdout/stderr are inherited and never carry frames (`process.rs`). |
| Framing | One JSON value per line; non-finite numbers rejected (`wire.mjs`). |
| Handshake | `hello {version}` both ways, exact match; the runtime package's `rutisProtocol` is also checked at build time. "Only one protocol version, no multi-version negotiation" (design §9). No capability exchange. |
| Readiness | After `hello`, a control call `mount` loads the plugins, awaits their fibers, fails if an in-group dependency can never resolve, and returns the service table `{name: [handle, version]}`. |
| Calls | `invoke`/`call`/`get`/`await`/`return`/`throw`; sync methods stay sync, Promise-returning ones become `async fn`. Nested reverse calls inside a synchronous call run on the blocked thread, routed by the call `path`; impossible waits return `SyncWaitCycle`. |
| Values | `undefined`, data, list, record, `signal`, `reference{function, future, object}` with grant counting and `release {reference, count}`; only Node exports object references. |
| Cancellation | Dropping the Rust future sends `cancel {id}`; Node aborts the call's `AbortSignal`; late replies are dropped and counted (`orphans`). No default timeouts anywhere (boundary rule 8). |
| Errors | Business errors travel as an object graph (`name`, `message`, `cause`, `AggregateError.errors`, shared/cyclic refs). Transport errors say how the process ended (exit code / signal). `SyncWaitCycle`, `BindingError`. "Sent but unanswered" = outcome unknown. |
| Interface source | Build-time extraction from TypeScript declarations with the TS checker (`generate.mjs`, run from `build.rs`), emitting Rust types; unsupported members are skipped with a `cargo:warning` and listed in docs, and calling them from the other side fails explicitly. No hand-written IDL (requirements §3). |
| Crash | In-flight and later calls fail with `Transport`; projected services are withdrawn so dependents stop by native gating; the mount plugin stays Active but empty. No automatic restart, no replay. |
| Shutdown | `dispose` unloads Cordis plugins and drains in parallel; when the mount is released the process gets SIGKILL; grandchildren spawned by plugins are not reaped (requirements §7). |
| Environment | An npm project + lockfile is the only version source; the build never installs packages and fails with the command to run. |
| Events | Notification-only, declared per mount and per direction; a name may only go one way (no loops). |

### 1.2 What the abandoned design proposed

`docs/design-protocol-plugins-2026-09-25.md` and `docs/roadmap-protocol-plugin-languages-2026-09-26.md` (both marked historical) proposed a general cross-language object-capability system: a host *broker* through which every cross-runner object call is routed; per-delivery grant tokens with `Offered/Accepted/Released/Revoked` state machines, epochs and watermarks; activation barriers and `StopUnconfirmed / RecoveryBlocked / Quarantined` states; a JSON interface-descriptor bundle (JSON Schema subset + object/callback/ownership annotations) identified by SHA-256 and consumed by every language; an M0 go/no-go gate; 24 acceptance scenarios (T01–T24) plus extensions (X01–X04) before a first release; and a 9+-language roadmap (Python, Go, Bash, PowerShell, AppleScript/JXA, Lua, Ruby, PHP, Perl, Bun, Deno) with per-language execution models and E01–E07 tests.

Several *principles* from the roadmap reappear in mature systems below and are worth keeping even though the mechanism was dropped: capability subsets with explicit rejection ("missing object references → reject interfaces containing objects … never degrade an object to a snapshot, a callback to a function name, an event to a notification"), argv instead of string interpolation, a protocol channel separate from logs, realism about macOS automation permissions, and "a separate process is not a sandbox".

### 1.3 What changes with the new languages

Node is the "maximal" peer: functions, promises and objects as values, an event loop, a type checker to extract interfaces from. The new languages span the whole range down to "no values but strings, no types, no event loop, cannot open a Unix socket". Orientation only (per-language reports are authoritative):

| | Node (today) | Python | PowerShell 7 | Bash | AppleScript / JXA |
| --- | --- | --- | --- | --- | --- |
| Can host the full v1 value model (functions, futures, objects) | yes | yes (callables, asyncio futures, objects) | partly (.NET objects; scriptblocks are runspace-bound; no promises) | no (strings, exit codes) | AppleScript no; JXA partly, only within one `osascript` process lifetime |
| Static interface info available at build time | TS checker | optional type hints | typed `param()` blocks, `[OutputType()]`, parseable AST | none | none (JXA: JSDoc at best) |
| Native Unix-socket client | yes | yes | yes (.NET) | no — Bash's `/dev/tcp`/`/dev/udp` redirections open TCP/UDP only ([Bash manual: Redirections](https://www.gnu.org/software/bash/manual/html_node/Redirections.html)) | no native socket API; connecting through the ObjC bridge [unverified] |
| Can use an inherited fd (e.g. fd 3/4) | yes | yes | likely, via .NET handles [unverified] | yes — verified with `/bin/bash` 3.2: `read -r -u 4` + `jq -c`, `printf … >&3` | yes — verified: JXA and AppleScriptObjC (`use framework "Foundation"`) read/write via `NSFileHandle initWithFileDescriptor:` under `osascript` |
| Cold start of a trivial command, measured on this Mac\* | `node -e 0` ≈ 30 ms | `python3 -c pass` ≈ 10 ms (`-S` ≈ 6 ms) | not installed here | `bash -c :` ≈ 2 ms | `osascript -e 'return 1'` ≈ 37 ms; JXA ≈ 29 ms |

\* 20 runs each, macOS 26.6.2, Apple Silicon. Real plugins add import/module-load time.

Environment facts verified on this machine that matter for (f): macOS still ships `/bin/bash` **3.2.57**, which rejects `coproc`, `declare -A` (associative arrays) and `mapfile` (tested locally); `/usr/bin/jq` (jq-1.7.1-apple) is present on this macOS; `/usr/bin/python3` is 3.9.6 (the Command Line Tools shim), so "the system Python" is old and may not exist at all on machines without the CLT.

## 2. Survey of precedent systems

Each entry has a short description, the mechanics that bear on questions (a)–(g), and lessons. Facts were checked against primary sources (specs, official docs, source files on GitHub) on 2026-10-03; "[inference]" marks readings of code that no document states, "[unverified]" marks memory not confirmed in a source.

### 2.1 Neovim remote plugins and providers

- **Model.** A remote plugin lives in `rplugin/{python3,node,ruby,perl}/` on the runtimepath. Nvim registers **one host per language**; all plugins of that language are imported into that one host process, which speaks msgpack-RPC over stdio (started with `jobstart(argv, {'rpc': v:true})`) ([remote_plugin](https://neovim.io/doc/user/remote_plugin.html), [host.vim](https://github.com/neovim/neovim/blob/master/runtime/autoload/remote/host.vim)). pynvim loads each plugin by `importlib.import_module` into a single interpreter; a plugin that fails to import is recorded and the rest still load ([pynvim host.py](https://github.com/neovim/pynvim/blob/master/pynvim/plugin/host.py)).
- **Interface description = runtime reflection, run once into a manifest.** `:UpdateRemotePlugins` starts a temporary registration clone of each host, calls `rpcrequest(ch, 'specs', path)` per plugin and writes `rplugin.vim` with `remote#host#RegisterPlugin(...)` stubs. A spec is `{type: command|function|autocmd, name, sync: 0|1|'urgent', opts}` (opts such as `nargs`, `range`, `eval`, `pattern`) — names and calling conventions, no types. Users must re-run the command whenever a remote plugin is installed, updated or deleted. At startup Nvim sources only the manifest; a host is spawned the first time one of its stubs is used (`remote#host#Require`); the stub is then redefined to call `rpcrequest`/`rpcnotify` directly, and the call is replayed.
- **Re-entrancy (nested synchronous calls).** Nvim adds out-of-spec rules to msgpack-RPC: "Responses must be given in reverse order of requests" (like unwinding a stack), and messages are processed in arrival order ([api](https://neovim.io/doc/user/api.html#api-rpc)). While blocked in `rpcrequest()`, Nvim runs `LOOP_PROCESS_EVENTS_UNTIL` on that channel's own event queue, so a sync handler can call back into `nvim_*` (nested); requests from *other* channels wait until the outer call returns; the wait has no timeout, so a hung sync handler hangs the editor ([channel.c](https://github.com/neovim/neovim/blob/master/src/nvim/msgpack_rpc/channel.c)). pynvim serves each request in a greenlet and keeps serving nested requests while its own request is pending. This is the same stack discipline rutis implements with call `path`s.
- **Interpreter discovery (providers).** Python: `g:python3_host_prog`, else `pynvim-python` on PATH, else the first `python3.x` that can import `neovim` (≥ 3.9) ([python.lua](https://github.com/neovim/neovim/blob/master/runtime/lua/vim/provider/python.lua)). `:checkhealth` recommends a virtualenv dedicated to Nvim; 0.12 reduced setup to `uv tool install pynvim` ([news-0.12](https://neovim.io/doc/user/news-0.12.html)). Consequence: every Python plugin's third-party dependencies must be installed into that one host environment. A missing provider fails loudly (`E319 … Run ":checkhealth vim.provider"`).
- **Lifecycle.** Readiness = `rpcrequest(ch, 'poll') == 'ok'`; host stderr is buffered and only shown if startup fails. No supervisor and no restart: after a crash the cached channel is dead and calls fail with an invalid-channel error. stdout is the RPC channel, so the node client replaces `console` with a file logger. `remote#host#RegisterClone` exists to run a plugin isolated from others of the same language.
- **Contrast: Nvim's own API metadata.** `nvim --api-info` / `nvim_get_api_info()` expose a generated, versioned API description (`api_level`, `api_compatible`, per-function `since` / `deprecated_since`) explicitly meant for statically compiled clients; signatures never change after release, changes are additive.
- **Status (Oct 2026): being dismantled.** Not formally deprecated yet, but issue [#27949](https://github.com/neovim/neovim/issues/27949) ("simplify remote plugins, massively", milestone 0.13) proposes dropping the per-language multi-tenant host, the decorator layer and `:UpdateRemotePlugins`. The stated reasons: almost all of the complexity buys little, every API client has to reimplement thousands of lines of host code, and the manifest is extra state that has to be refreshed and health-checked. The replacement is **one process per plugin**, with the plugin's commands defined on the Nvim side (Lua) calling `vim.rpcrequest()` handlers the plugin registers. The Go client already stopped serving `specs` (2024); the original author of remote plugins called the idea questionable in hindsight in that thread.

**Lessons.** (1) The expensive part was the per-language host layer (multi-tenancy, registration sugar, manifest), not the wire protocol: keep each language runner a thin, generic peer and do the typing/binding work once, on the host side (for rutis: in the Rust build). (2) Never require a separately refreshed manifest; tie interface extraction to the build and verify it at startup with a digest. (3) A shared host per language means a shared environment and dependency conflicts; process (and venv) per mount avoids it, and Neovim itself is moving there. (4) Specify re-entrancy and reply ordering explicitly per runner: Python can serve nested calls while waiting; Bash and AppleScript cannot. (5) An additive API level with per-feature `since` is friendlier than exact version matching once runners ship through pip/PSGallery/npm on different schedules.

### 2.2 Azure Functions language workers (+ custom handlers, AWS Lambda Runtime API)

The most direct precedent for "one host, many language workers, including PowerShell": Node, Python, PowerShell, Java and .NET workers behind one gRPC protocol.

- **Model.** The .NET Functions host runs a gRPC server and spawns worker processes, which connect back and open one bidirectional stream `EventStream(stream StreamingMessage)`; every frame is `StreamingMessage {request_id, oneof content}` ([FunctionRpc.proto](https://github.com/Azure/azure-functions-language-worker-protobuf/blob/dev/src/proto/FunctionRpc.proto)). An app has exactly one language (`FUNCTIONS_WORKER_RUNTIME`). One worker process holds every function of the app; `FUNCTIONS_WORKER_PROCESS_COUNT` (default 1, max 10) adds identical replicas, with invocations round-robined ([app settings](https://learn.microsoft.com/en-us/azure/azure-functions/functions-app-settings)). Each worker repo vendors the `.proto` (git subtree, tagged versions).
- **Messages.** `StartStream`, `WorkerInitRequest/Response`, `FunctionsMetadataRequest/Response`, `FunctionLoadRequest/Response` (+ batched forms), `InvocationRequest/Response`, `InvocationCancel`, `WorkerTerminate`, `WorkerStatusRequest` (a latency echo, not liveness), `RpcLog`, `FunctionEnvironmentReloadRequest` (assigning a pre-warmed worker to an app), shared-memory messages. Values are a `TypedData` union (string, json, bytes, stream, http, int, double, collections) — **no references to remote functions or objects**. Errors: `StatusResult {status: Failure|Success|Cancelled, exception: RpcException {source, stack_trace, message, is_user_exception, type}, logs}`.
- **No protocol version number; capabilities are a `map<string,string>`** exchanged in `WorkerInitRequest/Response` (`RawHttpBodyBytes`, `TypedDataCollection`, `RpcHttpBodyOnly`, `WorkerStatus`, `SharedMemoryDataTransfer`, `HandlesInvocationCancelMessage`, `HandlesWorkerTerminateMessage`, `EnableUserCodeException`, `SupportsLoadResponseCollection`, …) ([RpcWorkerConstants.cs](https://github.com/Azure/azure-functions-host/blob/dev/src/WebJobs.Script/Workers/Rpc/RpcWorkerConstants.cs)). The host checks them inconsistently (most by key presence, one must equal `"True"`, some parsed as booleans), and several proto fields are marked as unused leftovers awaiting a breaking release.
- **Degradation is mostly silent.** Of the Node, Python, PowerShell and .NET isolated workers, only .NET advertises `HandlesInvocationCancelMessage`; Node, Python and PowerShell never receive cancellations (the host fails already-cancelled calls locally; the PowerShell worker's cancel/terminate handlers do nothing) ([WorkerChannel.cs](https://github.com/Azure/azure-functions-host/blob/dev/src/WebJobs.Script.Grpc/Channel/WorkerChannel.cs), [PowerShell RequestProcessor.cs](https://github.com/Azure/azure-functions-powershell-worker/blob/dev/src/RequestProcessor.cs)). Hard rejection happens only for configuration: an unsupported OS, architecture or runtime version is refused with an explicit error, or a `Failure` status in the init response.
- **Interface description: two eras.** *Host indexing*: a static `function.json` per function (PowerShell, Python v1, custom handlers). *Worker indexing* (Python v2 decorators `@app.route(...)`, Node v4 `app.http(...)`): the worker imports user code and answers `FunctionsMetadataRequest` — runtime reflection; a worker can decline and the host falls back to `function.json`. Enabled per language by `"workerIndexing": "true"` in `worker.config.json`. Data on the wire is untyped; types exist only inside each language SDK.
- **Lifecycle.** Launch: `defaultExecutablePath [arguments] defaultWorkerPath --host --port --workerId --requestId --grpcMaxMessageLength` (duplicated with a `functions-` prefix). Timeouts: `StartStream` within 60 s; init reply within 10 s (raised to 2 min for Python and Node); function load 1 min; environment reload 30 s. Startup is raced against process exit, which gets its own error. Shutdown: `WorkerTerminate {grace_period: 5 s}` if the worker handles it.
- **Crash and restart.** In-flight invocations on a dead worker fail immediately. Exit codes 0, 200 (`IntentionalRestartExitCode`) and 143 count as intentional; others become errors carrying the last 3 stderr lines. Restarts are sequential, 10 s apart; the error count resets after 30 error-free minutes; at 3 × max-process-count errors the host recycles *itself* ([RpcFunctionInvocationDispatcher.cs](https://github.com/Azure/azure-functions-host/blob/dev/src/Functions.Rpc.Server/Rpc/FunctionRegistration/RpcFunctionInvocationDispatcher.cs)). The PowerShell worker deliberately exits with 200 to pick up new module versions.
- **stdout/stderr.** stdout → Information logs; stderr lines are classified by *substring* ("warn", "error", "fail", …) — a known wart with an open TODO to remove it ([WorkerProcess.cs](https://github.com/Azure/azure-functions-host/blob/dev/src/Functions.Rpc.Server/ProcessManagement/WorkerProcess.cs)).
- **PowerShell worker.** Not a pwsh script but a .NET program embedding the PowerShell engine with a **runspace pool** (`PSWorkerInProcConcurrencyUpperBound`). The PowerShell docs warn that Azure PowerShell modules keep process-level state that races across runspaces, and recommend a runspace limit of 1 and scaling with processes instead ([PowerShell reference](https://learn.microsoft.com/en-us/azure/azure-functions/functions-reference-powershell)). Modules: "managed dependencies" (`requirements.psd1`, background upgrade checks) are not supported on the newer Flex Consumption plan; the alternative is a `Modules/` folder (added to `PSModulePath`, filled with `Save-PSResource`).
- **Environment and dependency isolation.** `worker.config.json` per language: `defaultExecutablePath`, `defaultWorkerPath` (templated with runtime version / OS / architecture), `supportedRuntimeVersions`, `defaultRuntimeVersion`, `workerIndexing`, `processOptions` ([Python](https://github.com/Azure/azure-functions-python-worker/blob/dev/workers/python/prodV4/worker.config.json), [PowerShell](https://github.com/Azure/azure-functions-powershell-worker/blob/dev/src/worker.config.json)). The Python worker's own dependencies (grpcio, protobuf) clashed with apps' copies: `PYTHON_ISOLATE_WORKER_DEPENDENCIES` chose a winner by clearing `sys.path`/`sys.modules` after init; for Python 3.13+ the worker is split into a thin protocol proxy plus an `azure-functions-runtime` library imported from the app's own dependencies, with isolation always on. Node likewise splits the platform-versioned worker from the app-versioned `@azure/functions` library.
- **Why .NET left the host process.** The first reason Microsoft gives for the isolated worker model is fewer assembly-version conflicts between the app and the host; in-process support ends 10 November 2026 ([isolated vs in-process](https://learn.microsoft.com/en-us/azure/azure-functions/dotnet-isolated-in-process-differences)).
- **Custom handlers (any language).** A second, much simpler tier: the host POSTs `{Data, Metadata}` to a local HTTP server and expects `{Outputs, Logs, ReturnValue}`; configured in `host.json` (`customHandler.description {defaultExecutablePath, arguments}`); the handler must start within 60 s ([custom handlers](https://learn.microsoft.com/en-us/azure/azure-functions/functions-custom-handlers)).
- **AWS Lambda Runtime API** ([runtime API](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-api.html), [custom runtime tutorial](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-walkthrough.html), [environment lifecycle](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)): a `bootstrap` executable polls `GET /runtime/invocation/next` and replies `POST …/{id}/response` or `…/{id}/error`; startup failures go to `/runtime/init/error` (separate channel), and the first `next` *is* the readiness signal. The tutorial's Bash runtime is about 15 lines of `curl`. Error types are categorised `Runtime.*` (runner fault) vs `Function.*` (user fault), body `{errorMessage, errorType, stackTrace[]}`. New protocol fields are added as optional headers whose omission is never rejected. A crash or timeout resets the environment; shutdown grace is 0/500/2000 ms depending on extensions, then SIGKILL.

**Lessons.** (1) One protocol + feature flags does carry five languages including PowerShell — but untyped string capabilities with mixed semantics and dead fields became debt: use a closed, typed capability set. (2) Silent degradation (cancel never delivered) is the default failure mode of capability maps; require each mount's needs to be checked against the runner's declared capabilities, or reflect the limitation in the generated API (e.g. a non-cancellable future type). (3) Split the protocol runner from the authoring library and isolate the runner's dependencies from the plugin's (the Python 3.13 redesign; the .NET isolated model; Node's split). (4) Separate launch→hello and hello→ready timeouts; reserve an exit code meaning "restart me intentionally"; attach the last stderr lines to crash errors; never classify stderr by substring. (5) Azure's capped restart that escalates to recycling the host is the same shape as OTP intensity; rutis's "withdraw services, app decides" is the explicit version. (6) PowerShell runspaces do not isolate process-level module state; prefer processes for isolation. (7) For the weakest languages, a two-tier design (rich protocol + a trivially implementable process contract such as custom handlers or Lambda's pull API) is established practice; error categories should separate runner faults from plugin faults.

### 2.3 Pulumi language hosts, providers and the Package Schema

- **Model.** The Go engine launches plugins named `pulumi-<kind>-<name>` (kinds: resource, language, analyzer, converter, tool). A *language host* such as `pulumi-language-python` is a small **Go** gRPC server that locates the interpreter, manages the virtualenv/toolchain and launches an in-language shim; the user program's SDK then talks gRPC directly to the engine's `ResourceMonitor` ([architecture: plugins](https://github.com/pulumi/pulumi/blob/master/docs/architecture/plugins.md), [languages](https://github.com/pulumi/pulumi/blob/master/docs/architecture/languages.md), [pulumi-language-python main.go](https://github.com/pulumi/pulumi/blob/master/sdk/python/cmd/pulumi-language-python/main.go)). Providers are separate gRPC processes (one per provider plugin); Python/TypeScript providers run without wrapper scripts because a `PulumiPlugin.yaml` names the runtime and the language host starts them (`RunPlugin`).
- **Protocol.** `LanguageRuntime`: `Handshake`, `GetRequiredPackages`, `Run`, `InstallDependencies` (streams output), `RunPlugin`, `GeneratePackage`, `GenerateProject`, `GenerateProgram`, `Pack`, `Link`, `Cancel`, … ([language.proto](https://github.com/pulumi/pulumi/blob/master/proto/pulumi/language.proto)). `ResourceMonitor`: `RegisterResource`, `Invoke`, `Call`, `SupportsFeature`, …, `SignalAndWaitForShutdown` (keeps the program's runtime alive to serve callbacks after the program body finishes) ([resource.proto](https://github.com/pulumi/pulumi/blob/master/proto/pulumi/resource.proto)). Remote function references exist as a `Callbacks` service (`{target, token}`, `Invoke(token, bytes)`) — the same idea as rutis's function references.
- **Capability negotiation, version 1 and 2.** `SupportsFeature(id)` with string ids (`secrets`, `resourceReferences`, `outputValues`, `deletedWith`, `transforms`, `parameterization`, …). The engine source now forbids adding more strings to that list because copying strings across codebases proved bug-prone; the replacement is a typed enum list `DeploymentInfo.supportedFeatures`, with fallback to the old probe when an older engine answers UNIMPLEMENTED ([source_eval.go](https://github.com/pulumi/pulumi/blob/master/pkg/resource/deploy/source_eval.go)). The provider `Handshake` exchanges booleans in both directions (engine: `configure_with_urn`, `supports_views`, …; provider: `accept_secrets`, `accept_resources`, `accept_outputs`, …); absent means false; a provider without `Handshake` gets the legacy path ([provider.proto](https://github.com/pulumi/pulumi/blob/master/proto/pulumi/provider.proto)).
- **Lifecycle.** The engine passes its address in argv; the plugin prints a single port line on stdout; the engine connects and calls `Handshake`. Invalid output and early exit produce distinct errors. Plugins poll the engine's gRPC health service and exit when the engine is gone (no orphans). Shutdown: interrupt the process tree, 5 s, kill. A provider's output is hidden unless it exits prematurely, in which case the engine dumps it and blames the provider. No automatic restart.
- **Environment.** Plugins live in `~/.pulumi/plugins/<kind>-<name>-<version>/` (newest satisfying version wins); a binary on `PATH` overrides the cache unless `PULUMI_IGNORE_AMBIENT_PLUGINS`. Python projects choose `toolchain: pip|poetry|uv`, `virtualenv`, and `typechecker: mypy|pyright` in `Pulumi.yaml`; Pulumi creates the venv and installs dependencies on `pulumi install`/`up` ([Python docs](https://www.pulumi.com/docs/iac/languages-sdks/python/)); interpreter = `PULUMI_PYTHON_CMD`, else `python3`, else `python`.
- **Interface descriptions: one neutral schema, sourced from code.** The Package Schema (`resources`, `functions`, `types`, primitives/arrays/objects/refs, per-language options) drives SDK generation for every language (`pulumi package gen-sdk --language …`) ([schema](https://www.pulumi.com/docs/iac/using-pulumi/extending-pulumi/schema/)). For *source-based components*, the schema is inferred from the author's code when the plugin starts: Python reads constructor annotations with `inspect.get_annotations` ([analyzer.py](https://github.com/pulumi/pulumi/blob/master/sdk/python/lib/pulumi/provider/experimental/analyzer.py)), TypeScript uses the compiler API ([analyzer.ts](https://github.com/pulumi/pulumi/blob/master/sdk/nodejs/provider/experimental/analyzer.ts)), Go uses struct tags; **unsupported types fail loudly** (unions, intersections, functions). Consumers run `pulumi package add <path|git>` and get an SDK generated locally in their own language; authors never touch gRPC ([source-based plugins](https://www.pulumi.com/docs/iac/guides/building-extending/packages/source-based-plugin/)).
- **Conformance.** `pulumi-test-language` runs one suite against every language host, tiered L1 (basic features), L2 (provider code paths), L3 (features needing advanced language support such as first-class functions) ([conformance tests](https://pulumi-developer-docs.readthedocs.io/latest/pkg/testing/pulumi-test-language/README.html)).

**Lessons.** (1) This is the closest model for rutis: **per-language extractor (TS checker, Python annotations, PowerShell `param()` parsing) → one neutral schema → typed bindings generated from the schema only**, rejecting unrepresentable types during extraction. (2) Write the per-language *launcher* in the host's language (Go for Pulumi, Rust for rutis): it finds the interpreter, sets up the venv/toolchain and streams dependency-installation output; the in-language SDK only speaks the protocol. (3) Start capability negotiation with a typed enum, not strings (Pulumi had to migrate). (4) Booleans where absent = false, plus a defined legacy path, make old/new peers interoperate. (5) Children should watch the parent and exit when it is gone. (6) A shared, tiered conformance suite run against every runner is how a multi-language host keeps semantics aligned; the tiers double as capability profiles.


### 2.4 Nushell plugin protocol (Rust host, any-language plugin processes)

The closest analogue to rutis: a Rust host, plugins as separate executables in any language, opaque plugin-owned live values, and callbacks into the host during a call.

- **Topology.** One OS process per plugin (each `.py` plugin gets its own `python`; no shared language host), started on first use and stopped by an idle "plugin GC". A plugin crash affects only that plugin's in-flight calls ([book: plugins](https://www.nushell.sh/book/plugins.html), `crates/nu-plugin-engine/src/init.rs`).
- **Transport and framing.** Default stdio: the plugin first writes its encoding as a length-prefixed name (`"\x04json"` or `"\x07msgpack"`); in JSON mode the engine newline-terminates messages so plugins can parse line by line ([protocol reference](https://www.nushell.sh/contributor-book/plugin_protocol_reference.html)). A `LocalSocket` feature was added so that plugins need not occupy stdio and can read the terminal: if the plugin's `Hello` lists it, the engine sends `Goodbye` and relaunches the plugin with `--local-socket <path>`; on failure it falls back to stdio (`nu-plugin-core/src/communication_mode/`).
- **Handshake and versioning.** Both sides send `Hello {protocol, version, features}`. Unknown features must be ignored; a side may only use features that *both* `Hello`s list; a plugin must not choose its features based on the engine's `Hello`. The version rule is a caret (semver-compatible) match between the two sides, so before 1.0 the *minor* version must match. The cost: minor releases come roughly every six weeks (0.107.0 on 2025-09-03 … 0.116.0 on 2026-09-26), the book tells users to update plugins with every Nushell update, the official Python example hard-codes `NUSHELL_VERSION = "0.116.0"`, and the community Go SDK sits at 0.114.0, which the caret rule refuses on 0.116 ([contributor book](https://www.nushell.sh/contributor-book/plugins.html), [releases](https://github.com/nushell/nushell/releases), [ainvaltin/nu-plugin](https://github.com/ainvaltin/nu-plugin)).
- **Messages.** Engine→plugin: `Call [id, Metadata|Signature|Run|GetCompletion|CustomValueOp]`, `EngineCallResponse`, `Signal (Interrupt|Reset)`, `Goodbye`, stream `Data/End/Drop/Ack`. Plugin→engine: `CallResponse`, `EngineCall {context, id, call}`, `Option {GcDisabled}`, streams. Engine calls (`GetConfig`, `GetEnvVar(s)`, `GetCurrentDir`, `AddEnvVar`, `EvalClosure`, `FindDecl`, `CallDecl`, `EnterForeground`, …) are only valid inside a call that is still in flight — callbacks are *call-scoped*. Streams use per-direction ids with `Ack` backpressure (writer window 100 list values / 50 byte buffers).
- **Interface description = runtime reflection, cached at registration.** `plugin add` runs the binary, checks compatibility, fetches `Metadata` + `Signature`s and stores them in the registry file (`plugin.msgpackz`), so the parser knows every plugin command at startup without launching plugins; users must re-run `plugin add` after upgrading a plugin. Signatures are typed shapes (positional/named params, input/output types) that the parser checks statically — the closest precedent for "reflection cached ahead of time, then used for static checking in the host". Other languages write these dictionaries by hand; there is no codegen.
- **Live values.** `PluginCustomValue {name, data: bytes, notify_on_drop}`: an opaque blob the engine holds and operates on by calling back into the owning plugin (`ToBaseValue`, `FollowPath*`, `PartialCmp`, `Operation`, `Save`, `Dropped`). A plugin only ever receives its own custom values (`CustomValueIncorrectForPlugin`). Live state (the polars plugin) is an opt-in pattern: the blob is a UUID into a ref-counted cache, the plugin sets `GcDisabled` while the cache is non-empty, and frees entries on `Dropped`. The docs warn that every emission counts as a new value for drop checking, so a value sent back and returned yields two drop notifications — a pitfall for anyone using drops as reference counts. The engine will even *start* a stopped plugin just to deliver `Dropped`.
- **Cancellation.** No per-call cancel: only a global `Interrupt` signal to every running plugin plus stream `Drop`. Plugins run in their own process group so that Ctrl-C in the terminal does not kill them.
- **Errors.** `LabeledError {msg, labels: [{text, span}], code, url, help, inner}`; spans point into the engine's source text.
- **Lifecycle.** Readiness = `Hello`. GC: `$env.config.plugin_gc = {default: {enabled: true, stop_after: 10sec}, plugins: {…}}`; held custom values do *not* count as activity, so authors must remember `GcDisabled`. Stop = wait for activity to end, send `Goodbye`, close stdin; the process is not killed. Crash = EOF fails all pending calls with a closed-unexpectedly error; the next call restarts the plugin lazily, with no backoff or limit. stdout is the protocol in stdio mode, stderr is inherited and is the documented debug channel.
- **Environment.** Plugins inherit the caller's environment (a source comment notes that Python virtualenvs depend on this); interpreter chosen by extension (`.py` → `python`, `.rb` → `ruby`, `.nu` → `nu --stdin`; Unix shebang otherwise) or `plugin add --shell <path>`, stored in the registry.

**Lessons.** (1) Version coupling is the dominant ecosystem cost: an exact or minor-locked protocol version across five hand-written runtimes means constant churn — version the wire separately from rutis releases and grow it with a `features` list. (2) Distinguish self-contained values from live references, and bind live references to one process incarnation: fail them deterministically when that process dies; never resurrect a process to deliver a `release`. (3) Count transfers, not identities — rutis's `release {reference, count}` already does this better than Nushell's per-emission drops. (4) If mounts are ever idle-stopped, liveness must follow reachability (outstanding references, futures, subscriptions keep the mount alive) by construction, not by author discipline. (5) A stdio/line-JSON baseline is what lets Python and Nu scripts participate at all. (6) Make cancellation a declared capability (`cooperative | kill | none`).

### 2.5 Babashka pods (any-language "pods" for a Clojure interpreter)

- **Model.** A pod is any executable exposing namespaces and functions to babashka (or the JVM). The client starts it, sends `{"op": "describe"}`, builds proxy functions from the reply, and turns each call into `{"op": "invoke", "id", "var", "args"}`. Messages are bencode dictionaries; argument and result payloads are strings in a format the pod picks in `describe` (EDN, JSON, Transit+JSON) ([README](https://github.com/babashka/pods/blob/master/README.md)).
- **Runtime reflection with a cache.** `describe` returns namespaces, vars (names plus optional `meta` such as `:doc`, `:arglists`), and an `ops` map of optional operations (e.g. `shutdown`). No types. For pods declared in `bb.edn` the reply is cached (`metadata.cache`); `:cache false` exists for pods under active development — i.e. stale cached metadata is a known failure mode. Namespaces marked `"defer"` are loaded on first `require` (`load-ns`).
- **Results and errors.** `{"id", "value", "status": ["done"]}`; errors carry `ex-message`/`ex-data` with `"error"` in `status`. Several `value` messages before `done` give async/streaming results, consumed via `babashka.pods/invoke` with `:handlers`. No cancel, no flow control, no object references.
- **Host-side adaptation.** Pods may ship Clojure `code` that the client evaluates to build idiomatic APIs (macros, callback wrappers) over the plain request/response wire — callbacks never cross the process boundary.
- **Capabilities.** Optional operations are discovered from `ops`, each with a defined fallback (no `shutdown` → the process is killed). No protocol version at all; the README calls the protocol alpha.
- **Lifecycle and I/O.** stdio by default; output printed by the pod during a call travels as `out`/`err` fields tagged with the call id; a socket mode (`BABASHKA_POD_TRANSPORT=socket`, port written to a file) frees the terminal for TUI pods. EOF fails all pending calls with an unexpected-quit error; no restart.
- **Distribution.** A central registry of manifests: per-OS/arch artifacts with sha256, downloaded on `(load-pod 'org.babashka/aws "0.0.5")` ([pod-registry](https://github.com/babashka/pod-registry)). The Python example needs a pre-installed `bcoding`; nothing manages Python environments. The README estimates that bencode takes only a few hundred lines to implement in most languages.

**Lessons.** (1) Put the adaptation on the host side: for low-capability profiles the *generated Rust bindings* can present idiomatic shapes over plain request/response frames. (2) Every optional operation needs a specified fallback or a hard rejection. (3) Cache the interface description but key it by content hash and verify it at startup. (4) Tag plugin output with the call id where possible.

### 2.6 HashiCorp go-plugin and Terraform

**go-plugin** ([README](https://github.com/hashicorp/go-plugin), [internals](https://github.com/hashicorp/go-plugin/blob/main/docs/internals.md), [non-Go guide](https://github.com/hashicorp/go-plugin/blob/main/docs/guide-plugin-write-non-go.md), `client.go`, `server.go`, `grpc_broker.go`):

- **Model.** The host wraps an `exec.Cmd` in a `plugin.Client`, reads one handshake line from the child's stdout, dials the advertised Unix socket (TCP on Windows) and speaks net/rpc or gRPC. One process per `Client`; a started `Client` can never be restarted (restart = new `Client`). Non-Go plugins implement the gRPC side by hand (the Python example is ~30 lines).
- **Handshake.** `CORE-PROTOCOL-VERSION|APP-PROTOCOL-VERSION|NETWORK-TYPE|NETWORK-ADDR|PROTOCOL`, e.g. `1|3|unix|/path/sock|grpc`; field 6 carries an AutoMTLS cert, an optional field 7 advertises broker multiplexing (only appended when asked, because old clients split into at most 6 fields). A malformed line yields an error listing likely causes (wrong architecture, missing libraries, permissions). The *magic cookie* env var is documented as a usability aid, explicitly not a security measure: a plugin started by hand prints a hint to launch the host program instead and exits.
- **Two-tier versioning.** The core version must be `1`. App versions are negotiated: the host exports `PLUGIN_PROTOCOL_VERSIONS` (keys of `VersionedPlugins map[int]PluginSet`); the plugin picks its newest listed version; on no match it falls back and the host reports both sides' version lists.
- **Interfaces.** Shared `.proto` + per-language codegen; Go authors also hand-write client/server adapters per interface (the README calls this the most tedious step).
- **Callbacks/objects.** `GRPCBroker`: one side `AcceptAndServe(NextId(), …)` and sends the `uint32` id in an ordinary field; the other `Dial(id)`s (5 s timeout). Without multiplexing each served object costs a new listener socket; there is no release or reference count — a served object lives until its listener or the broker closes.
- **Capabilities.** No feature negotiation; optional services degrade *silently* (a plugin without `GRPCStdio` just logs a warning; controller/broker errors are ignored). The one explicit rejection: host requires multiplexing, plugin does not advertise it → `ErrGRPCBrokerMuxNotSupported` at start.
- **Lifecycle.** `StartTimeout` default 1 min, with distinct errors for timeout vs exit-before-handshake. Non-Go plugins must serve the gRPC health service named `plugin`; `Ping()` is on demand, not periodic. `Kill()`: graceful `GRPCController.Shutdown`, wait up to 2 s, then SIGKILL; idempotent; `Managed: true` + `CleanupClients()` kills all children on host exit. The plugin side ignores SIGINT so the host owns teardown. `ReattachConfig` attaches to an already-running plugin (debugging, host upgrades).
- **stdout/stderr.** After the handshake, stdout is drained and discarded; stderr is read line by line into an hclog logger named after the plugin (JSON lines become structured entries; `[TRACE]…[ERROR]` prefixes set levels; a `panic:` line switches following lines to Error). Go plugins' own stdout/stderr are swapped for pipes and streamed to the host via `GRPCStdio`.
- **Environment.** The host supplies the full command line (e.g. `KV_PLUGIN="python plugin.py"`); no interpreter discovery. `SecureConfig` checksums `cmd.Path` only — for `python plugin.py` that is the interpreter, not the script [inference].

**Terraform** ([plugin protocol](https://developer.hashicorp.com/terraform/plugin/terraform-plugin-protocol), [tfplugin6.proto](https://github.com/hashicorp/terraform/blob/main/docs/plugin-protocol/tfplugin6.proto)) builds on go-plugin: `VersionedPlugins{5, 6}`; major versions break, minors only add and are *not sent on the wire* — feature detection instead. `ServerCapabilities {plan_destroy, get_provider_schema_optional, move_resource_state, generate_resource_config}` and per-request `ClientCapabilities {deferral_allowed, write_only_attributes_allowed, …}` flow in both directions. Schemas are runtime reflection (`GetProviderSchema`), cached per provider address. Business errors are `Diagnostic {severity, summary, detail, attribute}` in the response; gRPC codes are reserved for transport (`Unavailable` ≈ crashed, `Canceled`, `Unimplemented` = method unsupported). Each provider factory call starts a new process. On a provider panic Terraform captures up to 100 stderr lines and prints them with a message that the provider crashed and the bug should be reported.

**Lessons.** (1) Version in two tiers: a tiny exact-match core + negotiated or feature-flagged application level. (2) Keep the mandatory surface tiny, but declare every optional feature and fail at bind time — go-plugin's silent fallbacks are exactly what (d) should avoid. (3) Shutdown ladder: graceful frame → bounded grace → SIGKILL, idempotent, plus a global "kill all children on host exit". (4) Keep a protocol channel separate from stdout (rutis already does; go-plugin's stdout handshake breaks on one stray print), but *capture* stderr per plugin with attribution and keep the last lines for crash reports. (5) In-band, counted references (rutis) beat go-plugin's socket-per-object broker. (6) Separate error variants: business error, crash/unavailable, unsupported, cancelled.

### 2.7 osquery extensions and Steampipe

- **osquery** ([SDK](https://osquery.readthedocs.io/en/stable/development/osquery-sdk/), [deployment](https://osquery.readthedocs.io/en/stable/deployment/extensions/), [osquery.thrift](https://github.com/osquery/osquery/blob/master/osquery/extensions/thrift/osquery.thrift), [osquery-python](https://github.com/osquery/osquery-python)). The daemon runs a Thrift `ExtensionManager` on a Unix socket; an extension process connects and calls `registerExtension(InternalExtensionInfo{name, version, sdk_version, min_sdk_version}, ExtensionRegistry)`, then serves its own `Extension` service (`ping`, `call`, `shutdown`) on `<socket>.<uuid>`. One extension process may hold many table/config/logger plugins. **Self-description at registration:** the registry carries each table's columns `{name, type, op}`. The data model is all strings (`map<string,string>` requests, `list<map<string,string>>` rows) — a deliberately low common denominator. **Liveness both ways:** the extension pings the core every `--interval` and exits when the core is gone (osquery-python calls `os._exit(1)`); the core pings every extension every `--extensions_interval` (default 3 s) and removes all of an extension's plugins on failure. `--extensions_require` waits up to `--extensions_timeout` (default 3 s). The watchdog relaunches dead autoloaded extensions; stopping is graceful kill → 4 s → hard kill. Autoloaded binaries must pass a safe-permissions check (root-owned, not world-writable) unless `--allow_unsafe`. Python DX: decorate a `TablePlugin` subclass with `@osquery.register_plugin`, implement `columns()` and `generate(context)`.
- **Steampipe** ([plugin manager](https://github.com/turbot/steampipe/blob/main/pkg/pluginmanager_service/plugin_manager.go), [plugin.proto](https://github.com/turbot/steampipe-plugin-sdk/blob/main/grpc/proto/plugin.proto)): a plugin manager (itself a go-plugin server) owns all plugin processes and hands `ReattachConfig`s to consumers; one plugin process serves many connections; capabilities are a struct of booleans from `GetSupportedOperations`; a dead plugin is dropped and restarted lazily on the next request (retryable error). Per-plugin memory limits are set via `GOMEMLIMIT`. Go-only SDK.

**Lessons.** A typed registry broadcast at registration suits languages without build-time extraction; a two-way heartbeat plus "exit when the host is gone" closes the orphan gap; one dead process removes all its plugins at once (the same unit as a rutis mount); a single owner of all child processes simplifies teardown; lazy restart on next use is the common pattern for stateless plugins.

### 2.8 Dapr pluggable components

([overview](https://docs.dapr.io/developing-applications/develop-components/pluggable-components/pluggable-components-overview/), [registration](https://docs.dapr.io/operations/components/pluggable-components-registration/), [discovery.go](https://github.com/dapr/dapr/blob/master/pkg/components/pluggable/discovery.go)) A component is a gRPC server in any language, started by the user (not by Dapr) before Dapr. Discovery: Dapr lists `$DAPR_COMPONENTS_SOCKETS_FOLDER` (default `/tmp/dapr-components-sockets`), the socket file name is the component name, and gRPC reflection (`ListServices`) tells which known interfaces it implements (`StateStore`, `TransactionalStateStore`, `QueriableStateStore`, …). Fine-grained capabilities come from `Features()` (a `repeated string`, fetched once during `Init`: `ETAG`, `TRANSACTIONAL`, `QUERY_API`, `TTL`, …). Unsupported use is rejected at the API boundary with a dedicated error (`TransactionsNotSupported`, gRPC `Unimplemented`). Every service has `Init / Features / Ping`. One process may serve several instances, selected per call by an `x-component-instance` header. SDKs: Go and .NET only, both still marked as under development.

**Lessons.** Capability = declared interfaces + feature strings, checked at the API boundary with a dedicated "unsupported" error; `Init/Features/Ping` is a good minimal per-service lifecycle; a per-call instance selector lets one process host several plugin instances.

### 2.9 Telegraf `execd`, Erlang/Elixir ports, Tauri sidecars (process-contract precedents)

- **Telegraf execd** ([inputs/execd](https://github.com/influxdata/telegraf/blob/master/plugins/inputs/execd/README.md), [internal/process](https://github.com/influxdata/telegraf/blob/master/internal/process/process.go)): a long-running process in any language; stdout parsed in a data format (inputs), stdin fed metrics (outputs/processors). `signal = none|STDIN|SIGHUP|SIGUSR1|SIGUSR2` triggers collection. stderr goes to Telegraf's log, with `E!/W!/I!/D!/T!` prefixes selecting the level. `restart_delay` (default 10 s) restarts without limit; stop = close stdin → 5 s → SIGTERM → 5 s → SIGKILL. `command` is an argv array (no shell). Pitfall: outputs are fire-and-forget (a metric counts as delivered once it is in the pipe), and processors cannot correlate outputs with inputs. A Go "shim" runs an in-tree plugin out of process unchanged.
- **Erlang ports** ([open_port/2](https://www.erlang.org/doc/apps/erts/erlang.html#open_port/2)): framing options `{packet, 1|2|4}` (length prefix), `{line, L}`, or raw `stream`; `nouse_stdio` moves the channel to **fds 3 and 4**, leaving stdio free; `exit_status` reports signals as 128+n. **Elixir** ([Port: orphan OS processes](https://hexdocs.pm/elixir/Port.html)): if the VM dies, the child's stdin/stdout close but the child is *not* killed — external programs must exit on stdin EOF, or be wrapped in a script that does. **OTP supervisors** ([supervisor principles](https://www.erlang.org/doc/system/sup_princ.html)): restart types `permanent | transient | temporary`; more than `intensity` restarts within `period` seconds (defaults 1 and 5) makes the supervisor give up and escalate; shutdown is `brutal_kill` or a timeout (5000 ms default) before a hard kill.
- **Tauri sidecars** ([sidecar](https://v2.tauri.app/develop/sidecar/)): bundled external binaries named `<name>-<target-triple>`, spawnable only through declared, permission-scoped identities with optional argument validators; the shell plugin kills children it tracks on app exit, but children spawned from Rust via `sidecar(..).spawn()` must be killed by the app.

**Lessons.** The likely shape of a "script" profile is execd-like (argv, data in/out, stderr as levelled log), but even the minimal profile needs request ids and explicit return/throw, or failures are lost. Adopt the close → SIGTERM → SIGKILL ladder. Every runner must exit on EOF of its control channel (wrapper where the runtime cannot). rutis's no-restart policy is OTP's `temporary`; if restarts are added, use `transient` with intensity/period and escalation. Track every child in one table killed at exit.

### 2.10 LSP, DAP and MCP (stdio protocols built around capability negotiation)

**LSP 3.17** ([spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/), [metaModel.json](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/metaModel/metaModel.json), [vscode-languageserver-node client.ts](https://github.com/microsoft/vscode-languageserver-node/blob/main/client/src/common/client.ts)):

- **No version handshake, only capabilities.** One `initialize` exchange swaps `ClientCapabilities` / `ServerCapabilities`; a missing property means the capability is absent, unknown properties are ignored, and an unknown server capability must not fail `initialize` (the old `unknownProtocolVersion` error is deprecated because 3.x has no version handshake). Some capabilities are signalled per request (e.g. a `workDoneToken`); the client offers `positionEncodings` and the server picks one. Dynamic (un)registration is opt-in per feature.
- **One neutral model, generated bindings.** The protocol is written in TypeScript; `metaModel.json` (67 requests, 26 notifications, 324 structures in 3.17) is generated from that TypeScript, and other languages generate bindings from the model: `lsprotocol` (Python, Rust), gopls (Go). This is exactly the "per-language front-end → neutral model → per-language back-end" shape.
- **Framing.** `Content-Length` header + JSON-RPC 2.0 body over stdio, pipe, socket or node-ipc. Methods starting with `$/` are optional (requests must still be answered with MethodNotFound).
- **Lifecycle.** Before `initialize` the server answers requests with `ServerNotInitialized (-32002)`. Shutdown is a `shutdown` request then an `exit` notification (exit code 0 only if `shutdown` came first). `processId` in `initialize` lets the server exit when its parent dies.
- **Cancellation is advisory but must terminate.** `$/cancelRequest {id}`; the cancelled request must still return (a result, partial result, or `RequestCancelled -32800`); `ContentModified -32801`, `ServerCancelled -32802`. The spec notes that a single-threaded synchronous server can do little with cancel — pyright accepts a file-based cancellation channel so a busy server can poll for it.
- **Restart policy (client side).** vscode-languageclient's default error handler restarts a crashed server up to 4 times; on the 5th crash within 3 minutes it stops restarting. `stop()` races shutdown+exit against 2 s, then kills the whole process tree. Server stdout/stderr are forwarded line by line to an output channel.

**DAP** ([overview](https://microsoft.github.io/debug-adapter-protocol/overview), [debugAdapterProtocol.json](https://github.com/microsoft/debug-adapter-protocol/blob/main/debugAdapterProtocol.json)): same framing, its own `{seq, type: request|response|event}` messages, still at its first version: every new feature gets a flag, and absence of a flag always means unsupported (42 adapter flags such as `supportsCancelRequest`, `supportsTerminateRequest`; client flags such as `supportsRunInTerminalRequest`). Reverse requests (`runInTerminal`, `startDebugging`) are allowed only if the client declared them. `cancel` is only sent if declared and still requires a response (`success: false, message: "cancelled"`). Two-stage stop: `terminate` (graceful, may be refused) then `disconnect` (forceful, including child processes). **Object references are integers valid only while the debuggee is suspended**; when execution resumes the counter can reset, so no release messages exist at all.

**MCP** ([versioning](https://modelcontextprotocol.io/specification/versioning), [2026-07-28 stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [2025-11-25 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [Python SDK](https://py.sdk.modelcontextprotocol.io/), [FastMCP tools](https://gofastmcp.com/servers/tools)):

- **Versioning.** Date strings (`YYYY-MM-DD`) that change only on backwards-incompatible changes. Up to 2025-11-25: `initialize` with a version proposal and echo, after which only negotiated capabilities may be used. The current revision **2026-07-28 removed the handshake and protocol-level sessions**: every request carries `protocolVersion` and `clientCapabilities` in `_meta`; servers implement `server/discover`; dedicated errors `-32022 UnsupportedProtocolVersion` (with `data.supported` and `requested`) and `-32021 MissingRequiredClientCapability` (with `data.requiredCapabilities`); when an extension is missing on the other side, the supporting side must either fall back to core behaviour or reject the request. The handshake went together with protocol-level sessions: state must now be referenced by explicit ids, and a stdio process is explicitly not a session.
- **stdio rules.** One message per line, no embedded newlines; the server must not write anything but protocol messages to stdout; logs go to stderr, which the client must not interpret as errors. Shutdown: close the server's stdin, wait, SIGTERM, SIGKILL; servers should exit on stdin EOF (the only portable graceful signal). On unexpected exit the client should restart; in-flight requests are lost. The Python SDK client spawns servers in a new session/process group, passes only a minimal environment (HOME, LOGNAME, PATH, SHELL, TERM, USER) and escalates close → 2 s → SIGTERM to the group → 2 s → SIGKILL.
- **Cancellation and errors.** `notifications/cancelled {requestId}`; the receiver should stop and *not* respond; late responses are ignored (unlike LSP/DAP/Bazel, which require a terminal reply). Every request should have a timeout. Protocol errors are JSON-RPC errors; tool execution errors are normal results with `isError: true`.
- **Interfaces = runtime reflection as JSON Schema.** `tools/list` returns `inputSchema` (JSON Schema 2020-12) and optional `outputSchema`.
- **DX: schema from type hints.** In the Python SDK (`FastMCP`, renamed `MCPServer` in v2), `@mcp.tool()` takes the name from the function, the description from the docstring, the input schema from type hints via Pydantic (defaults → optional, `Annotated[int, Field(ge=1, description=…)]` → constraints, `Literal` → enum, models → `$defs`), and the output schema from the return annotation; a parameter annotated `Context` is injected and omitted from the schema; bad arguments are rejected before the function runs. Async handlers are cancelled at their next `await`; sync handlers run in a thread and only stop at explicit checkpoints, otherwise their result is discarded. The TypeScript SDK does the same with zod/Standard Schema.

**Lessons.** (1) Keep one major version for framing breaks and negotiate everything else as named capabilities ("absent = unsupported, unknown = ignored"). (2) Put one neutral interface model between language-specific extractors and the Rust generator (LSP's metaModel). (3) A cancelled call must still end with a terminal frame (`throw {Cancelled}` or `return`) so Rust futures and reference counts settle deterministically — the LSP/DAP/Bazel rule, not MCP's "do not respond". (4) Weak runtimes need an out-of-band cancel path (signal or file). (5) Reject with typed errors that list what *is* supported (MCP -32021/-32022). (6) rutis mounts are stateful (references, fibers, subscriptions), so keep a handshake. (7) The Python authoring model should be decorators + type hints (+ `Annotated`/`Field`), with an injected context object; the same introspection can run at build time to produce the description the Rust generator consumes. (8) Call-scoped references (DAP) need no release protocol at all — a natural middle profile.

### 2.11 Jupyter kernels (one process per kernel; wrapper kernels for shells)

([messaging](https://jupyter-client.readthedocs.io/en/latest/messaging.html), [kernels](https://jupyter-client.readthedocs.io/en/latest/kernels.html), [restarter.py](https://github.com/jupyter/jupyter_client/blob/main/jupyter_client/restarter.py), [wrapper kernels](https://jupyter-client.readthedocs.io/en/latest/wrapperkernels.html), [bash_kernel](https://github.com/takluyver/bash_kernel/blob/master/bash_kernel/kernel.py))

- **Model.** A kernel manager launches one kernel process per kernelspec; the kernel binds five ZeroMQ sockets: shell (requests), IOPub (broadcast of all side effects incl. stdout/stderr and status), stdin (kernel asks the frontend for input), **control** (same as shell but on a separate socket so shutdown/interrupt/debug do not queue behind long executions; recommended to run in its own thread), heartbeat. Messages are HMAC-signed (key from the connection file).
- **Self-description and capabilities.** `kernel_info_reply` carries `protocol_version` (major changes only for incompatible changes), implementation, `language_info`, and `supported_features` (e.g. `debugger`). Kernels must implement execute, kernel_info and busy/idle status; everything else is optional and kernels may simply not reply to messages they do not handle. The kernelspec declares `interrupt_mode`: `signal` (SIGINT to the process group) or `message` (`interrupt_request` on control) — a per-language capability for runtimes that cannot handle signals. Frontends that cannot answer input send `allow_stdin: false`.
- **Readiness.** `wait_for_ready` repeats `kernel_info_request` until a reply *and* an IOPub message arrive (5.5 adds `iopub_welcome`); otherwise the client reports that the kernel died before replying. 5.6 adds a registration handshake in which the kernel picks its own ports.
- **Shutdown, orphans, restart.** `shutdown_request {restart}` on control; `shutdown_wait_time` 5 s split into request → SIGTERM → SIGKILL, signals sent to the kernel's process group (`start_new_session=True`). ipykernel watches `JPY_PARENT_PID` every second and exits when its parent changes. `KernelRestarter` polls `is_alive()` every 3 s and allows `restart_limit = 5` consecutive restarts; a kernel alive for 10 s counts as stable.
- **Output.** ipykernel replaces `sys.stdout/stderr` with objects publishing `stream` messages; `capture_fd_output` also captures fd-level writes from C extensions.
- **Environment.** `ipykernel install --name … --sys-prefix` writes a `kernel.json` whose `argv` is the absolute interpreter of that environment — the environment is pinned by an explicit, generated spec, not discovered at run time. Kernelspecs are looked up in user/env/system directories.
- **Wrapper kernels for weak languages.** A wrapper kernel subclasses `ipykernel.kernelbase.Kernel` in Python and implements `do_execute`. bash_kernel drives a persistent bash through pexpect with a random sentinel prompt, reads `$?` after each cell, interrupts with SIGINT and restarts bash on EOF; jupyter-powershell is derived from it. (.NET Interactive, which included PowerShell, was deprecated and archived in April 2026.)

**Lessons.** Cancel/release/shutdown need a lane that cannot queue behind a long call (separate socket or a dedicated reader thread per runner; rutis's Node runner already reads on an I/O worker thread). "Ready" means an application round-trip succeeded, not "process alive". Generate a per-environment spec recording the absolute interpreter path. The protocol can be terminated in a capable language that drives a weak one (bash_kernel); for Bash/PowerShell a persistent REPL with a sentinel prompt is a proven, if fragile, pattern.

### 2.12 Bazel persistent and multiplex workers

([persistent workers](https://bazel.build/remote/persistent), [creating workers](https://bazel.build/remote/creating), [multiplex](https://bazel.build/remote/multiplex), [worker_protocol.proto](https://github.com/bazelbuild/bazel/blob/master/src/main/protobuf/worker_protocol.proto))

- `WorkRequest {arguments, inputs[{path, digest}], request_id, cancel, verbosity, sandbox_dir}` / `WorkResponse {exit_code, output, request_id, was_cancelled}` on stdin/stdout; protobuf with varint length prefix, or JSON (no delimiter; unknown fields must be tolerated, missing fields take defaults). `request_id` 0 = singleplex; non-zero = multiplex, matched by id. Every non-cancel request must be answered exactly once, even when cancelled.
- **Capabilities are static execution requirements, not negotiation**: `supports-workers`, `supports-multiplex-workers`, `supports-worker-cancellation`, `supports-multiplex-sandboxing`, `requires-worker-protocol: json|proto`. Bazel never sends an unsupported feature; without cancellation support it waits for the in-flight reply before reusing the worker.
- **Process sharing is decided by a `WorkerKey`**: startup args, environment, exec root, mnemonic, and the sandbox/multiplex/cancel/protocol flags; digests of the worker's own files are rechecked whenever a worker is reused. Pools: 4 singleplex workers per mnemonic, 8 concurrent requests per multiplex process by default.
- **stdout is protocol-only**; stray output fails with a message asking whether you printed to stdout; stderr goes to a per-worker log file. A crashed worker fails the in-flight action (with up to 8 KB of its log); dead or changed workers are discarded on next use and replaced on demand.

**Lessons.** Define a *mount key* (language, resolved interpreter path + version, environment digest, plugin-set digest, wire format, profile): only mounts with equal keys may share a process, and any change forces a new one. Capabilities can live in the build-time manifest and merely be checked at the handshake. Exactly one terminal reply per call.

### 2.13 VS Code extension host and Sublime Text `plugin_host`

- **VS Code** ([extension host](https://code.visualstudio.com/api/advanced-topics/extension-host), [activation events](https://code.visualstudio.com/api/references/activation-events), [rpcProtocol.ts](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/extensions/common/rpcProtocol.ts)). All local extensions share one Node extension-host process by default. A **static manifest** (`contributes`, `activationEvents`, `extensionDependencies`, `engines.vscode`) lets the UI show commands and menus without running extension code; extensions activate lazily. Handshake: child sends `Ready`, parent sends `initData`, child compares the build commit and exits with a dedicated code (55) on mismatch, then `Initialized`. Every RPC request is **acknowledged** as soon as its handler starts; if no ack arrives within 3 s while requests are pending, the host is marked unresponsive, profiled, and a specific extension can be blamed. Cancellation tokens travel with requests. The child polls its parent PID every second (plus a native watchdog) so it dies with its parent; extensions cannot call `process.exit()`. Crashed hosts are restarted automatically unless they crashed 3 times within 5 minutes (then the user gets "Extension Bisect"). Shared fate was mitigated later by `extensions.experimental.affinity`, which assigns extensions to additional host processes — but extensions linked by `extensionDependencies` are always kept in the same process because they share live API objects. stdout/stderr of the host are forwarded line by line; RPC uses its own channel.
- **Sublime Text** ([API environments](https://www.sublimetext.com/docs/api_environments.html)). All plugins of one Python version share one `plugin_host` process and one embedded Python. There is one host per Python version (3.3, and 3.8 later replaced by 3.14); a package selects its version with a `.python-version` file, and a missing or unknown value **silently falls back to 3.3**. Retiring the 3.3 host has dragged on from 2025 into 2026. Libraries are installed into one shared folder per Python version. A host crash is not restarted.

**Lessons.** Static manifest + lazy activation is the main startup lever (rutis's generated bindings can be that manifest: spawn a runner only on first use, if desired). VS Code independently arrived at rutis's *mount*: co-dependent extensions must share a process; affinity groups are the knob users need. An ack separate from the reply cheaply distinguishes a blocked runner from a slow async call. A distinct exit code for version mismatch and a parent-death watchdog make failures diagnosable. One host per runtime version means carrying old runtimes for years; silent fallback to a default version is the pattern to avoid.

### 2.14 Script-metadata systems: Raycast Script Commands, xbar/SwiftBar, Stream Deck

- **Raycast Script Commands** ([repo](https://github.com/raycast/script-commands), [arguments](https://github.com/raycast/script-commands/blob/master/documentation/ARGUMENTS.md)): any executable script (templates for Bash, AppleScript `on run argv`, Python, Ruby, Node, Swift, …) run as a fresh process per invocation; the interface is a comment header `# @raycast.<key> <value>` with a mandatory `schemaVersion` (only version 1 exists), `title`, `mode`, and up to three arguments declared as JSON objects (`{"type": "text"|"password"|"dropdown", "placeholder", "optional", …}`) passed as `$1..$3`. Non-zero exit = failure, last output line = error message. Counter-example: `inline` mode without `refreshTime` silently becomes `compact`.
- **xbar / SwiftBar** ([xbar CONTRIBUTING](https://github.com/matryer/xbar-plugins/blob/main/CONTRIBUTING.md), [SwiftBar](https://github.com/swiftbar/SwiftBar)): refresh interval in the file name (`date.1m.sh`), metadata tags in comments (`<xbar.title>`, `<xbar.dependencies>`), typed variables (`<xbar.var>string(VAR_NAME="…"): …</xbar.var>`) that become environment variables and stored preferences; output is stdout lines with a small markup. SwiftBar adds `streamable` plugins: a long-lived process emitting updates separated by `~~~` lines; exit status distinguishes success/error. Compiled plugins keep metadata in an extended attribute.
- **Elgato Stream Deck** ([manifest schema](https://schemas.elgato.com/streamdeck/plugins/manifest.json), [registration parameters](https://github.com/elgatosf/streamdeck/blob/main/packages/plugin/src/api/registration/parameters.ts)): the app launches `CodePath` (per-OS overrides) with `-port -pluginUUID -registerEvent -info`; the plugin connects back over a local WebSocket and registers with the one-time UUID. Node plugins run on an app-supplied runtime pinned in the manifest (`Nodejs.Version`) with global module search paths disabled.

**Lessons.** For Bash, AppleScript and PowerShell a versioned comment header with JSON-typed parameters is a proven interface definition that can be parsed at build time without executing the script. These systems also show the natural restricted profile — one process per call, simple values in, text out, exit code + last line as error — and that refusing unsupported features is better than Raycast-style silent fallbacks. Streams remain possible over a long-lived process with a frame delimiter. A connect-back handshake (endpoint + one-time token in argv) works in any language.

### 2.15 Wasm Component Model + WIT, wRPC, Extism, Zed (the "one IDL, in-process" alternative)

([WIT](https://component-model.bytecodealliance.org/design/wit.html), [Explainer](https://github.com/WebAssembly/component-model/blob/main/design/mvp/Explainer.md), [wasmtime bindgen!](https://docs.rs/wasmtime/latest/wasmtime/component/macro.bindgen.html), [WASI releases](https://wasi.dev/releases), [WASI proposals](https://github.com/WebAssembly/WASI/blob/main/docs/Proposals.md), [componentize-py](https://github.com/bytecodealliance/componentize-py), [wRPC](https://github.com/bytecodealliance/wrpc), [Extism](https://extism.org/docs/concepts/plug-in), [xtp-bindgen](https://github.com/dylibso/xtp-bindgen), [Zed extensions](https://zed.dev/docs/extensions/developing-extensions))

- **What it offers.** WIT packages define interfaces and worlds (imports + exports); components share no memory; values cross via the Canonical ABI. Types: primitives, string, record, variant, enum, flags, list, option, result, tuple, **resources** with methods, and (WASI 0.3) `async func`, `stream<T>`, `future<T>`. There is no function/closure type and no dynamic "any". Handles are `own` (destroyed when dropped) or `borrow` (must be dropped before the current call returns), enforced by the runtime. Host side: Wasmtime's `bindgen!` generates statically typed Rust traits and functions. **Unsupported imports are rejected at instantiation** (an opt-in mode installs trapping stubs instead) — "reject at link time" is the default.
- **Status.** WASI 0.3.0 (native async) was published 2026-06-11, 0.3.1 on 2026-08-11; Wasmtime 46+ runs 0.3 components by default. Phase-3 proposals cover clocks, random, filesystem, sockets, cli, http. **No proposal at any phase covers process spawning** (the `posix_spawn` issue #414 from 2021 is open and inactive); threads are at phase 1.
- **Python** (componentize-py 0.25): bundles a customised CPython per component; dependencies are resolved at build time; native extensions need special WASI builds (the NumPy example uses an unofficial build); no subprocess. **JS** (ComponentizeJS/jco): embeds SpiderMonkey (~8 MB), experimental. **.NET** (componentize-dotnet): NativeAOT-LLVM, which rules out dynamic loading and runtime codegen — i.e. no PowerShell.
- **wRPC** carries WIT-typed calls across processes (TCP, Unix sockets, QUIC, …), with generators only for Rust and Go; **resources travel as opaque byte blobs with no drop or reference counting on the wire** — the hard part rutis already solved is exactly what it leaves out.
- **Extism**: plug-ins are Wasm modules with a bytes-in/bytes-out interface plus host functions; the Python PDK only supports pure-Python dependencies. Its own docs say host and guest must agree on the interface out of band — which is why the XTP schema (an OpenAPI-like, data-only plug-in interface description, `version: v1-draft`, per-value `contentType`) and xtp-bindgen were added later.
- **Zed** is the instructive hybrid: extension *logic* is Rust compiled to `wasm32-wasip2`, but language servers, debuggers etc. are native processes that the extension describes (`command, args, env`) and Zed spawns, gated by user-granted capabilities such as `process:exec` with argument patterns.

**Fit for the target languages.** Python: partial — a sandboxed, pure-computation profile is possible, but typical glue code (`subprocess`, native wheels, threads) does not run. PowerShell: no — it is a .NET runtime that loads modules/assemblies dynamically and needs processes, registry/CIM/COM; NativeAOT forbids exactly that. Bash: no — its essence is fork/exec of real processes that inherit env, cwd and fds; without process creation it shrinks to builtins. AppleScript/JXA: no — they *are* OSA components exchanging Apple Events with other apps, under TCC automation consent attributed to the sending process; a Wasm guest could only call host imports that Rust would have to implement (at which point the "plugin" is the host). Node: no need (it already runs natively).

**Lessons.** (1) Mount system-scripting languages as native processes; Wasm could later be a separate, sandboxed mount kind for compute-only guests, contract-first. (2) WIT is a good *type vocabulary* for rutis's internal interface model (records, variants, option/result, resources, own/borrow, async, stream/future) and could be emitted from it, but adopting WIT as the authored IDL contradicts "no hand-written IDL" and leaves PowerShell/Bash/AppleScript without generators. (3) Copy `own`/`borrow`: a borrow-like reference valid only during one call needs no release frames — a cheap middle profile. (4) Copy "reject at link time by default; trap-on-call only as an explicit dev mode". (5) Bytes-in/bytes-out interfaces end up needing a schema anyway (Extism → XTP).

### 2.16 Cap'n Proto RPC and Cap'n Web (object capabilities, implementation levels)

([rpc.html](https://capnproto.org/rpc.html), [rpc.capnp](https://github.com/capnproto/capnproto/blob/v2/c++/src/capnp/rpc.capnp), [other languages](https://capnproto.org/otherlang.html), [Cap'n Web](https://github.com/cloudflare/capnweb))

- **Levels as profiles.** rpc.capnp defines cumulative implementation levels: **0** — no object references, only the bootstrap interface can be called (comparable to JSON-RPC); the spec calls it a temporary stepping stone and asks protocol designers not to design around it; **1** — object references and promise pipelining between two parties (third parties only via proxying); **2** — persistent capabilities (SturdyRefs); **3** — three-party handoff with direct connections; **4** — joins (capability equality). Message types are assigned to levels (0: `unimplemented, abort, bootstrap, call, return, finish`; 1: `resolve, release, disembargo`; 3: `provide, accept, thirdPartyAnswer`; 4: `join`). The spec itself notes that level 1 suffices for many applications. Non-C++ implementations mostly stop at level 1 (Rust capnp-rpc, go-capnp) or are serialization-only.
- **Rejection by echo.** A peer that does not understand a message sends it back wrapped in `unimplemented`; for question-introducing messages the sender treats that as a failed call; otherwise behaviour is explicitly a gray area. At method level, `Exception.Type.unimplemented` (alongside `failed`, `overloaded`, `disconnected`).
- **Reference counting.** `Release {id, referenceCount}`: each time an export id is sent its count increments, and release decrements by the given amount; `Return.releaseParamCaps` / `Finish.releaseResultCaps` release all capabilities of a call in bulk. `Disembargo` exists only to restore ordering when a promise resolves to a capability on a different path — the price of pipelining plus path shortening.
- **No handshake/version message**; the level is advertised out of band and discovered via `unimplemented` at runtime.
- **Cap'n Web** (same author, JSON, no schemas): messages `push, pull, resolve, reject, release, stream, pipe, abort`; `["release", importId, refcount]` where refcount counts introductions; explicit disposal (a GC cannot trace a remote graph); stubs passed as params stay the caller's, stubs returned transfer ownership; when a session ends, all stubs are implicitly disposed.

**Lessons.** (1) Cumulative levels are a proven way to define profiles — but put the level in the hello and reject at codegen/mount time rather than discovering gaps at runtime via echo. (2) For Bash/AppleScript, "level 0" is permanent, not a stepping stone: interfaces meant for them must be designed data-only from the start, and the generator must enforce it. (3) Counted release and session-end disposal are exactly what rutis v1 already does — Cap'n Web is close to rutis's Node protocol, which is reassuring. (4) Embargoes come from pipelining + three-party resolution; a star topology with the host as hub and no pipelining (rutis today) avoids them. The abandoned rutis design borrowed the *capability/security* framing of Cap'n Proto without the property that justifies it (a security boundary between mutually distrusting vats).

### 2.17 Py4J / Spark Connect, and PowerShell remoting serialization (live objects vs snapshots)

- **Py4J** ([advanced topics](https://www.py4j.org/advanced_topics.html), [gateway API](https://www.py4j.org/py4j_java_gateway.html)): Python holds dynamic `JavaObject` proxies (no IDL) over sockets; Java can call back into Python objects that implement Java interfaces (a separate callback server). Java objects referenced from Python are released when Python garbage-collects the proxy (`enable_memory_management=True`); for Python objects referenced from Java there is no guarantee that a release message is ever sent, and proxy cycles delay collection. The default threading model spawns threads to avoid deadlock on indirect recursion; a pinned-thread model runs callbacks on the initiating thread — **PySpark switched its default to pinned threads (Spark 3.2) for correctness**.
- **Spark Connect** (since 3.4) replaced Py4J for clients with a declarative, language-agnostic protocol (unresolved logical plans as protobuf over gRPC, Arrow results), citing stability (client runs in its own process with its own dependencies), upgradability and debuggability — and explicitly giving up access to live JVM internals.
- **PowerShell remoting** ([about_Remote_Output](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_remote_output), [how objects are sent](https://devblogs.microsoft.com/powershell/how-objects-are-sent-to-and-from-remote-sessions/)): live .NET objects cannot cross the wire, so they are serialized to CLIXML and arrive as property bags **whose type name is prefixed `Deserialized.`** and which keep no methods (except `ToString`). A curated set of types is rehydrated as live objects (Guid, Uri, Version, DateTime, PSCredential, IPAddress, …); enums become integers, collections become ArrayList/Hashtable. Depth is configurable per type (`Update-TypeData -SerializationDepth`, default 1); `ConvertTo-Json` defaults to depth 2 and only since 7.1 warns on truncation.

**Lessons.** GC-driven release is unreliable in both directions: rutis needs explicit release, scope-tied cleanup (fibers/LIFO), mount-level teardown, with finalizers only as a backstop (rutis already does). Re-entrant calls need one documented threading rule per runner (e.g. "callbacks run on the runner's main/event-loop thread"). Snapshots are acceptable *only if labelled in the type*: PowerShell's `Deserialized.` prefix is the right instinct; for rutis, data-only profiles should generate snapshot types without methods, never proxies, and truncation must be an error. Ecosystems that started with live reflective proxies (Py4J) moved to narrow declarative protocols for stability.

### 2.18 Other relevant precedents (brief)

- **Temporal Core SDK** ([sdk-core](https://github.com/temporalio/sdk-core)): one Rust core with a C bridge underlies the TypeScript, Python, .NET and Ruby SDKs, so the hard semantics are implemented once and each language layer stays idiomatic. For rutis this suggests an *option* for capable languages (a Python runner peer as a PyO3 extension reusing `rutis-interop`'s Rust `rpc`), at the cost of native wheels per platform; it cannot help Bash or AppleScript.
- **Pulumi language-host binaries are Go programs** that launch the real interpreter (`sdk/python/cmd/pulumi-language-python/main.go`, `sdk/nodejs/cmd/pulumi-language-nodejs/main.go`), and Pulumi has a **language conformance suite** with levels: L1 (basic features), L2 (provider code paths), L3 (features needing advanced language support such as first-class functions), run against every language host via `pulumi-test-language` ([conformance tests](https://pulumi-developer-docs.readthedocs.io/latest/pkg/testing/pulumi-test-language/README.html)). See also §2.3.
- **OpenRPC** ([spec](https://spec.open-rpc.org/)): optional `rpc.discover` returns the service's OpenRPC document (methods with JSON-Schema params/results); documents may be produced statically or generated by the application, and are used for client/server codegen. The useful idea: one `describe` document produced statically at build time and dynamically at the handshake, compared by hash.
- **Neovim `$NVIM`** ([vvars](https://neovim.io/doc/user/vvars.html)): Nvim sets `$NVIM` (its server address) for `:terminal` and `jobstart()` children so any child — including a shell script — can connect back and make RPC requests. Precedent for giving script plugins *reverse calls* via an environment variable and a small CLI helper rather than a protocol implementation in the script language.
- **systemd socket activation** ([sd_listen_fds](https://www.freedesktop.org/software/systemd/man/latest/sd_listen_fds.html)): passed descriptors start at fd 3 (`SD_LISTEN_FDS_START`) and are announced via `$LISTEN_FDS` / `$LISTEN_PID` / `$LISTEN_FDNAMES` — a well-known convention for handing a pre-opened channel to a child in any language (Erlang's `nouse_stdio` uses fds 3/4 the same way).

Patterns that recur across almost all of them:

1. **Process per independently developed plugin** is the norm; sharing a process is reserved for code designed to cooperate. The one prominent "host per language" design (Neovim) is being removed.
2. **Capabilities, not versions, carry evolution.** Version numbers change only for framing/semantic breaks (LSP and DAP have none at all); features are flags where absence means "not supported".
3. **Runtime self-description is the norm for dynamic hosts**; hosts that want static types generate them from a single neutral model (LSP metaModel, Pulumi Package Schema, WIT), and only Pulumi (and rutis) derive that model from the plugin's own source.
4. **Live references across processes are rare** and, where present, either call-scoped (Nushell engine calls, DAP, WIT `borrow`), plugin-owned with explicit drop notices (Nushell custom values), or counted with session-end disposal (Cap'n Proto, Cap'n Web, rutis v1).
5. **The weakest languages are served by a second, trivial tier** (Azure custom handlers, Lambda's pull API, execd, Raycast/xbar scripts, bash_kernel driven from Python), not by implementing the rich protocol in the weak language.

## 4. Lessons for rutis

The recommendations below assume rutis keeps its existing decisions: no kernel changes, no hand-written IDL, no default timeouts on calls, explicit failure rather than silent degradation, and no automatic retries of side effects.

### (a) One wire protocol, layered — and a second tier for script languages

1. **Keep one protocol family**, evolving v1 into v2 rather than writing per-language protocols. Every system surveyed that serves several languages (Azure, Neovim, Pulumi, LSP, MCP, Jupyter, Nushell) uses one protocol; the per-language work is the runner and its SDK.
2. **Common to every runner (the "core"):**
   - **Framing:** keep UTF-8 JSON, one value per line. It is the format every target language can produce and parse (Bash `read -r` + `jq -c`, PowerShell `ConvertFrom-Json`, JXA `JSON.parse`, AppleScript via `NSJSONSerialization`); Bazel's undelimited JSON and LSP's `Content-Length` headers are both harder for shells.
   - **Transport:** keep the protocol off stdio (rutis already does; LSP/MCP/Bazel/go-plugin all suffer from stray prints). Add an *inherited descriptor* binding next to the socket path: e.g. a `socketpair` passed as fd 3 and announced in an environment variable (the systemd `LISTEN_FDS` / Erlang `nouse_stdio` convention). This works in every target language without a connect step — verified locally with `/bin/bash` 3.2 (`read -r -u 4`, `>&3`) and with JXA and AppleScriptObjC under `osascript` (`NSFileHandle initWithFileDescriptor:`), whereas Bash cannot open a Unix socket at all.
   - **Handshake:** `hello {protocol: {major}, runner: {name, version, language, interpreter: {path, version}}, profile, features: [...], pid, interface_digest}` from the runner, and the host's own `hello {features}` in reply. Rules from LSP/DAP/Nushell: a feature is usable only if both sides list it; unknown features are ignored; absence means unsupported. A major mismatch is rejected with a typed error listing the supported majors (MCP's `UnsupportedProtocolVersion {supported, requested}`) and a distinctive runner exit code (VS Code uses 55).
   - **Calls:** `invoke` / `return` / `throw` with ids, and **exactly one terminal frame per call, even after `cancel`** (LSP/DAP/Bazel rule; the caller drops it if it already gave up, as rutis's `orphans` counter does today). This keeps callee-side pins and Rust futures deterministic.
   - **Error envelope:** one shape for all languages — `{kind: user | runner | protocol | unsupported | cancelled, name, message, stack?, cause?, data?, errors?}` — with the existing JS object graph kept as an optional `graph`. Each runner maps native errors into it (Python exception class/args/`__cause__`/`ExceptionGroup`; PowerShell `ErrorRecord` with `FullyQualifiedErrorId`; Bash exit status + stderr tail; AppleScript error number + message). Lambda's `Runtime.*` vs `Function.*` and MCP's protocol error vs `isError` result show why the runner-vs-plugin distinction matters.
   - **Logs:** an optional `log {level, message, call?}` frame (Azure `RpcLog`, Babashka call-tagged `out`/`err`) in addition to captured stderr.
   - **Lifecycle control:** `dispose` (graceful unload) and "exit on EOF of the channel" (mandatory, see (e)).
3. **Optional feature sets, negotiated** (see (d)): references (`function`, `future`, `object`) with counted `release`; plugin→host calls; nested synchronous re-entrancy; events in each direction; live property `get`; service-slot change notifications; cooperative cancellation; streams (future).
4. **Per language:** the runner (a thin peer — Neovim's lesson is that thick per-language hosts are what became unmaintainable), the authoring SDK, the type extractor (see (b)), value-conversion rules (`None`/missing, PowerShell array unrolling and `$null`, AppleScript records), the execution model (threads/event loop), and environment setup — the last one written in Rust, like Pulumi's Go language hosts.
5. **Second tier for Bash and AppleScript/JXA: do not implement the rich protocol in the script language.** Terminate the protocol in Rust and run scripts through a small, versioned *script calling convention*: function name and arguments via argv and/or JSON on stdin (never interpolated into source), result as one JSON value on fd 3, logs on stderr, failure as non-zero exit plus a structured error on fd 3 if available. Precedents: Azure custom handlers, Lambda's runtime API, Telegraf execd, Raycast/xbar, Jupyter's bash_kernel driven from Python, Babashka's host-side adaptation code. The generated Rust bindings stay identical in shape, so consumers do not care which tier a mount uses. Whether that Rust runner lives inside the host process (an alternative `Process` implementation behind the same `Dispatch`/`Projection` interfaces) or in a tiny helper binary is an implementation choice; in-process is simpler and avoids a second protocol hop.
6. **Optional: one protocol core implemented once in Rust for capable languages.** Temporal's Rust core under its TS/Python/.NET/Ruby SDKs shows the consistency benefit; a PyO3 build of `rutis-interop`'s `rpc` could serve as the Python peer. The cost is native wheels per platform; a pure-Python peer is likely simpler at first. Not applicable to Bash/AppleScript.

### (b) Interface descriptions: per-language extraction → one neutral model → Rust

1. **Introduce a language-neutral interface model ("IR") as the only input to the Rust code generator.** Split today's `generate.mjs` into a TypeScript front-end that emits the IR and a back-end (moved into `rutis_interop::build`, in Rust) that turns IR into Rust. This is LSP's metaModel and Pulumi's Package Schema pattern, and it keeps the "no hand-written IDL" rule: the IR is always generated. A WIT-like type vocabulary fits well (primitives, string, bytes, list, map, record, variant/enum, option — with rutis's null/undefined distinction —, result, `json` for any, plus rutis's `service`/`object`, `function` signatures, `future`, sync/async method shape, properties, events). Annotate each IR node with the features it requires, so profile checks become mechanical.
2. **Front-ends per language** (to be refined by the per-language reports):
   - TypeScript: the existing TS checker.
   - Python: build-time introspection inside the mount's own environment (`python -m <runner> describe <entry>`), importing the module and reading decorators plus `typing.get_type_hints` / `inspect.signature` — the approach of Pulumi's analyzer, FastMCP/Pydantic, Azure's worker indexing and pynvim. Importing executes code, so the SDK must define a describe mode and the docs must forbid import-time side effects (pynvim's documentation warns about exactly this). Unannotated parameters become `json` with a build warning, like TS `any`.
   - PowerShell: static parsing with PowerShell's own parser (typed `param()` blocks, `[Parameter(Mandatory)]`, `[ValidateSet()]` → enum, `[OutputType()]`), which needs no execution; `Get-Command` metadata after `Import-Module` is the runtime alternative.
   - Bash, AppleScript, JXA: no types exist, so use a versioned comment header or a sidecar manifest declaring functions and parameter/return types (Raycast's `schemaVersion` + JSON-typed arguments, xbar's typed variables), parsed at build time without running the script, and restricted to the data profile.
3. **Verify at runtime instead of trusting a cache.** Embed the IR digest in the generated code; the runner reports the digest of what it actually loaded (in `hello` or the `mount` reply), and a mismatch fails the mount with "plugin changed since build — rebuild". This replaces the stale-manifest failure modes of Neovim (`:UpdateRemotePlugins`), Nushell (`plugin add`) and Babashka (`:cache false`), and mirrors OpenRPC's static-plus-dynamic `rpc.discover` and Terraform's runtime schemas.
4. **Consequences for static Rust bindings:** dynamic languages give weaker types; the generator must make unknowns explicit (`serde_json::Value`), reject unrepresentable types loudly (Pulumi rejects unions/functions at extraction), and never coerce silently (Python `int` → `i64` vs `f64`; PowerShell `[int]` vs `[long]`; Bash values are strings unless the manifest says otherwise). Data returned by data-only runners should be generated as *snapshot* structs (no methods), named and documented as such — PowerShell's `Deserialized.` prefix is the precedent for labelling.

### (c) Process topology: keep "one process per mount"

1. **Do not introduce one host process per language.** Neovim is removing exactly that; VS Code had to add affinity groups; Sublime carries one host per Python version for years; Azure warns that PowerShell runspaces in one process race on module state. Per-plugin (or per-mount) processes are the norm everywhere else.
2. **Keep mount groups for co-designed plugins only** — VS Code reached the same rule independently (dependency-linked extensions always share a process because they share live objects).
3. **Define a mount key** (Bazel's `WorkerKey`): runner kind and version, interpreter path and version, environment digest (venv / module path), relevant environment variables, plugin-set digest, profile. All members of a group must have the same key — a build-time check — and any change means a new process.
4. **Execution unit per tier:** Node, Python, PowerShell — one persistent interpreter per mount (`pwsh` start-up could not be measured on this machine; the PowerShell report should measure it, since it decides how costly a restart or a per-call fallback would be). Bash and AppleScript/JXA — one short-lived interpreter process per call (measured cold starts on this machine: Bash ≈ 2 ms, JXA ≈ 29 ms, AppleScript ≈ 37 ms), with state kept in files or in the host. A persistent shell driven by sentinel prompts (bash_kernel) is possible later but fragile.
5. **Blast radius stays as today:** a mount process crash withdraws all of its services and its dependents stop by native gating; a failed script call is just an error for that call. Optional lazy spawning (VS Code activation events, Neovim stubs) can come later; rutis's dependency gating already starts mounts only when they are needed.

### (d) Capability negotiation and profiles: declare, check three times, reject

1. **Define a few named, cumulative profiles**, each a fixed feature set (Cap'n Proto levels and Pulumi's L1–L3 conformance tiers are the precedents):

   | Profile | Contents | Natural targets |
   | --- | --- | --- |
   | **P0 "command"** | host→plugin unary calls; JSON data in/out; structured errors; logs; cancel = terminate the call's process (outcome unknown); no plugin→host calls, no events, no references | Bash, AppleScript, JXA, any executable |
   | **P1 "service"** | P0 + persistent process and state, service availability changes, plugin→host calls on host services (data only), notification events in both directions, cooperative cancellation; optionally *call-scoped* callbacks (valid only during the call, no release — DAP / WIT `borrow`) | PowerShell, a minimal Python |
   | **P2 "objects"** | P1 + references (function, future, object) with counted release, live properties, nested synchronous re-entrancy | Node (today), Python |

   Cap'n Proto calls level 0 a temporary stepping stone; for Bash and AppleScript it is permanent, so interfaces meant for P0 must be designed data-only from the start rather than degraded.
2. **Check at three points:** (i) **build time** — the generator compares each IR member's required features with the runner's declared profile (known statically from the runner package, like `rutisProtocol` today): mount-level requirements that cannot be met (e.g. host services on a P0 runner) are build errors; individual members are skipped with a `cargo:warning`, as now; limitations show up in the generated API (e.g. a call that cannot be cancelled says so). (ii) **mount time** — the runner's `hello` features must cover everything compiled into the bindings, otherwise the mount fails before any plugin code runs, with an error naming the missing features (MCP's `MissingRequiredClientCapability`). (iii) **runtime backstop** — any frame or operation a peer does not support gets `throw {kind: unsupported}` (Cap'n Proto `unimplemented`, LSP `MethodNotFound`), never silence.
3. **Use a closed, typed feature set** (a Rust enum, strings only on the wire), not free-form strings with mixed semantics — Azure's capability map and Pulumi's `SupportsFeature` list both became debt, and Pulumi migrated to a typed enum.
4. **No silent conversions inside runners:** a Python runner must not `json.dumps(default=str)` unknown objects, a PowerShell runner must not let `ConvertTo-Json` truncate at its default depth, and a callback must never become a function name; all of these are `unsupported` errors.

### (e) Lifecycle

1. **Start-up:** spawn in a new process group/session; hand over the channel (fd or socket path); expect `hello` within a start-up timeout that is separate from call semantics (go-plugin 1 min, Azure 60 s to connect, Lambda 10 s for init) — this does not contradict "no call timeouts", because nothing of the plugin has run yet. Report distinct errors for: interpreter not found, exited before `hello` (with exit status and stderr tail), malformed `hello` (stray output), version mismatch, missing features, interface-digest mismatch, plugin `apply` failure.
2. **Readiness** stays an application round-trip — the existing `mount` reply with the service table (Jupyter likewise requires a `kernel_info` reply, not just a live process; Lambda treats the first `next` as ready).
3. **Liveness without timeouts:** an optional `ping` (or VS Code-style per-request acknowledgement) answered by the runner's reader thread distinguishes "dead", "blocked main thread" and "slow async call" for diagnostics, without imposing call timeouts.
4. **Cancellation:** keep future drop → `cancel`. Each runner declares its mode in `hello`: `cooperative` (Node `AbortSignal`; Python `Task.cancel()` for `async def`, a checkpoint flag for threads — FastMCP documents that sync handlers otherwise run to completion; PowerShell pipeline stop), `signal` (P0: SIGTERM then SIGKILL to the call's process group; Jupyter's `interrupt_mode` is the precedent), or `none`. Outcome after cancel is always "unknown"; the callee still sends one terminal frame.
5. **Shutdown ladder:** `dispose` (framework unload in LIFO order) → close the channel → the runner must exit on EOF (Erlang/Elixir ports, MCP, Telegraf) → grace period → SIGTERM to the process *group* → grace → SIGKILL. rutis currently disposes and then, when the mount is released, SIGKILLs the runner process alone (the Node runner also disposes when its channel closes); adding the TERM step and group kill matters for Bash and PowerShell plugins, whose work is mostly child processes (the requirements currently exclude reaping grandchildren — this is worth revisiting for script tiers). Runners should also watch their parent (EOF on the channel, or a parent-PID check as in VS Code, ipykernel and Pulumi) because macOS has no parent-death signal.
6. **Crash detection:** keep EOF + exit status, and attach the last N stderr lines to the `Transport` error (Azure keeps 3, Bazel up to 8 KB, Terraform up to 100 lines after a panic).
7. **Restart policy:** keep "no automatic restart" as the default (Pulumi, Bazel and Babashka do the same, and it matches rutis's no-retry-of-side-effects rule). If restarts are offered, make them an opt-in, bounded mount policy modelled on OTP supervisors (`transient`, intensity/period, then escalate) and implemented as re-mount through rutis's dependency-driven reload; never replay in-flight calls. Bounds used elsewhere: VS Code 3 crashes per 5 min; vscode-languageclient 5 per 3 min; Jupyter 5 consecutive; Azure 3 × process count before recycling the host. Unbounded restarts (Telegraf, Nushell's lazy restart) invite crash loops.
8. **stdout/stderr:** never carry the protocol; capture both through pipes and forward them line by line into rutis logging with mount/plugin attribution (go-plugin's hclog, Bazel's per-worker log, Jupyter's `stream` messages), with a ring buffer for crash reports. Do not classify stderr by substring (Azure's acknowledged wart); use `log` frames or explicit level prefixes. In the P0 tier the script's stdout is *not* the result channel (fd 3 is), so ordinary `echo` and command output cannot corrupt results. Keep stdin at `/dev/null` unless a plugin explicitly needs the terminal (Nushell and Babashka added socket modes for that case).

### (f) Environments, interpreters and versions

1. **Resolve interpreters in Rust at build time and pin them:** explicit configuration in `[package.metadata.rutis-interop]` first (Neovim `g:python3_host_prog`, Azure `defaultExecutablePath`, `PULUMI_PYTHON_CMD`), then a project-local environment (`.venv`, a `Modules/` folder), then `PATH`. Record the absolute path and version in the generated code, the way `ipykernel install` writes the interpreter into `kernel.json`; the runner reports its interpreter version in `hello` and a mismatch is an error. Unsupported versions are rejected explicitly (as Azure does), never mapped to a default (Sublime's silent fallback to 3.3).
2. **One lockfile per mount group as the single version source**, as with npm today; the build never installs, and fails with the command to run. Python: a venv per mount group described by `uv.lock` / `pylock.toml` / `requirements.txt` (Pulumi supports pip/poetry/uv and creates the venv itself; rutis could at least print the exact `uv sync` command). PowerShell: a mount-local `Modules/` directory filled with `Save-PSResource`, and `PSModulePath` set per runner process to that directory plus the built-in paths — no runtime auto-install (Azure's managed dependencies are not available on its newer plan). Bash: declared required commands checked with `command -v`, and an explicit interpreter choice — macOS ships Bash 3.2.57 without `coproc`, associative arrays or `mapfile`, so either target that subset or require a newer Bash by path. AppleScript/JXA: declared target applications and automation permissions, checked at mount (details in the AppleScript report).
3. **Keep the runner out of the plugin's dependency space.** Azure's Python worker clashed with apps over grpcio/protobuf and finally split into a thin protocol proxy plus a library imported from the app's own dependencies; Node and .NET were split the same way. For rutis: a protocol runner that is stdlib-only and shipped with the crate (injected via `PYTHONPATH` or an explicit path, so it can never drift from the crate's protocol version), separate from an authoring library (decorators, `Context`) that plugins depend on and that declares the protocol range it supports.
4. **Version the protocol independently of rutis releases**, with a major number plus features (Nushell's minor-locked rule forces every plugin to be rebuilt about every six weeks, and its hand-written Python/Go SDKs visibly lag). The runner package keeps declaring `rutisProtocol`; make it a range once more than one runtime ships.
5. **Environment variables:** keep inheriting the application's environment (scripts expect `PATH`, `HOME`), allow per-mount overrides, and start interpreters without user profile scripts (`bash --noprofile --norc`, `pwsh -NoProfile -NonInteractive`) so start-up is fast and deterministic. (MCP's Python SDK goes further and passes a minimal allow-list of variables.)

### (g) Developer experience

1. **Authors write idiomatic code against a small SDK; the protocol is invisible.** Precedents: pynvim and osquery-python decorators, FastMCP (`@mcp.tool()`, type hints → schema, an injected `Context` parameter excluded from the schema), Azure's Python v2 decorators and Node v4 `app.http`, Pulumi components (annotations → schema), Nushell's `Plugin`/`PluginCommand` traits.
2. **Python** (the Cordis-like framework): plugin modules with `apply(ctx, config)`, `inject`, `ctx.provide`, `ctx.effect`, `ctx.on`; services as classes; required type hints on exported members (dataclasses / `TypedDict` / Pydantic for records, `Annotated[..., Field(description=…)]` for docs); `async def` ↔ Rust `async fn`, `def` ↔ sync fn; no work at import time.
3. **PowerShell:** advanced functions with typed `param()` blocks, `[CmdletBinding()]`, `[OutputType()]`, comment-based help; the module manifest (`.psd1`) as the plugin manifest (`RootModule`, `RequiredModules`, `PowerShellVersion`).
4. **Bash, AppleScript, JXA:** plain functions/handlers plus a versioned comment header or sidecar manifest; a helper library loaded by the runner (`rutis_result`, `rutis_error`, `rutis_log`, and — where the profile allows — `rutis_call` for host services through a CLI helper that connects back via an inherited descriptor, as Neovim's `$NVIM` lets child processes connect back). Arguments always arrive as data, never as code.
5. **A local loop without the host:** `describe` (print the extracted interface) and `call` (invoke one method with JSON) commands, like MCP's inspector, Nushell's test-support crate or Babashka's `describe`; Neovim's node client has a development mode that reloads the plugin on every call.
6. **A shared conformance corpus**, tiered by profile and run against every runner (Pulumi's `pulumi-test-language` with L1–L3), extends rutis's existing practice of acceptance through real plugins compared with native behaviour.

## 5. Anti-patterns to avoid

1. **One shared host process per language for unrelated plugins** — shared fate, shared dependency environment, re-implemented host logic in every client. Neovim is dismantling it; VS Code added affinity; Azure warns about runspace races.
2. **A separately refreshed registration manifest** (`:UpdateRemotePlugins`, Nushell's `plugin add`, Babashka's cache) that silently goes stale. Tie extraction to the build and verify a digest at mount.
3. **Version lockstep with host releases** (Nushell's minor-locked protocol; rutis v1's exact match would multiply across five runtimes shipped through npm, pip, PSGallery and the crate).
4. **Silent degradation:** Azure never delivering cancellations to Node/Python/PowerShell workers; go-plugin turning a missing stdio service into a warning and a missing controller into SIGKILL; Raycast's `inline` → `compact` and Sublime's fallback to Python 3.3; JSON depth truncation. Reject, or make the limitation visible in the generated API.
5. **Untyped, inconsistently interpreted capability strings** (Azure's presence-vs-`"True"` checks; Pulumi's string list that it had to freeze).
6. **The protocol on stdout of a process running user code** (go-plugin's handshake line, MCP and LSP stdio, Bazel), and **classifying stderr by substring** (Azure).
7. **GC-driven release of remote references as the primary mechanism** (Py4J's unreliable Java→Python release; Nushell's per-emission drop notices that double-count). rutis's counted `release` plus mount teardown is the right design.
8. **Interpolating data into script source** (`sh -c "$x"`, `osascript -e "… " & x`), and parsing human-readable output as results. Use argv/stdin/fd 3 and an explicit result channel.
9. **Unbounded automatic restarts and replay of in-flight calls** (Telegraf restarts forever; Nushell restarts lazily without backoff).
10. **Treating runspaces, sub-interpreters or a separate process as isolation or a sandbox** (Azure PowerShell warning; rutis's own requirement that a process boundary is not a sandbox).
11. **Running plugin code with side effects during extraction** — pynvim and Python introspection make this a real risk; the SDK needs a describe mode and a "no work at import" rule.
12. **Over-generalising before the second language exists — the abandoned rutis design.** Judged against the precedents, it fell into several of these at once:
    - a **broker that mediated and authorised every cross-runner call with its own state** (grants, delivery ids, per-object sequencing). A hub topology is fine — calls between mounts naturally pass through host services, as Cap'n Proto level 1 proxies third parties through the hub — but per-call authority bookkeeping in the hub is something no surveyed local plugin system carries;
    - **object-capability security machinery without a security boundary** (per-delivery grants, epochs, watermarks and revocation, while all processes run as the same user with no sandbox — Cap'n Proto's discipline pays off only between mutually distrusting vats);
    - a **hand-maintained interface-descriptor bundle with SHA-256 identity** consumed by every language — the IDL-maintenance cost rutis later rejected, and the opposite of how Pulumi and LSP derive their neutral model from code;
    - **symmetric peer runtimes** (separate Rust runner processes for rutis plugins alongside Node runners, each negotiating lifecycle authority with the host) instead of a host-centric design in which the host does the typing and lifecycle work once — the direction Neovim is now taking and the one rutis has since chosen;
    - **acceptance gates and a nine-language roadmap before one language worked** (M0 go/no-go, T01–T24 + X01–X04 + E01–E07). Successful systems grew by addition from a small core (Lambda, Babashka, Nushell's feature list, Cap'n Proto's level 1 being enough for most applications) and by real-plugin milestones — which is what the current requirements already prescribe.

    What the abandoned roadmap got right — explicit rejection of unsupported capabilities, argv instead of interpolation, a protocol channel separate from logs, realistic macOS automation constraints — is confirmed by the precedents and should be kept.

## 6. Open questions for the per-language reports

- **Python:** pure-Python peer vs a PyO3 build of the Rust `rpc`; how a sync method blocks while serving nested calls (a dedicated reader thread feeding the waiting thread, as the Node runner does with `Atomics.wait`); which threading rule callbacks follow (PySpark had to switch to pinned threads for correctness); extraction by import vs static AST.
- **PowerShell:** one runspace per mount process vs a pool; how scriptblock callbacks are invoked on the right runspace (Azure's worker hosts the engine from .NET rather than as a script); value conversion (array unrolling, `$null`, `PSCustomObject` vs hashtables, depth); `pwsh` start-up cost.
- **Bash:** Bash 3.2 compatibility vs requiring a newer Bash; per-call processes vs a persistent shell; reverse calls through a helper binary; process-group cleanup of pipelines and background jobs.
- **AppleScript/JXA:** per-call `osascript` vs a persistent OSA host; which process macOS attributes Apple Events to (and therefore which consent prompt the user sees); timeouts of Apple Events vs rutis's no-timeout rule; result encoding (records, lists, `missing value`).
- **Cross-cutting:** whether the P0 tier runs inside the host process or a helper binary; the exact IR type vocabulary; whether `hello` carries the full interface or only its digest.
