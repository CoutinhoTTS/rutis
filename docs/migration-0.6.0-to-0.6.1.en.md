# rutis 0.6.0 to 0.6.1: Plugin Control Plane

Starting in 0.6.1, rutis applications can manage plugins from data: configuration specifies which plugins to load and how to configure them, while the running application can add/remove plugins, change configuration, and hot-update them. These features are in the new `rutis-loader` 0.1.0 crate. The `rutis` core adds only a few interfaces and has no breaking changes. See the [rutis-loader design](design-rutis-loader-2026-10-02.en.md).

Packages released together:

| Package | Version | Code changes needed? |
| --- | --- | --- |
| `rutis` | 0.6.0 → 0.6.1 | No |
| `rutis-interop` crate and `@arcships/rutis-interop` npm package | 0.1.0 → 0.2.0, protocol 1 → 2 | Upgrade both together; add one field to hand-written `Mount { .. }` values |
| `rutis-loader` | New release 0.1.0 | Only needed to use the control plane |

For dylib hosts and plugins, also read “Integrate with rutis-loader” below: binary compatibility is determined by SDK identity, independently of Rust API compatibility.

## Using only the rutis core

Change the dependency to `rutis = "0.6.1"`; no code changes are needed. New interfaces are optional:

- `impl Plugin for Box<dyn Plugin>`: when the plugin to mount is chosen at runtime (for example, constructed from configuration), the boxed plugin can be passed directly to `ctx.plugin`.
- `Ctx::view(plugin_id)`: find a plugin's `FiberView` from a `PluginId` obtained from diagnostics or an event.
- `Ctx::dispose_self()`: unload the current plugin, similar to Cordis `ctx.fiber.dispose()`. Returns immediately; unloading happens after the current `apply` or callback ends. Do not wait for it inside the plugin. The root context cannot unload itself; use `Ctx::shutdown`. If an old generation calls this after restart, it gets `InactiveEffect` and does not unload the new generation.
- `FiberView::instance()`: the plugin instance's `InstanceId`.
- `FiberView::set_config(config)`: store a new configuration without restarting. Use this when the plugin applies changes in place (Cordis volatile field); otherwise use `update`.
- `ServiceChanged` event: emitted on the provider's bus when a service binding is registered or finally removed (`change` is `Provided` / `Removed`). The only behavior change is an additional event on the bus; it has no effect unless subscribed to.

## Using rutis-interop

### Upgrade both packages together

```toml
# Cargo.toml
rutis-interop = "0.2"
```

```json
// npm project's package.json
"@arcships/rutis-interop": "0.2.0"
```

Then run `npm install` (or `npm ci`) once.

The protocol is now version 2. If the crate and npm runtime versions differ, the build reports `... speaks protocol 1, this rutis-interop speaks 2: install a matching @arcships/rutis-interop`, and process handshakes are rejected. If only one side was upgraded, follow the message and upgrade the other.

### Hand-written `Mount`

`Mount` adds an `anchor` field (starts an empty Cordis Context when no plugins are included; see below). Add it where struct literals specify all fields:

| 0.1 | 0.2 |
|---|---|
| `Mount { plugins, services, observer, hosts, events, emits }` | `Mount { plugins, services, observer, hosts, events, emits, anchor: None }` |
| `Mount { plugins, ..Mount::default() }` | No change |

Bindings generated by `build.rs` (`rutis_interop::build::from_manifest`) do not need changes. They are generated by the npm runtime generator and regenerate automatically after both packages are upgraded to 0.2.

### Additions

- Generated configuration structs also implement `Deserialize` and can be created from JSON (for example, a loader row's configuration).
- **Load rows individually:** `Mount { anchor: Some(package_json), .. }` starts an empty Cordis Context with no plugins. Then use `Process::load_row` / `update_row` / `unload_row` to load, update, and unload plugins individually. `row_schema` returns JSON Schema converted from the plugin's schemastery `Config`.
- **`CordisRuntimePlugin`:** mount the Node process and Cordis Context into rutis as an ordinary plugin, with lifecycle following the fiber tree. See the [rutis-interop README](../crates/rutis-interop/README.en.md#loading-rows-individually).

## Integrate with rutis-loader (optional)

Applications with plugin composition fixed in code and no runtime additions/removals can continue to use `ctx.plugin` directly; rutis-loader is unnecessary.

When needed, replace a sequence of `root.plugin(...)` calls with “register plugin sources + describe what to load in configuration”:

```toml
rutis-loader = "0.1"
```

```rust
use rutis_loader::{Builtins, Editable, Layer, LoaderOptions, LoaderPlugin, Patch, Version};
use serde_json::json;

// Previously: root.plugin_with(MyFactory, MyConfig { level: 1 }).await?;
let mut builtins = Builtins::new();
builtins.register::<MyConfig, _>("my-plugin", MyFactory);

let plugin = LoaderPlugin::new(builtins, LoaderOptions::default());
let loader = plugin.handle();
root.plugin(plugin).await?;

// Application configuration is one layer; runtime modifications go into another (editable) layer.
let app: Vec<Patch> = serde_json::from_value(json!([
    { "insert": [{ "id": "main", "name": "my-plugin", "config": { "level": 1 } }] }
]))?;
loader
    .reconcile(
        vec![Layer::new("app", app), Layer::new("user", Vec::new())],
        Some(Editable::new("user", Version::default())),
    )
    .await?;

// Runtime changes—configuration, disable, delete, etc.—are written to the "user" layer.
loader.update("main", json!({ "level": 2 })).await?;
loader.set_disabled("main", true).await?;
```

The second argument to `reconcile` specifies the editable layer. `None` means read-only: the loader still loads plugins from all layers, but modifications such as `update` and `set_disabled` return `LoaderError::NoEditableLayer`.

Changes are in memory by default (`LoaderOptions::default()` uses `NoPersist`). To retain them across restarts, implement `Persist`: after every change the loader passes it the editable layer to save. `Version` detects external file changes; on conflict, the loader replays the modification on top of the latest content. See rutis-dsh's `UserLayerStore` for a complete file implementation. This example is compiled and run by `crates/rutis-loader/tests/migration_example.rs`.

The plugin itself need not change: `PluginFactory` constructs it as before. To expose a configuration schema to the loader, register a schema (`Builtins::register` generates one automatically for configurations implementing `JsonSchema`). A plugin may optionally support:

- **Volatile fields:** fields marked `"x-volatile": true` in the schema do not cause a restart when only they change. The plugin receives `VolatileUpdate` through `ctx.events().on(ctx, &volatile_key(ctx), ...)` in `apply`.
- **Self-disposal:** call `ctx.dispose_self()`; the loader disables that row and writes the change to the editable layer.

Besides `Builtins` compiled into the host, plugin sources include dylib plugins (`rutis-dylib` `loader` feature, `dylib:<directory>`, Linux/macOS/Windows x64/MSVC) and JavaScript (Cordis) plugins (this crate's `interop` feature). Dylib plugins share one SDK artifact with the host. Loading depends on SDK identity (`SDK_ID`, including package names and versions in the SDK dependency tree; see §5.2 of the [dylib SDK design](design-dylib-sdk-2026-09-24.en.md)), not Rust API compatibility:

- If you continue using the existing SDK artifact (do not rebuild the SDK; identity stays the same), already-compiled plugins still load and the loader treats them as having no configuration schema.
- If you rebuild the SDK and dynamic host with this release's lockfile, `rutis` in the SDK dependency tree becomes 0.6.1 and SDK identity changes. Plugins must be rebuilt with the new SDK or loading rejects them.
- To make a plugin's configuration schema available to the loader, rebuild it with `export_plugin!(..., schema: ...)`.

See the [rutis-loader README](../crates/rutis-loader/README.md) for configuration layers, editable-layer persistence, includes, and expressions.
