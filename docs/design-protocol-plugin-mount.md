# rutis / Cordis 跨进程挂载设计

状态：开发中。双向值方法挂载已采用接入时生成绑定、通过公开 API 注册的外挂方案；已实现范围和运行方式见[原生挂载示例](../examples/native-mount/README.md)。事件、对象及运行期依赖传播尚未实现；没有修改框架内核。

依据：[需求](requirements-protocol-plugins.md)。核对基准：rutis `2e564e3`；项目使用的 `@deepseek-ai/cordis@4.0.1`。

## 1. 核心决策

**原插件留在原框架中执行。两端适配器把跨边界的操作接回原生入口；语言绑定自动生成。**

| 决策 | 原因 |
| --- | --- |
| 两端各运行真实的 rutis / Cordis | 复用插件加载、依赖门控、Context 和清理；不重写框架 |
| 挂载入口表现为调用方的普通插件 | 应用继续使用自己的装配、配置和卸载方式 |
| 两端地位对等，使用一个双向会话 | 服务、依赖和回调都可能反向调用；不需要中心转发服务 |
| 绑定来自原接口和构建信息 | 不让用户逐插件维护另一份协议定义 |
| 同步调用在等待时允许处理嵌套调用 | 保留同步方法、属性与回调；不能只阻塞等待一个响应 |
| 生命周期由原框架决定 | 适配器连接跨进程关系，不维护第二套插件状态机 |

## 2. 结构与使用入口

```text
Rust 进程                                  Node 进程
+---------------------------+              +---------------------------+
| rutis + 原 Rust 插件       |              | Cordis + 原 TS 插件        |
|          | 原生 API       |              |          | 原生 API       |
| 生成的绑定 + rutis 适配器  | <==========> | Cordis 适配器 + 生成的绑定 |
+---------------------------+   双向 IPC   +---------------------------+

接入时：插件源码 / 类型声明 / 构建信息 --> 生成绑定 --> 编译、加载、原生注册
```

“适配器”是应用使用的库，不是新的宿主产品。插件仍拿到真实 `Ctx` / `Context`；适配器向其中注册服务和监听器，不以替换整个 Context 为前提。

应用装配只增加插件包、配置、运行位置及依赖连接。生成的挂载对象实现调用方的原生插件入口；服务仍从 `ctx.require...` / `ctx.xxx` 获取，事件仍走原生事件 API。不另设业务使用的 `remote.call()`、`remote.on()`。

自动接入是交付要求：安装／构建阶段由接入工具生成绑定并完成所需编译；运行时挂载由接入库建立连接并执行原生注册。开发者无需单独运行生成器或维护生成文件，最终用户无需执行生成或注册操作。

## 3. 自动绑定的职责

| 内容 | 生成结果 | 必须验证的约束 |
| --- | --- | --- |
| 插件入口、配置和依赖 | 调用方的原生插件包装与配置类型 | 原插件业务不改写；子插件仍交原框架加载 |
| 服务类型、方法和属性 | 消费方类型与代理；提供方调用真实对象的分发器 | 同步/异步、读写和错误形状保留 |
| 对象、函数、迭代器 | 本语言的对象、回调和迭代入口 | 原对象留在创建方；身份和生命周期不能变成值拷贝 |
| 事件和上下文关联 | 原生事件类型及作用域映射 | 使用完整的类型/名称/作用域身份，不只按字符串匹配 |

原插件已有 `.d.ts`、Rust 类型定义等是输入，不要求作者新增协议注解。生成器需使用解析后的类型及实际构建配置；运行时枚举对象属性或 Rust `TypeId` 不能替代接口信息。

接入 Cordis 服务时，生成本地 Rust 类型，例如 `bindings::Cache`；接入插件注册这个类型，Rust 消费者也针对这个类型编译。提供和读取使用相同的 `TypeKey`，不存在“把另一个类型冒充它”的问题。反方向生成 TS 绑定，由 Rust 导出代码读取并调用原服务对象。

Rust 绑定必须在使用它的代码编译前生成；运行时加载负责实例化和注册，不能临时向已编译代码增加静态类型。生成器还需验证 TS 动态成员、Rust 可访问类型、借用签名和接口发现，不能把这些工作省略为一个反射调用。

## 4. 调用与对象

### 4.1 一个调用机制

协议职责收敛为以下三项，消息编码和字段布局不在可行性验证之前冻结：

| 职责 | 最少携带的信息 |
| --- | --- |
| 调用与返回 | 调用编号、目标引用、操作、参数、结果或错误；嵌套调用关联 |
| 引用管理 | 会话内身份、归属端、保留与释放 |
| 框架连接 | 服务可用性、监听注册/撤销及挂载/清理操作 |

服务方法、属性操作、回调和事件续延共用调用机制，不分别建设 RPC 子系统。

```text
A 调用同步方法          B 执行业务
     | ----- call ------> |
     | <---- callback --- |
执行原回调                 | 等回调
     | ----- result ----> |
     | <---- result ----- |
返回普通值
```

异步调用交还语言运行时，最终完成原 Promise / Future。同步调用在原执行线程等待，并分发所属调用链中的反向调用；Rust 栈借用与 JS 闭包不能随意迁到通信线程执行。

独立通信线程只负责收发，不能代替 JS 所属线程运行闭包。等待器也不能被描述为“启动一个嵌套 Node 事件循环”：libuv 的 `uv_run` 不支持重入。需要覆盖正常插件中的 timer、Promise、I/O 与同步调用交错，才能证明执行模型成立。[Node-API 线程规则](https://nodejs.org/api/n-api.html#asynchronous-thread-safe-function-calls)、[libuv 循环规则](https://docs.libuv.org/en/v1.x/loop.html#c.uv_run)。

### 4.2 值与引用

具有值语义的数据按值传递；保有身份的对象、函数及 Context 关联按引用连接。引用回到归属端时恢复原对象；同一存活引用在接收端复用代理。属性读取执行原读取操作，不用缓存假装同步状态。

代理释放和插件清理接回原生所有权；借用引用不得越过原调用有效期。协议编号只在内部存在。原接口允许保存的回调不能一律绑到单次调用结束；借用接口也不能被偷偷提升为永久对象。

TS 异常映射为新生成 Rust 绑定的 `Result<T, Error>`；同步方法仍同步，Promise 方法生成 async 方法。断连使未完成调用失败，不自动重放。若既有 Rust 签名没有错误返回通道，如何保留该签名并暴露通信失败仍需单独验证，不能套用新生成绑定的规则改变原接口。

## 5. Context、依赖与清理

| 操作 | 接入要求 |
| --- | --- |
| 提供服务 | 在对应原生作用域注册代理，按真实提供者的可用性通知本地依赖机制 |
| 读取与拦截 | 保留读取方作用域及上下文关联；返回本语言类型；反向调用仍使用正确的调用方身份 |
| isolate / 派生 Context | 建立作用域对应关系；原框架执行本地解析，不复制整个 Context 内存 |
| 配置、子插件和重载 | 操作真实原生实例；挂载包装转交操作及结果，不自行模拟状态转换 |
| 依赖撤销 | 清理相关消费者时保持其关闭所需的服务，随后撤销代理和提供者资源 |
| 卸载 | 由原生 effect / disposer 触发跨边界清理，完成后才报告卸载结束 |

接入优先采用原生依赖链：导出适配插件声明依赖原服务，导入适配插件提供生成的代理；两端清理通过各自的异步 effect 连接。这样原服务的移除可以先触发导出适配插件的清理，再等待远端代理及消费者退出。此路径需验证持有的原服务在清理期间的可用性、动态替换与循环依赖，不先增加全局服务变更钩子。

远端插件的依赖由其原框架判定，不能让两端挂载包装互相等待“对方已 Active”而形成额外启动循环。连接与依赖接入必须先于原插件的业务初始化建立。

必要的是连接原生操作发生的边界。轮询诊断快照不能精确替代服务变化、监听注销或清理开始通知；也不能在提供者已经销毁后补发一条消息，宣称保留了消费者的清理顺序。

## 6. 事件

决策：跨边界监听必须作为独立监听参与一次原生分发，保留顺序、作用域、once、短路与 `next`。不能用“本地广播一遍，再让远端整条总线广播一遍”替代。

优先通过原生 `on` / `on_waterfall` 等入口登记生成的监听器，把调用另一进程的操作放进监听器内部，由原总线负责顺序、短路与续延。中间件的 `next` 使用同一反向调用机制。分发归属及两端注册如何进入同一逻辑顺序仍需验证；不预设必须提取所有既有回调并另建全局分发器。

| 原生入口 | 跨边界需要保留的行为 |
| --- | --- |
| Cordis `emit` | 返回前调用监听器的同步部分，不等待其返回的 Promise |
| rutis `emit` | 保留原有异步入队及同键分发顺序 |
| `parallel` / `serial` | 保留原生等待、错误汇总、监听顺序与短路规则 |
| Cordis `bail` / rutis `bail_sync` | 同步得到短路结果 |
| `waterfall` / `waterfall_sync` | 保留续延控制、返回值和原生有效期规则 |

这是语义映射要求，不是现成实现。两端对同步重入、短路值和监听类别原有差异还需逐项验证；不能按同名方法直接转发。特别是 rutis 的异步监听没有可供 Cordis `emit` 任意调用的“同步前半段”入口，跨类别组合不能未经验证便声称等价。

## 7. 现有接口的接入方式与边界

### 7.1 原生入口能够承担什么

| 接入内容 | 使用现有 API 的方式 | 尚需验证的部分 |
| --- | --- | --- |
| 服务提供和读取 | 生成类型后使用 `provide_as` / `require_as`；导出侧作为普通消费者取得原服务 | 接口自动发现、私有类型、动态服务及作用域映射 |
| 原生依赖 | 生成适配插件通过 `Plugin::injects` 声明实际服务依赖 | 远端可用性变化与本地门控的连接 |
| 事件 | 生成监听器通过 `on` / `on_waterfall` / 同步入口注册，内部执行跨进程调用 | 混合监听顺序、once、同步/异步类别及重入 |
| 清理 | 使用 `Effect::AsyncDisposer` 和原生依赖撤销过程等待远端清理 | 清理期反向调用、替换与循环依赖 |
| Context | 在真实原生 Context 中提供代理、读取服务和挂载适配插件 | 跨边界的隔离与调用方关联 |

依据：[Ctx 注册与读取](../crates/rutis/src/ctx.rs)、[Plugin 依赖声明](../crates/rutis/src/plugin.rs)、[事件注册](../crates/rutis/src/bus.rs)、[异步清理](../crates/rutis/src/effect.rs)。这些入口支持“生成后作为普通插件接入”，尚不能单凭接口存在就宣称全部行为已验证。

### 7.2 具体类型限制适用的场景

若某个既有 Rust 消费者明确依赖另一个 crate 的具体 `OriginalCache`，再生成一个 `CacheProxy`，两者不能互换；字段和固有方法也不能仅靠注册表拦截。这一限制针对替换既有具体依赖，不否定 §3 的目标语言绑定生成。

已有可实现的 trait 可以由代理实现；导出原 Rust 对象给 TS 也不要求把原 Rust 对象替换为代理。遇到具体类型替换场景时应单独说明，不把所有跨语言挂载都视为这一场景，也不据此删除完整需求。

依据：[精确类型存储](../crates/rutis/src/registry.rs)、[读取拦截](../crates/rutis/src/intercept.rs)、[Rust 字段访问规则](https://doc.rust-lang.org/reference/expressions/field-expr.html)。

### 7.3 观察接口的限制不等于接入接口不足

`observe_dispatch` 不能改变结果，`subscriptions()` 不提供回调，诊断快照不能代替实时变化；这些事实只能排除“靠事后观察接管全部内部行为”的做法。它们不能证明生成的普通插件无法通过注册、依赖与清理入口完成接入。

例如，若某个实现需要把运行期间新增的 Rust 监听器逐个放进远端列表，现有监听快照确实不给它回调入口；但应先验证“监听器留在原总线、向该总线注册远端代理”的接入方式，而不是立即增加内核钩子。

只有给出原生插件的具体用例，并证明生成接入后仍缺少必要操作，才提出最小扩展。当前不把修改框架列为实施前提。

## 8. 验证与下一步

2026-09-28 在临时目录完成两项最小实验，未加入仓库代码：

| 实验 | 结果 | 能证明什么 |
| --- | --- | --- |
| Node 26.8.1，两进程管道，同步方法内反向同步回调 | 返回普通数值 `42`，没有 Promise | 同步 IPC 与嵌套同步回调可行；不证明完整 Node 调度兼容 |
| Rust 1.98.1，按 rutis 存储形状擦除 `Arc<T>` | 代理不能下转为原具体类型；同一 trait 的代理可下转 | 只证明不同具体类型不能互换，不否定生成类型后按同一类型注册与读取 |

下一步验证接入路径，不开展大面积实现：

1. 以普通插件的实际接口生成两端绑定，验证编译、注册、原生读取和双向调用；区分接口生成与既有具体类型替换。
2. 用原生依赖链与异步 effect 验证服务撤销、远端消费者清理及关闭期间的反向调用。
3. 验证运行时增删监听、两端混合顺序、短路和续延；失败时定位缺失操作，不能仅凭观察接口的限制推断要改内核。
4. 验证同步等待与真实 Node / Tokio 调度的组合，不能只用简单 RPC 成功代替。

部署、重连、重试、监督进程、共享内存模拟、通用编译器改写和分布式垃圾回收都不作为补洞手段。若上述问题不能成立，应修改设计或明确讨论约束；不增建平台，也不默默收缩成异步服务子集。
