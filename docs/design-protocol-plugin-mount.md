# rutis / Cordis 跨进程挂载：组合设计

依据：[需求](requirements-protocol-plugins.md)。原生基准：rutis `2e564e3`、Cordis `4.0.1`。本文定义目标方案；实现范围与阶段验收见[路线图](roadmap-native-plugin-mount.md)。框架扩展、共享版本页和新的接口提取器均尚未实现。

**原插件在原框架中运行。接入时生成另一语言的类型和挂载入口；服务读取取得对象，后续操作固定指向该对象。原生依赖和 effect 决定启动、撤销与清理。**

## 1. 身份与所有者

```text
应用：包 / 原入口 / 配置 / 运行位置 / 依赖连接
                         |
                     自动生成绑定
                         |
       Rust 应用或插件                    TS 应用或插件
              |                                 |
        真实 rutis                        真实 Cordis
              |                                 |
       原生接入 + 绑定 <====== 双向会话 ======> 绑定 + 原生接入
              |                                 |
          原 Rust 对象                      原 JS 对象
```

适配器是库，不引入另一个业务 host。每次独立挂载拥有一个对端运行时；不建设共享进程调度、部署、重试或重连平台。

| 身份 | 含义 | 所有者 |
| --- | --- | --- |
| 接口 | 类型、成员、同步性、所有权、错误及事件规则 | 原声明 |
| 服务绑定 | 某作用域及键当前提供的对象和可用性 | 原生注册表 |
| 对象引用 | 一个具体对象及其原生有效期 | 原对象所有者 |
| 注册代次 | 一次服务、监听或 effect 的激活 | 原生提供者 / 作用域 |
| 调用 | 一次操作、嵌套回调及临时借用 | 原始调用链 |

服务名不是对象身份，引用不是插件依赖，重新激活不复活旧对象。线协议不传 TypeId、指针或原生框架内部状态枚举。

## 2. 接入生成与连接规则

### 2.1 类型来自编译期，注册来自运行期

| 内容 | 来源与处理 |
| --- | --- |
| TS 类型 | TypeScript 检查器读取包导出、实际项目和声明合并 |
| Rust 类型 | rustdoc JSON + 对应格式版本的 rustdoc-types，读取公开可达 API、展开后的项、re-export 和公开 trait 接口 |
| 类型闭包 | 从公开服务、事件、配置及其参数 / 结果递归生成描述；私有实现留在原进程 |
| 实际服务 | 原生注册观察接口报告类型、键、qualifier、作用域及代次；不静态推断任意控制流中的 provide |
| 实际实例 | 运行期建立对象引用；一个类型描述可对应任意数量的实例和动态服务名 |
| 校验 | 生成的调用由原语言编译器检查；启动先核对线协议和接口契约，再执行原插件 |

**不采用 rustc_driver / rustc_private。** rustdoc JSON 仍需要 nightly，格式也不是稳定标准；降低的是对编译器内部 API 的耦合，不是消除了工具链成本。[rustdoc JSON](https://doc.rust-lang.org/rustdoc/unstable-features.html#json)、[格式版本](https://docs.rs/rustdoc-types/latest/rustdoc_types/constant.FORMAT_VERSION.html)。

构建集成锁定受测的提取工具链和 JSON 格式。默认让 Rust 插件进程与接口提取使用同一工具链、目标和 features；通过 IPC 连接它的 Rust 应用仍可用 stable。已发布的接口产物只有匹配原包、构建条件和插件产物时才能复用。首次从源码接入需要准备该 nightly 工具链及额外的文档编译；这必须列为安装依赖和构建耗时，不能藏成“零成本自动生成”，也不使用 RUSTC_BOOTSTRAP。

普通构建自动执行提取和生成，开发者不单独运行生成器。仅有 stable、没有匹配产物且不能准备提取工具链的环境，不能完成首次 Rust 接口生成。指定另一编译器构建插件、文档专用 cfg、宏 / build.rs 的环境差异不能靠一次编译通过就证明接口完整，须在 P1 的构建矩阵中验证；无法确认的组合明确诊断。

公共类型表不依赖扫描 provide 调用。原生注册时，以本地 TypeId 找到编译进同一插件进程的类型描述和转换函数，再发接口标识。仅内部使用的私有服务不自动导出；被连接的服务若没有可生成的公开接口，应在激活前诊断。开放泛型和运行期才出现的新类型不能凭 TypeId 补出 Rust 静态 API。

### 2.2 构建入口

```text
普通安装 / 构建
  -> 读取包配置、原入口和连接
  -> 提取公共类型闭包，生成两端绑定
  -> 编译原包、分发器与应用，打包对端入口
普通启动
  -> 协议握手及契约检查
  -> 建立双向接入及原生作用域
  -> 原框架加载原插件
  -> 按实际注册及原生可用性发布绑定
```

生成文件在构建目录；缓存键包含源码 / 声明、锁文件、工具链、目标、features / cfg 和 TS 配置。应用不维护 IDL。当前示例的源码路径和 build.rs 是开发切片，包级构建集成在 P5 交付。

业务仍用 ctx.require / ctx.get、ctx.xxx、原生事件和 disposer。新生成 Rust 类型可以把外语属性表示成同步访问方法，把外语异常表示成 Result；不改写原 Rust 类型已有字段或方法。

### 2.3 服务名与类型映射

| 项目 | 规则 |
| --- | --- |
| 接口标识 | 锁文件中的包身份 + 定义项完整路径 + 已具体化类型参数；re-export 别名归到同一项，结构相同不自动视作同一类型 |
| 绑定地址 | 挂载别名 + 作用域 / isolate + 原生键 / qualifier + 注册代次 |
| Rust 导入类型 | 同一接口生成一个实体类型，挂载别名模块重导出它，例如 `foreign::search::Counter`；本地以该类型的 TypeId 注册 |
| Cordis 默认键 | JS 原键保留；Rust 类型默认使用短名的小驼峰形式，例如 Counter → counter，仅作可读别名 |
| 冲突 | 在同一可见作用域发布前检查；同名但不同来源 / 类型 / qualifier 不覆盖、不自动加随机后缀；动态注册同样检查 |
| 显式连接 | 应用把完整来源地址映射到目标类型或服务键；先校验接口及原生可见性，名称相同不代表契约相容 |

配置放在应用现有清单：Rust 为 `Cargo.toml` 的 `package.metadata.rutis.mounts.<别名>`，Node 为 `package.json` 的 `rutis.mounts.<别名>`。每项记录 package、entry、config、services 和事件连接；services 用完整来源名映射目标键。例如两个 crate 的 Counter 映射为 `billingCounter` 和 `metricsCounter`。短名无冲突时无需配置映射，已有消费者所需的键由应用明确连接。

类型身份是包内定义身份；同一原生类型的多个挂载必须放入不同原生作用域或 qualifier，不能靠生成两个类型绕过原生冲突规则。

### 2.4 线协议版本

第一帧交换 `hello { major, minor, requiredFeatures, contractDigest }`。尚未握手成功不得发送业务操作。初版只实现一个版本，不预建多版本转换层。

major 表示帧 / 操作 / 所有权语义的不兼容变更，必须相同；minor 只允许可忽略的附加信息，选择共同支持的版本。所需能力或接口摘要不匹配时在挂载前失败，不降级掉事件或所有权能力。未知必需操作、引用计数错误均终止会话。协议版本、接口摘要和注册代次各有用途，不能互相替代。

## 3. 调用、异步结果和执行器

### 3.1 invoke 与 await 分开

| 操作 | 行为 |
| --- | --- |
| invoke | 执行原方法、属性或闭包，返回普通值、异步结果引用或原异常 |
| await | 等待已有的 Promise / Future，返回完成值或错误；不重新调用方法 |
| cancel / drop | 取消等待者或释放结果引用；是否取消业务由原对象的规则决定 |

JS async 函数的同步前缀在 invoke 时执行，返回的 Promise 已开始工作；Rust async 函数创建的 Future 按原生轮询规则推进。Cordis bail 对 Promise 本身判断短路，不等待其最终值。通信层不得统一 await 返回值。

调用状态保留真实参数借用和回调，直到原异步计算完成或原生取消实际释放它们；invoke 返回 Future 编号不结束借用，取消通信等待也不能提前释放。返回借用对象时继续关联其原所有者和有效期。

### 3.2 调用线程与顺序

```text
原调用线程                         对端原执行环境
    | -------- invoke ----------> |
    | <------- callback --------- |
 执行原回调                       | 等待本次回调结果
    | -------- result ----------> |
    | <--- value / awaitable ---- |
 同步返回，或把异步等待交还调度器
```

一个双向 Unix socket 传逐行 JSON 帧和带类型的值。调用号为“发起端 + 序号”，嵌套操作带调用链关联；每个方向按接收顺序受理，异步完成独立匹配。引用授予、使用和释放复用这条有序通道，不另走控制连接。

通信线程只收发。同步等待器只执行当前调用链所需的反向操作；控制消息仍可处理。JS 闭包留在所属线程，Rust 回调保留原执行器及借用约束。调用业务前释放全部会话锁和引用表锁；无关业务不因等待而任意重入。

**消息泵不等于事件循环 / Tokio 调度器。** 两端的同步等待都占用调用线程；§9 定义无法透明处理的调度环，不能把通信 Worker 或多线程运行时当成通用解法。

## 4. 服务读取、对象与释放

### 4.1 对象固定，稳定绑定用版本缓存

```text
第一次读取槽位 -> A -> 代理 A
提供者换值    -> B，提交新版本
第二次读取    -> 版本不同，解析 B -> 代理 B
已有代理 A 的方法 ----------------> 原 A
```

每次读取先经过调用方的原生声明、可见性及拦截检查。缓存键包含读取方 Context 视图、绑定地址和接口；不同 isolate / 关联 Context 不共用错误的对象代理。

| 读取类型 | 选择 |
| --- | --- |
| 原生注册表中的稳定绑定 | 本地缓存代理；读取共享版本，未变则不做 IPC |
| 首次读取或版本变化 | 向归属端解析一次，返回对象引用及解析时版本 |
| 有动态 getter、外部状态检查或远端逐次拦截 | 每次执行原解析；版本计数不能推断任意函数的结果或跳过副作用 |
| 对象方法 / 属性 | 固定指向已取得对象；对象属性的真实读写仍需通信，不缓存业务状态 |

选择每个导出运行时一份共享版本页，先用全局版本使缓存失效，不建立逐对象同步系统。归属端在原生注册、换值、撤销及影响读取视图的提交前置为奇数，提交后以 release 发布新的偶数版本；这个提交窗口不得执行用户代码或 await。读取端 acquire 读到相同偶数版本才命中；否则走解析操作。解析响应与其版本必须来自同一已提交状态。版本不回绕复用，结束会话使缓存整体失效。

共享页只放失效元数据。Node 自带 SharedArrayBuffer 不能直接把 Rust 进程的 mmap 映射进去；因此这条路线需要一个小型本地扩展，负责 mmap、原子版本读取和解除映射。它带来平台构建及分发成本，P1 必须测量；不能把现有 Worker 的 SharedArrayBuffer 当成跨进程共享页。原生接口还必须暴露正确的提交边界，事后异步通知不足以保证缓存不读旧值。

若无法证明某条读取路径的失效覆盖，它必须标记为逐次解析；不得偷用陈旧缓存，也不得因此宣称它达到了热路径性能目标。缓存失效不表示提供者重启，不改变旧 A 的身份。

**代价依据：** 2026-09-28 本机 Node 26.8.1、Intel Core Ultra X7 358H、Rust debug 子进程，预热 200 次后同步调用 `counter.current` 3,000 次：p50 51.8 μs、p95 113.0 μs、均值 61.2 μs，主线程连续阻塞约 184.5 ms。这是当前小值方法往返的样本，不是尚未实现的 getter 或缓存基准；已足以说明“每个 ctx.xxx 都往返”不能作为无性能代价的方案。P1 / P5 分别测缓存命中、失效、动态读取、事件和真实插件负载，保留延迟及事件循环停顿数据。

### 4.2 值与对象

| 内容 | 规则 |
| --- | --- |
| 值 | 保留 undefined / null、整数精度、BigInt、特殊浮点和字节 |
| 对象 / 可变数组 / 函数 | 保留身份；不能因可 JSON 化就转成快照 |
| 属性 | 归属端真实读写一次，保留 this 和原副作用 |
| 往返 | 返回归属端恢复原对象；同一存活引用复用本地代理 |
| 拥有引用 | 按 §4.3 计数持有；代理弱缓存不能作为永久强根 |
| 借用 / FnMut / FnOnce | 保留真实借用期、独占与单次消费；动态语言做对应运行期检查 |
| 弱引用 | 记录持有原生 Weak，不强持有目标；upgrade 在归属端成功后才授予目标的拥有引用 |
| 迭代 / 流 | 逐次 next、背压、取消及关闭，不预收集全部数据 |

传入的 Context 是原生 Context 的操作视图；接收插件自身仍使用当地真实 Context。派生、过滤、isolate、拦截和扩展属性走原操作，不复制字段模拟 Context。拥有的回调可在首次调用结束后继续使用；借用回调遵守调用期。

借用分发由持有真实 guard 的归属端状态执行，不把 guard 任意迁到通信线程，也不从编号制造延长寿命的 Rust 引用。生成类型与保存状态共同兑现生命周期。

### 4.3 引用授予与 release(ref, n)

每个会话内对象编号不复用。拥有端保存导出计数 E，接收端保存导入计数 I；它们表示线上的授予次数，不等于本地 Arc 数量或代理数量。

弱引用记录与目标对象使用不同编号；记录本身同样授予 / 释放，但其载荷为原生 Weak，不把这份记录的计数加到目标的强拥有计数上。

1. 拥有端每次向对端发送一项拥有引用，先增加 E，再把消息排入有序发送队列；在途授予也计数。
2. 接收端每收到一项授予增加 I，即使复用了同一代理。最后一个本地持有者释放后，可批量发送 `release(ref, n)` 并扣减 I。每批计数关联实际代理的持有期；旧代理的延迟 finalizer 只能释放自己那批，不能清掉同编号新代理刚收到的授予。
3. 拥有端处理 release 后扣减 E；只有 E 为零且没有本地在途调用 / 发送持有，才删除导出项。原生对象自己的其他所有者继续按原规则存在。
4. 消息编码、排队及执行都要临时持有其所用引用。引用使用消息必须排在对应 release 之前；不能把“已交给 Worker”当作“已写入有序队列”。
5. 传回归属端使用“归属端已有引用”标记，不重新授予自己；归属端解码时先取得本地持有，发送端随后才可释放该次使用的持有。断连统一清表，不逐项等待 release。

```text
已有 E = 1
拥有端排入新授予 R：E = 2 -- 新引用尚在途中
收到旧 release(R, 1)：E = 1 -- 不能删除 R
接收端收到新 R：I 增加      -- R 仍有效
```

计数与有序发送两者缺一不可：计数解决“旧释放与新授予交叉”，排队持有解决“把已释放编号传回”。计数下溢、溢出、越权 release 或释放后的使用是协议错误。[Cap’n Proto 导出 / 导入计数与 Release](https://raw.githubusercontent.com/capnproto/capnproto/master/c%2B%2B/src/capnp/rpc.capnp)。

### 4.4 业务清理与会话关闭

原生 effect / close 清业务资源；引用释放撤掉持有。独立拥有的旧对象可以在原插件卸载后继续合法存活，但失活 Context 和已关闭业务对象不能被引用计数复活。

挂载资源提供明确的 `close()` 会话回收入口，并挂到应用所有者的原生清理中。它先启动原生撤销和清理，保持收尾通信，随后使残留引用以 SessionClosed 失败并回收自有进程；**不等待 FinalizationRegistry 或所有代理被 GC。** 清理本身仍可能被业务代码阻塞，按原生取消 / 超时接口报告；这与等待 GC 是不同问题。

只卸载原插件而保留合法对象时，会话可被这些引用持有，没有隐式 TTL；需要确定退出时调用 close。配置更新 / 普通 fiber restart 复用会话；显式替换整个进程时由挂载所有者 close 旧会话，再启动新会话。应用无需逐个释放业务代理，也不依赖多次 GC 才回收热重载进程。

FinalizationRegistry 只用于正常运行期间归还未显式释放的导入计数，不能决定显式关闭的完成。跨端强引用环仍需原生 close、注销或弱关系断开；不建设分布式 GC。强制结束会话与“旧对象永久可用”不能同时保证。

## 5. 事件路由

每个连接的事件键及作用域选择一个真实原生总线拥有监听顺序，另一端的监听逐个登记进去，effect 仍归原注册插件。并发登记以拥有方提交为序，prepend、过滤和 once 保留原规则。

```text
原监听 A 登记 -- 完成
远端 B 登记  -- invoke 登记一个监听代理 -- 完成
原监听 C 登记 -- 完成
                    |
                 [ A, B, C ]
                    |
             一次原生分发，各调用一次
```

原生接口须提供带作用域、once 资格和调用期持有的监听快照，并允许入口采用所需的原生分发算法。不把远端整条总线包装成一个监听，不双边重复广播，不复制第三套全局调度器。

| 入口 | 调用及等待 |
| --- | --- |
| Cordis emit | 逐个 invoke，保留 JS 同步前缀；不 await Promise |
| rutis emit | 交原队列，保持同键规则；原调度器推进异步监听 |
| parallel | 按原规则启动并等待，保留调用方的错误汇总 |
| serial | 按快照调用并等待，按事件契约短路 |
| Cordis bail | 同步判断原返回值；Promise 自身也是返回对象 |
| rutis bail_sync | 只调用同步监听；None 放行、Some(v) 短路 |
| waterfall | 传递本次原生 next 引用，保留次数、借用和返回类型 |

同名不保证兼容：Some(false) 不等于 Cordis 原始 false；Rust 单次借用 Next 不等于可多次调用的 next。可生成忠于来源的外语类型，但不能默改已有消费者的契约。参数和结果复用同一对象、Promise、回调和 Context 机制。

注销撤掉后续资格，已开始分发按原快照收尾；once 只由登记来源的原生包装消费一次，不双重包装。同键重入检查仍归原框架。

**同步成本：** 总线归 rutis 时，每次 Cordis 同步 emit / bail 至少需要一次主线程往返；其中每个 JS 监听还需反向调用，使同步前缀回到原线程执行。通信线程无法消除这段阻塞。总线归 Cordis 时 Rust 同步入口有对称代价。总线归属由连接固定，不按某次调用临时切换来隐藏成本。

## 6. 依赖与生命周期

### 6.1 原生依赖图

导出侧是原服务的原生消费者；导入侧按原生可用性发布绑定。可选读取不变成必需依赖；每个提供者及激活独立拥有注册，不把整进程服务合成一个依赖单位。

```text
Rust Audit -> 导出 / 导入 Audit -> Cordis Search
           -> 导出 / 导入 Search -> Rust 消费者
```

先建双向入口，再由原框架决定业务就绪；不能等 Search Active 才提供它依赖的 Audit。保存回调、Cursor 或 next 只形成引用关系，不凭空增加关闭顺序。

### 6.2 单向撤销

```text
提供者开始撤销
  -> 绑定不能新获取，保留合法旧对象
  -> 导入侧撤销提供者，启动原生消费者清理
  -> 清理仍能调用对象 / callback / close，解除在途等待
  -> 下游清理完成，确认本代撤销
  -> 完成导出清理
```

**先启动清理，再等在途调用结束。** 清理用已取得对象，不通过失活 Context require。导入侧卸载不反向要求原提供者或整个进程退出；单个导出 disposer 不等待会话关闭。

重复撤销加入同代完成结果，旧消息不能删除新注册。双方同时卸载，各自先开始原生清理；不建立相互等待整进程退出的边。真实业务互等不由协议猜测打破，桥接新增的等待环属于缺陷。

### 6.3 更新、reload 与子插件

| 操作 | 规则 |
| --- | --- |
| Cordis update(config, noSave) | 调用原 fiber.update；保留校验、Pending 延后解析及 internal/update waterfall 的拦截 / 返回值 |
| rutis update | 调用原 factory fiber.update；静态 plugin 无工厂时保留原生“不支持更新”结果 |
| 外层挂载更新 | 原生挂载句柄负责转发一次；只在来源框架执行业务配置校验和更新，不能两端各 restart 一次 |
| restart / reload | 普通重启复用会话，服务重新激活用新代次；进程替换须 close 旧会话并重做握手 |
| 子插件 | 留在原进程、原父 fiber 下运行；其公开注册通过同一观察入口投影，保留自己的作用域、依赖和代次 |
| 父插件卸载 | 原框架清理真实子树；外层只撤销相应投影，不逐子插件创建进程或另排清理顺序 |

外层的普通挂载 / 配置更新入口必须能转发原生 fiber 操作，并关联其完成结果。当前两端普通包装插件的 apply / effect 不足以保证这点；这是 §8 的生命周期接入要求，不以接收新 config 然后自写 restart 冒充完整 update。

### 6.4 故障

断连失败全部在途等待，撤销相关注册并执行本地可完成清理。已发送、未收到结果的调用标记“执行结果未知”；取消等待不撤销副作用。不重放、不自动重连，不影响无关插件。业务错误、接口错误、不可用、对象失效和通信失败进入目标语言相应错误通道。

## 7. 组合场景

场景：rutis 提供 Audit；Cordis Search 依赖 Audit，返回 Cursor、保存用户回调并广播 page；rutis 消费者使用 Search 和 page。以下是目标轨迹，双向验收清单见路线图。

| 阶段 | 行为与不变量 |
| --- | --- |
| 构建 | 一个公共类型闭包覆盖 Search、Audit、Cursor、page 和回调 |
| 初始化 | 先建立反向 Audit，Search 再按原依赖就绪 |
| 调用 | scan 的异步结果与返回 Cursor K 是不同引用 |
| 保存回调 | scan 返回后仍能调用拥有的回调 |
| 事件 | A / B / C 按原顺序参与；B 可异步调用 Audit |
| 同步操作 | K 的属性 / 方法可同步调用回调；不强行等待异步结果 |
| 换值 | 新读取得到 B；已有 A / K 不变；提交版本失效缓存而不重启提供者 |
| 更新 / 子插件 | 原 update 钩子只执行一次；子插件自己的注册代次可独立撤销 |
| 撤销 Audit | 沿真实依赖清理 Search 及其消费者，不沿引用边排关闭 |
| 关闭 Cursor | K.close 可完成反向操作，解除在途调用；清理先于排空 |
| 收尾 | 注销监听、归还计数；显式 close 无需 GC 即回收进程 |
| 任意阶段断连 | 失败在途调用，撤销投影；旧引用不投向新实例 |

反向由 Cordis 提供依赖、挂载 rutis 插件，使用同一协议与所有权规则。

## 8. 接入改动及上游依赖

协议、生成、序列化、对象表、共享页和进程管理均在外挂库。原框架只提供无法由现有公开入口实现的接入能力；本设计不授权直接修改第三方内核。

| 能力 | 原生接口必须保证 |
| --- | --- |
| 服务 | 覆盖 get / require / 属性读取；观察真实注册与代次；提供可验证的提交版本边界，区分稳定绑定与逐次解析；保留检查及锁外业务调用 |
| 事件 | 路由指定键的登记、注销及分发；提供原生快照和分发算法入口；本地后端入口不得再次进入路由 |
| 挂载生命周期 | 外层原生 update / restart 转发及完成关联；保留来源 fiber 钩子、原生子树和清理所有权 |

| 归属 | 实施条件 | 未具备时的结果 |
| --- | --- | --- |
| rutis（本仓库） | 独立小改动、原生行为测试及评审；不把协议类型放进核心 | 相应读取 / 事件 / 更新能力不计完成；不能用当前 intercept_require_as 代替 get 覆盖或提交后观察 |
| Cordis（第三方 @deepseek-ai/cordis） | 先完成基于 4.0.1 的接入验证和最小接口提案，再取得维护者接受及可依赖的发布版本；时间线不由本仓库控制 | 现有纯公开 API 的方法切片可保留；完整入口接管不能发布为已支持 |

若 Cordis 不接受事件接口，则其原生 emit / parallel / bail / waterfall 无法统一路由到 rutis 的总线；全局逐监听顺序、跨端短路和 once / 过滤的组合语义不能保证。双边广播或订阅转发不能作为等价退路。依赖这些能力的挂载须在启动前报缺失能力。持续维护 fork / monkey patch 不是默认方案。

现有实现依据：[rutis Context](../crates/rutis/src/ctx.rs)、[注册表](../crates/rutis/src/registry.rs)、[事件](../crates/rutis/src/bus.rs)、[fiber](../crates/rutis/src/fiber.rs)；已锁定 Cordis 包的 src/reflect.ts、src/events.ts、src/fiber.ts。rutis 逆序清理与 Cordis 并发 effects 的差别由适配器自己的组合 effect 处理，不重排原业务 effects。

## 9. 不能被适配器消除的约束

| 组合 | 判定与处理 |
| --- | --- |
| 现有公开 API 完全不变，同时覆盖所有原生入口 | 无法成立；需要 §8 的明确接入能力 |
| 原同步签名等待被自己阻塞的执行器 | 等待环；需要真正的异步边界，不能假称 Worker 或消息泵解决 |
| 不同具体类型 / 事件契约无损替换 | 生成忠于来源的外语绑定；不兼容的既有接口明确诊断，不能默改类型或短路规则 |
| 无提取工具链 / 匹配产物，仍首次生成完整 Rust API | 当前选定的 rustdoc 路线不能满足；安装成本必须明确 |
| 永久保留远端对象，同时确定结束其进程 | 不能同时保证；显式 close 是会话有效期的终点 |

两端调度冲突必须分别验收：

| 调用方向 | 具体等待环 |
| --- | --- |
| Node → Rust → JS 回调 | Node 同步等待 Rust，Rust 等回调的异步结果；回调的 timer / Promise 后续步骤需要被阻塞的 Node 主线程 |
| Rust → JS → Rust 回调 | Process::call 在 Tokio worker 上 recv；JS 等回调结果；Rust 回调依赖该运行时的 spawn / timer / 生命周期任务；current_thread 无线程推进 |
| Tokio 多线程 | 只是增加可用 worker；嵌套或并发同步调用占满 worker 仍可饥饿，不能当作任意插件支持条件 |

同步立即回调与创建后返回的 Promise / Future 本身不必形成上述等待环；它们仍须实现。把回调搬到另一运行时会改变执行环境，block_in_place 也不能通用支持 current_thread。当前方法切片没有反向回调，不能据其测试通过推断闭环已解决。[Node 线程通信](https://nodejs.org/api/worker_threads.html#worker_threadsreceivemessageonportport)、[libuv 循环规则](https://docs.libuv.org/en/v1.x/loop.html#c.uv_run)、[Tokio block_in_place](https://docs.rs/tokio/latest/tokio/task/fn.block_in_place.html)。

生成 foreign::Cache 不要求伪装成另一 crate 的 OriginalCache；但若要替换已有具体类型，或给没有错误通道的签名增加通信失败且禁止形状变化，差异必须单独确认。拒绝用例不等于完成“任意插件”目标。

## 10. 实现范围与验收

[PR #73](https://github.com/arcships/rutis/pull/73) 是[双向值方法切片](../examples/native-mount/README.md)。本轮修正为：导出时捕获真实对象，方法调用不重新查槽位；两端先启动原生清理，再等待在途调用。回归覆盖“disposer 解除等待”、旧代理不跟随换值，以及 Rust 导出 Context 关闭后的独立对象。

当前按名称编码的目标只定位一次挂载内已经捕获的对象，并非完整引用协议。新读取拿到新 B、运行期注册代次、引用计数、invoke / await 分离、反向回调、事件和包接入仍按路线图开发；不能把这次修复写成这些能力已经交付。

验收必须同时包含原生结果 / 顺序 / 身份对照，以及 IPC 次数、吞吐、p50 / p95 / p99 和调用线程停顿。缓存命中路径须做到零 IPC；动态 getter 和同步远端事件必须单独展示成本。阶段用例通过后仍要运行 §7 全链路，不再用孤立方法测试代替完整兼容性。

历史 [#66](https://github.com/arcships/rutis/issues/66)—[#70](https://github.com/arcships/rutis/issues/70) 只作为来源：其中仅异步事件、仅调用期回调、排除 waterfall / 流及人工接口的限制已被最新需求覆盖。PR 的关联不表示按旧范围验收。
