# rutis / Cordis 跨进程挂载设计

依据：[需求](requirements-protocol-plugins.md)。核对基准：rutis `2e564e3`、`@deepseek-ai/cordis@4.0.1`。状态：设计审查。

**采用原框架、自动绑定、一个双向会话。完整目标尚未闭合，不能把剩余工作全部视为编码。** §9 列出具体阻塞场景及闭合条件；这些场景仍属于需求，不以“不支持”处理后宣告完成。§2—§8 是其余机制的设计约束，不代表现有代码已经实现。

## 1. 目标与决策边界

| 项目 | 决策 |
| --- | --- |
| 使用方式 | 两端通过本框架的插件、Context、服务、事件和清理入口使用对方插件 |
| 原插件 | 留在原语言和真实框架中执行；不增加协议入口，不改写提供者和消费者业务 |
| 装配差异 | 应用选择包、原入口、配置、运行位置和依赖连接；绑定集成到正常构建和加载 |
| 接口形状 | 同步仍同步，异步仍异步；跨语言类型按目标语言生成，原语言接口不变 |
| 实现范围 | 外挂适配库；需要框架新能力时列出具体缺口，不默认修改内核 |
| 复用边界 | 原框架拥有插件状态、依赖解析、事件分发和 effects；适配器连接跨进程操作 |
| 不建设的内容 | 部署平台、重连重放、自动重启、监督进程、共享内存模拟、备用通信路线 |

历史 issue 不能缩小最新需求：[#66](https://github.com/arcships/rutis/issues/66) 的“仅调用期回调、异步事件、排除流”，[#67](https://github.com/arcships/rutis/issues/67) 的异步边界及由接口维护者集中维护适配的安排，及 [#68](https://github.com/arcships/rutis/issues/68) 对同步事件、waterfall、任意 Context 过滤闭包的排除均已过时。[#69](https://github.com/arcships/rutis/issues/69) 的依赖清理要求和 [#70](https://github.com/arcships/rutis/issues/70) 的接口一致性要求继续适用；不据此引入额外平台。

## 2. 模块和接入流程

```text
应用的普通安装 / 构建
  插件包 + 原生入口 + 构建配置 + 依赖连接
                         |
                     绑定生成器
                         |
          +--------------+---------------+
          |                              |
   Rust 类型 / 挂载插件             TS 类型 / 挂载插件
   Rust 原对象分发代码             TS 原对象分发代码
          |                              |
   rutis + 原 Rust 插件            Cordis + 原 TS 插件
          |                              |
   生成绑定 + rutis 适配器 <======> Cordis 适配器 + 生成绑定
                          双向 IPC
```

没有另一个业务 host。适配器是应用依赖的库；新进程只承载另一语言的运行时和原框架。初始实现每次独立挂载拥有一个对端进程和一个会话，不引入共享进程调度。原插件继续按原框架加载子插件。

| 模块 | 拥有的职责 | 不拥有的职责 |
| --- | --- | --- |
| 生成器 | 接口分析、目标语言类型、原对象分发、挂载包装 | 运行期业务状态 |
| 会话 | 消息收发、在途调用、引用与调用链关联 | 插件加载策略、事件排序规则 |
| 框架适配器 | 原生注册、作用域连接、可用性与清理连接 | 第二套依赖解析器或插件状态机 |
| 原框架与原对象 | 依赖判断、业务执行、监听规则、资源清理 | 通信细节 |

挂载顺序：校验产物 → 建立会话与作用域连接 → 注册双向依赖入口 → 交原框架加载原插件 → 按实际可用性发布服务。初始化中的反向调用必须可用；不能先等待远端插件 Active，再建立它启动所需的依赖。

## 3. 自动绑定与包接入

### 3.1 构建流程

输入包括：包及原生入口 / factory、配置类型、原接口、实际构建配置、应用的依赖连接。一个 Rust crate 不一定只有一个插件，也没有统一无参构造约定；选择已有入口属于应用装配，不要求插件作者增加协议入口。

生成器使用一份内部接口模型产生两端代码。模型记录类型、成员、同步性、所有权、错误、事件规则及源位置；它是构建产物，不是用户另写的 IDL。生成文件放在构建目录，不提交、不手工维护。

```text
正常构建
  -> 解析原入口及实际类型
  -> 检查类型映射及访问权限
  -> 生成两端代码、声明和契约摘要
  -> 原语言编译器检查生成代码与原包
  -> 编译应用并打包对端入口
正常启动
  -> 比对两端契约摘要
  -> 使用本框架的普通插件入口挂载
```

Rust 类型必须在消费者编译前存在；“接入时生成”包含构建期，不能解释成运行时向已编译程序新增静态类型。Cargo 和 Node 包构建集成调用同一生成流程，应用不逐插件编写生成脚本。缓存由接口输入、锁文件、工具链、目标、features / cfg 和 TS 配置决定。两端摘要不一致时在原插件初始化前报错，不使用猜测兼容或运行时降级。

### 3.2 类型分析与生成形状

TS 使用真实类型检查器解析包导出、声明合并及引用。Rust 必须依据实际构建后的语义信息处理模块、宏、trait、关联类型及具体泛型实例；单文件 AST 不能代表完整接口。`cargo metadata` 只有包和构建信息，`Any` 没有方法反射；rustdoc JSON 当前仍属不稳定功能，也不能单独发现任意业务代码中的服务注册。完整 Rust 提取路线和动态接口发现属于 G1，当前解析器不是最终方案。[Cargo metadata](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html)、[Any](https://doc.rust-lang.org/std/any/index.html)、[rustdoc JSON](https://doc.rust-lang.org/rustdoc/unstable-features.html#-w--output-format-output-format)。

| 来源接口 | 目标语言绑定 |
| --- | --- |
| 同步方法 / Promise、Future 方法 | 同步方法 / 对应异步方法 |
| 对象及方法、属性 | 有类型的对象代理；TS 使用 getter / setter，生成的 Rust 类型使用同步访问方法 |
| 可调用对象 | 原生函数或闭包形状，保留接收者、参数、结果与所有权限制 |
| 迭代器 / 异步迭代器 | 目标语言迭代入口，逐次调用原 next，保留结束及关闭操作 |
| 服务、配置、事件 | 目标语言类型及本框架注册入口，不暴露引用编号 |

Cordis 服务可生成 `bindings::Cache`，rutis 提供方和消费者共同使用这个类型。它不能替换既有消费者已经依赖的不同具体 `OriginalCache`；可实现的原 trait 才能通过实现代理接入。导出原 Rust 对象给 TS 不涉及这种类型替换。私有成员、直接字段访问、开放泛型也必须逐项分析，不能生成同名类型后宣称兼容。

## 4. 会话与执行模型

### 4.1 一套操作机制

| 消息 | 最少信息与行为 |
| --- | --- |
| 建立会话 | 两端契约摘要；成功后才允许原插件初始化 |
| 调用 / 返回 | 唯一调用号、所属调用链、目标引用与代次、操作、参数、读取视图、结果或错误 |
| 引用持有 / 释放 | 引用身份、所有者、持有关系；释放代理与业务 close 完成分开 |
| 框架操作 | 服务发布 / 撤销、监听登记 / 注销、挂载 / 清理，关联原生所有者及代次 |

方法、属性、回调、事件续延和迭代共用调用机制。控制操作可在同一连接上交错，不能排在一个等待反向调用的业务请求后面。每个方向保持发送顺序；结果按调用号匹配。执行业务时不持有会话锁或适配器注册表锁。

传输先沿用现有 Unix socket 和逐行 JSON 帧；标准输出及错误输出保留给原插件。调用号由“发起端 + 单调序号”组成，两端均可发起。接收端先校验完整帧、契约和引用有效期，再调用业务；数值及引用使用带类型标记的值编码。更换编码不是补足接口语义的前提，不同时维护第二条通信路线。

### 4.2 同步、异步与重入

```text
调用方原线程                  对端业务线程
    | -------- call ----------> |
    | <------- callback ------- |
 执行原回调                      | 等待回调
    | ------- result ---------> |
    | <------ result ---------- |
 返回普通值
```

异步调用立即交还本语言调度器，结果完成原 Promise / Future。同步等待器处理当前调用链必需的反向调用及控制消息，无关业务留在正常调度队列。嵌套调用仍执行原框架的重入和借用检查，不因 IPC 允许原本非法的重入。

通信线程只收发、唤醒和路由；JS 闭包在所属 JS 线程执行，借用 Rust 数据的回调留在有效调用作用域内。不能把原闭包迁到 Worker，也不能嵌套 `uv_run`。[Node-API 线程约束](https://nodejs.org/api/n-api.html#asynchronous-thread-safe-function-calls)、[libuv 循环约束](https://docs.libuv.org/en/v1.x/loop.html#c.uv_run)。

这能处理同步反向回调，不能证明同步等待中任意异步工作都可推进。回调等待被阻塞线程上的 timer / I/O，是 G2。Rust 同样不能假定所有应用都使用多线程 Tokio；`block_in_place` 不适用于 current-thread runtime。[Tokio 执行约束](https://docs.rs/tokio/latest/tokio/task/fn.block_in_place.html)。

### 4.3 错误和中断

| 情况 | 对外行为 |
| --- | --- |
| 原业务错误 | 保留可表达的原类型、码、消息及原因，不丢失可匹配的错误分支 |
| 类型 / 契约不匹配 | 构建或挂载失败，指出原接口位置 |
| 失效引用 / 服务不可用 | 走生成绑定的原生错误通道，禁止转投新实例 |
| 断连 | 结束全部在途等待，撤销相关服务；已发送但无结果的调用标明执行结果未知 |
| 调用方取消等待 | 不推断对端副作用已停止；原接口提供取消操作时才传递取消 |

新生成的 Rust 绑定用 `Result` 表达远端操作失败，TS 用异常 / Promise rejection；不因此改写既有 Rust 签名。原有无错误通道的具体类型或 trait 如何暴露通信失败，属于 G1，不默认 panic、返回默认值或吞错。没有自动重试或重放。

## 5. 对象、属性、回调与流

### 5.1 身份与数据

值语义数据按值传递；具有身份的对象、函数、Context 和资源按引用传递。JS 对象和可变数组不能仅因可 JSON 化就认定为值。编码区分 `undefined`、`null`、布尔值、整数 / BigInt、浮点特殊值、字节及引用；不能丢失精度或把非有限数变成 `null`。

引用身份由会话、归属端、原对象及其有效代次确定。接收端对同一存活引用及同一原生上下文视图复用代理；传回归属端恢复原对象。经另一端再次传递时沿用身份，不层层创建新对象。类型描述决定可调用成员，编号不进入业务 API。

**读取服务与调用对象是两种操作：**一次原生读取得到 A，之后对 A 的操作固定指向 A。服务槽位换成 B 后，新读取得到 B，持有 A 的消费者仍使用 A，直至 A 按原所有权规则失效。每次方法调用都按服务名重新查询会破坏此规则。

### 5.2 操作及所有权

| 接口 | 执行规则 |
| --- | --- |
| 属性读写 | 在归属端执行真实 getter / setter 或字段操作一次，保留 this；不用快照伪装远端属性 |
| 同步 / 异步回调 | 返回形状不变，反向调用使用同一调用链 |
| 被保存的回调 | 原接口允许保存时，持有期跨越首次调用；注销或原生所有者释放后才撤销 |
| FnOnce / once | 调用前消耗资格，嵌套调用也不能再次执行 |
| FnMut / 借用 | 保留独占及借用期；不提升为 static，不把互斥锁当成可重入借用 |
| 返回借用值 | 归属端保留真实借用及拥有者，目标绑定表达有效期；不能仅返回脱离作用域的编号 |
| 迭代 / 流 | 按原协议拉取或订阅，保留结束、错误、取消和背压；不预先收集全部结果 |

适配器分别记录对象所有者、跨端持有关系和调用期借用。释放代理移除持有关系；调用原生 close / disposer 执行业务清理，两者不互相冒充。插件资源随原生 effect 清理；可独立存活的对象按自身所有权处理，不一律绑到首次调用或整次挂载。

发送拥有引用的消息前，归属端先建立该接收端的持有关系，避免消息在途时对象已释放。接收端以弱缓存复用代理，本地强持有结束后发送释放；同一代理的本地复制不产生新的远端对象。调用期借用只在对应调用存活时可访问，借用结束与迟到消息按调用及代次判定。断连移除该会话的持有关系；业务资源仍按其原生所有者清理。这些规则覆盖可明确表达的拥有 / 借用关系，不解决下述跨端环。

JS finalizer 只可辅助回收，不能作为按时关闭资源的依据。retain / release 也不能解决所有跨运行时引用环；原本可回收的环仍可回收，需要 G6 的完整方案。“卸载时统一释放”不等于保存回调和任意对象已经兼容。

## 6. Context、服务与动态依赖

### 6.1 作用域与原生注册

挂载点建立真实原生作用域的对应关系。服务身份包含类型 / 原名、实例或 qualifier、isolate 作用域及提供者代次；Rust `Event::NAME` 也不是事件唯一身份。原插件拿到真实 `Ctx` / `Context`，生成适配插件在其中提供和依赖服务。

读取先经过读取方的原生声明、可见性和拦截规则，再连接到提供方的相应原生读取视图。Cordis 上下文关联服务可能随读取方产生不同视图，不能只按底层对象全局缓存代理。派生 Context、isolate、过滤函数及用户扩展值保留原所有者和原生行为，不以 scope 字符串代替整个 Context。

| 场景 | 接入规则 |
| --- | --- |
| 必需依赖 | 导出适配插件作为真实消费者声明依赖；导入侧按实际可用性提供代理，交本地框架门控 |
| 可选读取 | 保留原可选读取方式，不新增必需依赖改变启动或重启条件 |
| 动态提供 / 撤销 / check 变化 | 原生变化接入对端注册与门控，不轮询诊断快照 |
| 配置更新 / 子插件 | 转交原实例的原生入口，不另造重载规则 |
| 服务值替换 | 新读取取得新引用，旧引用保持身份；替换值不等于提供者重启 |

普通导出插件的 apply / disposer 可连接依赖可用性，但不能涵盖所有可选读取、调用方视图和原地换值。rutis `ServiceWriter::set` 在同一提供者代次内更新值，不触发导出插件重启；需要补足 G3 的读取 / 变化边界。

### 6.2 撤销与清理

```text
原服务开始撤销
  -> 停止新获取，保留已持有且仍有效的对象
  -> 导出适配插件进入原生清理
  -> 对端撤销代理提供者，启动其原生消费者清理
  -> 清理代码仍可使用保留的对象和反向调用
  -> 必需清理完成，确认撤销
  -> 释放桥接持有关系，完成本次原生清理
```

清理期间使用已捕获的原对象，不通过已经失活的导出 Context 重新 require。提供者自身资源次序仍遵守原框架；适配器不能修复本地就提前销毁资源的插件。

**先启动原生清理，再等待需要收尾的调用。**不能先等全部调用结束再执行 disposer：某个调用可能正等待 disposer 释放资源才能结束。清理期间保持通信可用，最后才关闭会话和拥有的进程。

同代次重复撤销加入同一个完成结果；旧消息不得删除新代次注册，旧引用不得转向新实例。取消等待者不代表取消已开始的原生清理。关闭确认代表约定的清理完成，不能为打破等待环提前伪造确认。

rutis effects 的逆序清理和 Cordis 独立 effects 的并发清理不能混同。适配器内部需要顺序时，以一个原生组合 effect 串起“撤销服务 → 等待消费者 → 关闭会话”，不替原插件重排全部 effects。依据：[rutis 清理](../crates/rutis/src/effect.rs)，Cordis 4.0.1 `src/fiber.ts` 的 `_unload` 与 generator effect。

原生必需依赖环可保持 Pending，桥接不能新增双方等待 Active 的启动环。双方互相关闭时，重复关闭与循环等待是不同问题，见 G6。断连时没有远端清理确认，本地仍执行可完成的清理并报告失败，不宣称远端资源已正常关闭。

## 7. 事件

### 7.1 登记、分发与顺序

一个连接后的事件在相应作用域内只拥有一份有效监听顺序，归属于一个真实原生总线；事件连接确定归属，不新增中心事件服务。跨端监听作为单个原生监听参与其中。JS 回调回到所属线程，Rust 回调遵守原执行器及借用约束。

```text
原生监听 A -- 注册完成
远端监听 B -- 登记代理并确认
原生监听 C -- 注册完成
                  |
           原生顺序 [A, B, C]
                  |
         一次分发，逐个调用原监听
```

登记返回前完成拥有方注册，先后发生的登记有确定顺序；并发登记以拥有方实际提交顺序为准。prepend、once、注销、分发时快照及过滤采用相应原生规则。disposer 归原注册插件所有，跨端注销完成后才完成对应的原生注销。

归属端确定监听集合，调用入口仍决定所要求的完成和返回语义。不能因总线归属在 rutis 就把 Cordis emit 当作 rutis 入队。兼容分发接回已有原生算法，不存在等价算法或入口时进入 G4 / G5，不按同名 API 直接转发。

一个“转发远端整条总线”的监听不能产生任意交错顺序；两端各广播一次还会产生重复、回环和错误短路。原插件动态新增的监听同样需要完整接入，现有 rutis API 尚未证明满足 G4。

### 7.2 语义映射

| 原生操作 | 必须保留的规则 |
| --- | --- |
| Cordis emit | 返回前调用监听器的同步部分，不等待其返回的 Promise |
| rutis emit | 异步入队及同键分发次序，不改成 Cordis 的同步开始规则 |
| parallel | 原生并发、完成时机和错误汇总方式 |
| Cordis serial / bail | null、false、undefined 放行，其他值短路；bail 不自动 await Promise |
| rutis serial / bail_sync | None 放行，Some(v) 短路，包括 Some(false)；同步和异步监听分开 |
| waterfall | 每个监听收到真实余下链的续延；保留调用次数、有效期、返回值和不调用 next 的行为 |
| 过滤、global、模式监听 | 使用原作用域及真实分发上下文，保留实际匹配键，不只匹配诊断名称 |

内部结果区分“放行”和“短路及载荷”，避免把 Some(false) 丢成放行。但编码不能消除原生表达差异：变成 TS 原始 false 后，Cordis 仍会放行。混合规则需要明确的目标类型与执行入口，不能仅改 wire 格式宣称完成。

waterfall 的 next 是有原有效期的回调引用，不是额外广播。rutis 借用、单次消费的 Next 与 Cordis 可多次调用的闭包不等价；不缓存一次结果假装重复执行。原总线拒绝的同键同步重入仍应拒绝。

依据：[rutis 事件类型](../crates/rutis/src/event.rs)、[同步事件](../crates/rutis/src/event/sync.rs)、[总线](../crates/rutis/src/bus.rs)；Cordis 4.0.1 `src/events.ts` 的 `isBailed`、`dispatch`、`emit`、`serial`、`bail`、`waterfall`、`on`。

## 8. 兼容验收

每个用例先记录原生行为，再记录跨进程行为；检查调用 / 注册 / 清理轨迹、结果、身份和作用域，忽略通信耗时。双向分别验收。下列是完成条件，不是当前测试通过声明。

| 能力 | 必须覆盖的用例 |
| --- | --- |
| 自动接入 | 干净应用按包配置后正常构建启动，无手工生成；配置更新、子插件；接口变化重建，错误产物在 apply 前拒绝 |
| 接口分析 | 模块、宏、trait、features、具体泛型实例、动态注册；无法表达的接口给具体诊断，仍计为目标未覆盖 |
| 服务与属性 | 同步 / 异步方法、getter / setter 次数及接收者、业务错误；A 换 B 后旧读取仍 A、新读取为 B |
| 对象与回调 | 身份复用、往返及再次传递；保存 / 注销回调；嵌套调用；FnOnce、借用结束、跨端引用环 |
| 执行模型 | 反向同步回调；回调依赖原线程 timer / I/O；Tokio 不同执行模型；合法和非法重入 |
| Context 与依赖 | 双向依赖、必需 / 可选读取、isolate、关联和拦截；运行期出现 / 消失 / 替换 / check 变化；不串实例 |
| 事件 | A/B/C 顺序、prepend、once 嵌套分发、分发中注销、过滤；每种模式的短路 / 错误 / 完成时机；next 次数及有效期 |
| 迭代与流 | 拉取、结束、错误、提前关闭、取消及原背压，不提前耗尽或遗留订阅 |
| 清理 | 撤销依赖、清理期反向调用、清理解除在途等待、重复关闭及关闭环；旧消息不影响新实例 |
| 故障 | 初始化失败、对端退出、断连、失效引用；无伪成功或重放，无关插件继续运行 |

拒绝某类接口是明确诊断，不是兼容验收通过。简单 RPC 成功或测试总数增加不能代替上述行为验收。

## 9. 阻塞完整目标的设计缺口

以下给出反例、现有能力和闭合条件。不默认选择改内核、改原业务或收缩需求；这些条件闭合前，不继续扩展完整实现。

### G1：完整接口提取与目标语言表达

**场景：**Rust 插件通过模块 / 宏注册服务，返回借用对象；既有消费者依赖具体 OriginalCache。同名代理不能替换该类型，公开类型名也不赋予私有成员访问权。TS 运行期才确定的形状不能靠启动时枚举保证未来接口完整。

**现状：**生成器只证明部分公开值方法可接入。生成目标语言新类型、导出原 Rust 对象、替换已有 Rust 具体依赖是三种不同问题。

**闭合条件：**确定可复现的完整 Rust 类型提取工具链、动态登记的类型入口及所有权映射；为具体依赖和无错误通道签名给出不改原业务的接入方式。若需编译器改写或新的框架类型入口，先评审该实质变更，不能用排除这些接口宣告完成。[类型存储](../crates/rutis/src/registry.rs)、[字段规则](https://doc.rust-lang.org/reference/expressions/field-expr.html)、[访问权限](https://doc.rust-lang.org/reference/visibility-and-privacy.html)。

### G2：同步调用等待所属线程上的异步工作

```text
Node 原线程调用 Rust 同步方法
  -> Rust 调用异步回调，并等待它完成
  -> 回调在 Node 原线程启动，等待该线程上的 timer / I/O
  -> Node 原线程仍在同步等待 Rust 返回
```

**现状：**同步等待器能执行反向闭包，却不能推进被阻塞的完整 Node 事件循环。Worker 收包不解决原线程 timer，嵌套 uv_run 也不是合法方案。对应 Rust 同步方法在原生场景可以等待另一可运行执行器上的 Future，不能笼统归为“用户本来就死锁”。也不能静态承诺识别任意回调内部的调度依赖。

**闭合条件：**给出保持原同步形状及原线程行为的执行方案；若必须改变调用形状或运行时约束，明确承认与当前要求冲突并单独对齐。普通嵌套同步回调成功不关闭此项。

### G3：新读取、原地替换和读取方 Context

**场景：**同一提供者把 A 换成 B。消费者已持有 A，再通过 get 和 require 新读取；另有消费者处于不同 isolate 或上下文视图。应分别得到旧 A、新 B 和各自读取视图。

**现状：**rutis ServiceWriter::set 拦截发生在提交前，后续提交仍可能失败；成功后没有通知，依赖身份仍是原提供者及代次。intercept_require_as 不覆盖 get_as。固定导出 A、调用时重查 B、提交前通知都不满足完整规则。Cordis 4.0.1 直接 reflect.set 也不自动 notify，只拦截属性赋值不能覆盖全部入口。

**接入方向：**Rust 导出到 TS 时，可优先让生成的属性读取同步解析原服务，再返回固定对象引用；这不要求先把所有换值广播出去，但仍须覆盖 Cordis 的全部相关读取入口。TS 导入到 Rust 时，原 get_as 直接取注册表中的 Arc，不能仅靠生成代理的方法实现“每次读取取新对象”。因此缺口在原生读取边界，不是所有方法都要新增一层动态查找。

**闭合条件：**覆盖成功换值与相关原生读取的接入边界，保证因果可见性和读取方 Context；若选变化通知，明确提交、对端可见和同步 set 返回的次序，事后异步通知不足。最小框架扩展只针对该缺口，不是改造整个注册表的授权。[写入与拦截](../crates/rutis/src/intercept.rs)、[读取](../crates/rutis/src/ctx.rs)、[依赖判定](../crates/rutis/src/registry.rs)。

### G4：原插件动态监听的统一接入

**场景：**一端原插件注册 A，另一端注册 B 并确认，第一端再注册 C；从两端分别短路分发，都要求 A、B、C 顺序。

**现状：**整总线代理只能把 A、C 作为一组，不能插入 B。把单个监听注册到同一原生总线可保顺序，但要求另一端原插件的登记和分发可接入。rutis 回调存于私有 Hook，subscriptions 只有元数据，observe_dispatch 不能接管结果；Cordis 有 internal/listener 登记拦截，internal/dispatch 只是观察。生成代码调用 on 不能覆盖这些原插件入口。

**优先路径：**让 Rust 监听留在原总线，逐个注册 TS 监听代理；Cordis 在原插件加载前接入对应事件服务的登记和分发。这样不先要求提取 Rust 私有回调。仍需证明 Cordis 的 ctx.on / ctx.emit、直接 events 调用、派生 Context 及内部事件都保留行为，并解决 G5；公开事件服务可被包装，不等于这些入口已全部接通。

**闭合条件：**证明两端全部相关登记、注销和分发入口可按 §7 接入，或评审准确到这些操作的框架扩展。不能只因观察接口不足就推断必须改核；判据是实际 A/B/C 交错及两端原生分发都成立。[rutis 登记与观察](../crates/rutis/src/bus.rs)。

### G5：两框架事件规则不能直接等同

**场景：**rutis Some(false) 应短路，Cordis 原始 false 应放行；Cordis next 可再次调用，rutis Next 单次消费；Cordis emit 要同步开始监听，rutis async Listener 没有同样的同步前半段入口。

**现状：**同名转发、统一 await、包一层 Promise、缓存 next 结果都改变行为。一个原生总线只解决归属，不消除这些差异。

**闭合条件：**为混合事件的结果类型、监听类别和续延给出两端可表达的具体映射及执行入口，说明每种原生调用采用哪套规则。某组合若无法在原接口下表达，应讨论该项冲突，不能直接删除同步事件或 waterfall。

### G6：跨端所有权及循环清理

**场景：**JS 对象保存 Rust 回调，回调持有该 JS 对象；或两端 disposer 分别等待对方依赖清理。前者可能把原本可回收的关系变成永久远端根，后者可能形成桥接新增的等待环。

**现状：**引用计数、JS finalizer、卸载时清空引用表和关闭请求去重都不能单独证明正确。原生清理可覆盖有明确所有者的对象，不能推广为任意对象与关闭环已解决。

**闭合条件：**明确强 / 弱持有、借用和释放实现，以及允许清理反向调用但不新增循环等待的完成规则；原生已有问题与桥接新增问题分别验收。不默认建设分布式 GC，也不靠提前确认或超时强杀冒充原生完成。

## 10. 现有 PR 的定位与后续顺序

[PR #73](https://github.com/arcships/rutis/pull/73) 是双向值方法切片，运行方式见[示例](../examples/native-mount/README.md)。它证明生成代码可通过普通插件注册并调用原服务，不证明 §9 已解决。

| 现有内容 | 对完整方案的处理 |
| --- | --- |
| 双向原插件示例、原生注册、编译检查 | 保留作基础证据，示例范围不能充当产品范围 |
| 值方法生成器 | 可复用的初始实现；完整类型分析和包级接入尚未定型 |
| 服务名 + 方法调用 | 改为原生读取取得对象引用，再对固定对象操作 |
| 单向请求 / 返回等待器 | 需要双向调用链、回调、引用及清理控制交错 |
| 先排空调用再 dispose | 按 §6 先启动原生清理，避免互相等待 |

先闭合 G1—G6，涉及取舍或框架扩展时按具体场景评审；随后按“绑定与会话 → 对象及回调 → Context / 事件 / 生命周期 → 包接入与双向验收”实现已确定的整体方案。阶段只划分交付，不再把未决定的架构问题留给下一阶段。
