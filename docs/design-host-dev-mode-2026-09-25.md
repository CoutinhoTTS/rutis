# 宿主开发模式:真实宿主上的插件开发(2026-09-25)

> 对应 #52(插件分层)的开发体验面;依赖 #45/#56(dylib SDK 的热换机制)。
> 状态:设计稿;通道骨架已实现(`crates/rutis-dev`,建在 rutis-loader 上):`hello`/`describe`/`status`/`watch`/`load`/`swap`/`unload-dev`,装载项进 loader 的 overlay 层,swap 全有或全无。总线 probe、录制、dev 合成清单、保留上限配置、`cargo xtask dev` 未做。核心判断来自 2026-09-25 关于插件开发方式的讨论,结论:**插件开发必须在真实宿主上进行,宿主本身是开发平台,不只是运行容器。**

## 一、动机与定位

全 plugin 体系下,插件开发的真实依据是**运行中的宿主里实际存在什么**:此刻注册了哪些服务、事件怎么流动、你的服务被谁怎么调用、时序和数据长什么样。这些东西:

- 不在 SDK 里——其他插件动态带来的对象、事件类型,宿主方不可能预先定义;
- 不在文档里——环境是活的,每次部署都不一样;
- mock 编不出来——mock 覆盖接口形状,覆盖不了行为、状态和数据流。

因此在脱离真实宿主的环境(独立开发宿主、mock 栈)上只能做出 play demo。真实开发循环是:

```
改代码 → 编译 .so → 热换进正在运行的真实宿主 → 观察行为 → 再改
```

环境全程不重启、其他插件不动。这个循环的每个环节都宿主侧要有支持,本文档设计四件事:

| 能力 | 解决什么 |
| --- | --- |
| dev 通道(§三) | 热换怎么进真实宿主 |
| 环境自描述(§四) | 开发依据从哪来(动态接口与事件的唯一权威来源) |
| 观测(§五) | 换进去之后看什么 |
| 编译对齐(§六) | 本地编的产物凭什么挂得进真实宿主 |

**与 #45/#56 的分工**:dylib 设计解决"怎么安全地换代码"(机制);本文档解决"开发者在哪个宿主上换、依据什么写代码、换完看什么"(工作流)。协议插件(#46–#48)同样需要真实宿主调试,dev 通道对两者通用(§八)。

**dev 的"真实宿主"指什么**:完整业务部署——同一套宿主 + 全部业务插件,跑在开发机或共享 dev 环境,用开发数据。**不是**生产实例(§七安全边界)。生产宿主不开 dev 通道。

## 二、设计原则

1. **循环原子化**:从"保存源码"到"宿主里新版本生效"是一条命令、一个来回,中间不重启任何东西。
2. **环境是唯一权威**:写插件时参考的接口/事件清单来自运行时查询(§四),不来自离线文档或 SDK 预定义子集。
3. **校验分级,不降安全**:身份校验(SDK_ID,§5.4 of design-dylib-sdk)在 dev 下**照常执行**——dev 不是兼容性的后门;放宽的只是打包环节(清单、内容寻址缓存、发布哈希),dev 直接吃 `target/debug` 产物。
4. **观测先于功能**:没有事件流和注册表可见性,热换就是盲调。观测是 dev 模式的第一公民,不是附加调试器。

## 三、dev 通道

### 3.1 形态

宿主启动时显式开启(配置项或 CLI 参数),监听**本地** Unix domain socket / Windows named pipe,协议为 JSON lines(编解码零依赖,与 #47 的 schema 路线衔接;通道自身的消息 schema 进 #47 的接口定义,版本化)。生产构建默认无此监听(§七)。

### 3.2 指令集(初版)

| 指令 | 语义 | 失败语义 |
| --- | --- | --- |
| `hello` | 返回宿主身份:SDK_ID、SDK artifact sha256、toolchain、target、宿主版本 | — |
| `describe` | 环境自描述快照(§四) | — |
| `watch` | 订阅变更流:事件(可按名字/fiber/方向过滤)、注册表变更、fiber 状态 | — |
| `status` | fiber / 模块登记表当前状态(含 dylib 保留版本,§九) | — |
| `load` | 加载一个插件(本地 .so 路径,dev 不要求发布清单) | `LoadError` 原样返回 |
| `swap` | 对指定 fiber 热换新版本(复用 `FiberView::update` 全部语义) | **旧版本继续运行**,错误全量返回 |
| `unload-dev` | 从登记表移除一个 dev 加载的模块 | 仅 dev 加载项可移除 |

`load`/`swap` 的校验路径与生产完全一致(design-dylib-sdk §7.1 的六步),差别仅两处:第 1 步的清单由 dev 通道**现场合成**(以 .so 引导 blob 为源生成最小清单,不要求发布产物),第 3 步的内容寻址缓存复制跳过(直接以原路径加载)。

`swap` 失败保持现状是硬性要求:`update` 的 dry-run 拒绝、`DylibFactory::check_module` 拒绝、`LoadError` 任一发生,fiber 都不离开当前版本。开发者的下一次保存-编译-swap 不受影响。

### 3.3 与 `Loader` 的关系

dev 通道是 `rutis-dylib` 之上的一层壳(新 crate `rutis-dev`),不修改 `Loader::load` 的生产路径;dev 合成清单的代码与打包工具共享同一实现,避免两套清单逻辑漂移。

## 四、环境自描述

### 4.1 内容

`describe` 返回(快照 JSON):

- **fiber 列表**:id、插件 id/name/version、状态(Active/Pending/…)、injects、提供的服务键;
- **服务注册表**:服务键(TypeKey + 限定名)→ 提供者 fiber、版本代(provider_gen);
- **事件面**:已知事件键(含 D33 keyed 限定名)、各自的订阅者数量、订阅者 fiber;
- **依赖图**:谁注入谁,当前门控状态(谁在等谁)。

数据来源全部是现有结构:registry、bus 注册面、`RuntimeDiagnostics`/`DependencyDiagnostics`。新增的是聚合出口,不是新的记账。

### 4.2 动态接口与事件(核心场景)

全 plugin 体系下,其他插件带来的服务与事件类型**不在 SDK 接口 crate 里**(见 #52:那是官方控制的子集)。`describe` 是开发者获得"环境实际接口面"的唯一入口:

- **协议面**(插件经 #46–#48 接入):服务/事件带 schema(来自 #47 的接口定义),describe 直接给出 schema 引用与版本——这是动态接口的完整描述;
- **内核级 dylib 面**:Rust 类型无法在线导出,describe 给出**TypeKey 限定名 + 提供者插件 + 版本代**。开发者据此在自己的 crate 里引用同一个接口 crate 类型(若提供者已把类型放进去),或经协议面交互。类型不存在于任何共享 crate 时,该服务在 dev 视角标记为 `opaque`,只可见名字与代际。

这条边界要写实:**describe 做到"名字与拓扑永远可见,schema 在协议面完整,Rust 类型不承诺在线导出"**。不承诺的部分显式标记,不静默省略。

### 4.3 `watch`:活的参考

静态快照不够——开发依据还包括"事件实际怎么流"。`watch` 推送:

- 事件经过总线时的元数据(§5.1);
- 注册表增删(服务上下线、订阅变化);
- fiber 状态迁移(`FiberStatusChanged` 已有)。

开发者写插件时把 `watch` 挂着,等于对着活环境写代码。配套工具:`cargo xtask describe`(一次性导出)与 `cargo xtask watch`(持续流式打印)。

## 五、观测

### 5.1 事件流 trace

总线加可插拔 probe(不改变派发热路径,probe 挂在 emit/on 的注册面):

| 字段 | 说明 |
| --- | --- |
| key | 事件键(含 keyed 限定名) |
| origin | 发布者 fiber / 插件 id |
| listeners | 实际送达的订阅者(fiber / 插件 id) |
| ts / seq | 时间戳与单调序号 |
| payload | 默认仅大小与摘要;可显式开全文(§5.3) |

### 5.2 热换与依赖观测

- 每次 `load`/`swap`:版本、结果、失败步骤(design-dylib-sdk §7.1 六步的哪一步)、耗时;
- 依赖门控:等待、放行、驱逐、消费者重载的记录(诊断已有,补 dev 通道出口);
- 模块登记表:每插件 id 保留的版本、`Arc::strong_count`、内存占用(design-dylib-sdk §九)。

### 5.3 录制与回放

- **录制**(初版做):`watch` 的事件流按序落盘(含全文 payload,显式开启),开发者在真实环境复现一次问题,得到可离线分析的文件;
- **回放**(后续项,不在初版):按序重发录制的事件,喂给新版本插件。回放要求事件可重建与 payload 完整性,成本另评估,先不承诺。

## 六、编译对齐

本地编译的插件挂进真实宿主的前提:SDK_ID 与宿主内嵌值一致(design-dylib-sdk §5.4)。

1. **常规路径**:`hello` 返回宿主的 SDK_ID、artifact sha、toolchain。`cargo xtask dev` 在编译前先握手:工具链不匹配立刻报错并给出宿主的实际值——把"编完了才发现挂不上"消灭在编译前;
2. **可复现构建成立(V1)**:本地编译即对齐,循环最短;
3. **V1 不成立的退路**:宿主方提供同批构建(提交源码→CI 按宿主批次出 .so)。循环变长,但 `xtask dev` 的形态不变(构建步骤换成拉取远端产物)。

`cargo xtask dev` 一条命令串完整循环:

```
握手对齐 → watch 源码 → cargo build → swap → 流式回显宿主事件/日志/错误
```

## 七、安全边界

- dev 通道只监听本地 IPC,**不出网络**;
- 生产构建默认不编译进 dev 通道(crate feature + 运行时配置双开关);
- dev 通道能触发热换 = 本机代码执行入口,信任模型与 dylib 一方插件一致(同机可信);全部 dev 操作写审计日志;
- dev 加载项在登记表中显式标记 `dev: true`,与正式发布产物区分,`unload-dev` 只作用于 dev 项。

## 八、与既有工作的关系

- **#45 / PR #56(dylib SDK)**:提供 `Loader`、六步加载、`swap`/`update`、保留上限。本文档全部站在它上面;dev 通道不放宽其任何身份校验。
- **#46–#48(协议插件)**:dev 通道对协议插件同样开放(`load` 一个进程外插件 = 指挥宿主起代理 fiber)。协议面的 schema 描述由 #47 承接,§4.2 直接消费其结果。**协议插件开发同样必须在真实宿主上调试,本文档对两类插件同等适用。**
- **D32(config 热更)/ D33(动态事件键)**:`swap` 复用 update 语义;describe 的事件面依赖 D33 的限定名。
- **#41(迟到注册)**:热换安全的前置,对 dev 尤其重要(dev 是换代最频繁的场景)。
- **#12 / 诊断体系**:probe 与观测出口扩展 `RuntimeDiagnostics`,不另起炉灶。

## 九、dev 下的保留上限

design-dylib-sdk §九 的每插件 id 保留 N 个版本(默认 4)对开发循环太紧——连续调试很快顶满,顶满即 `RetentionExceeded`,被迫重启进程,摧毁"环境不重启"的整个前提。

- dev 模式下上限可配置,默认提高到 32(仅影响 dev 加载项的计数;登记表照常记录);
- 正式部署路径的上限不变;
- `status` 中可见当前保留量与距上限余量,逼近时提前提示,不要等到拒绝。

## 十、明确不做

- 远程/云端 dev 通道(跨机调试走共享 dev 环境 + 本地工具连其 socket,初版不额外设计);
- 事件回放(§5.3,列为后续);
- IDE/DAP 调试器协议集成——断点调试用 gdb/lldb 对着 dev 宿主做,本文档先把日志与事件观测做实;
- 热换之外的热改(改 SDK、改宿主自身):超出 dylib 设计边界,宿主或 SDK 变更仍然需要重新部署。

## 十一、实施步骤

1. bus probe 挂点 + `RuntimeDiagnostics` 聚合出口(事件流、服务/依赖快照)——不依赖 dylib,先行;
2. `rutis-dev` crate:本地 IPC 骨架,`hello`/`describe`/`status`/`watch`;
3. `load`/`swap`:dev 合成清单(与打包工具共享实现)、直连路径加载、失败保持现状;
4. dev 保留上限配置与登记表 `dev` 标记;
5. `cargo xtask dev`:握手对齐、源码 watch、build、swap、流式回显;
6. `cargo xtask describe` / `watch`;
7. 录制落盘(§5.3 初版);
8. 协议插件经 dev 通道装载的指令扩展(配合 #46)。

步骤 1 不依赖 #45,可立即启动;步骤 3 起依赖 dylib SDK 的 `Loader` 落地。

## 十二、验收标准

- [ ] 一条命令完成"改代码 → 宿主中生效":源码保存到宿主新版本运行,含编译在内可感知延迟 < 10 s(中型插件,增量编译);
- [ ] `swap` 失败时旧版本继续服务,错误信息含失败步骤与原因,与生产 `LoadError` 同源;
- [ ] SDK_ID/toolchain 不匹配在**编译前**被 `xtask dev` 拦下,错误信息给出宿主的实际值;
- [ ] `describe` 输出满足:新成员不看任何离线文档,仅凭 describe + watch 流就能写出第一个消费既有服务的插件并热换成功;
- [ ] 动态事件(非官方定义,来自其他插件)在 describe/watch 中可见:至少键名、提供者、订阅者;协议面事件带 schema 与版本;
- [ ] dev 通道不出网络,生产构建不含 dev 监听(feature 与配置双验证);
- [ ] dev 保留上限可配,`status` 可见余量,逼近上限有提示;
- [ ] 事件录制文件可离线按序查看(工具化,非裸 JSON);
- [ ] 协议插件可经 dev 通道装载与热换(依赖 #46)。

## 十三、待确认

1. **共享 dev 环境的形态**:一个团队共用一台常驻 dev 宿主(各自 swap 互不干扰?),还是每人一份本地完整部署?影响 `unload-dev` 与登记表隔离的设计,实施前定;
2. **事件 payload 全文抓取的量级**:watch 默认摘要、录制全文。真实环境事件吞吐多大、录制文件多久轮转,需要在第一个真实宿主上测;
3. **`opaque` 服务的开发路径**(§4.2):类型不在任何共享 crate 的 dylib 服务,开发者的正路是推动提供者把类型下沉到接口 crate,还是经协议面重导出?这是 #52 层级的延伸决策。
