# 远程插件：跨框架节点与对称协议（设计稿）

状态：设计稿，未实现。日期：2026-10-03。
依据：[网络栈：协议与通道解耦](design-protocol-channel-decoupling-2026-10-03.md)（下称"网络栈稿"）、[挂载 Cordis 插件：需求](requirements-protocol-plugins.md)、[兼容层设计](design-protocol-plugin-mount.md)、[rutis-loader 设计](design-rutis-loader-2026-10-02.md)、[Cordis 运行时插件化](design-cordis-runtime-plugin-2026-10-03.md)（#109）、[多语言决策记录](decision-multilang-2026-10-03.md)（#107，本文修订了其中几项，见 §十四）。
基准：`main` `d68471f`。
修订：第三版。第一版把网络连接桥接成本地 socket；第二版设计了"远端代理 + runner"；本版改为节点模型：远端本身就是一个插件框架实例，两端说同一份对称协议，中间是网络栈。桥本身也拆成了一组插件（§4.3）。

## 一、要解决什么

rutis 要支持远程插件，并且延续现在与 cordis 的对接方式和多语言的预设。跳出来看，整件事是：

```text
rutis ── 网络栈 ── rutis / cordis / pydis / …
```

- **两端都是完整的插件框架实例**（下文叫"节点"），各有自己的上下文、服务和插件，框架内核都不改。
- **中间的网络栈**只负责把消息送到，见网络栈稿。
- **两端说同一份对称的协议**，讲的是框架层面的事：服务、调用、事件、装插件。
- **远程插件**就是装在另一个节点上的插件。

现在的兼容层其实已经是这个形状的雏形："rutis ↔ 本地 socket ↔ cordis 节点"，只是角色、管子和对端种类都写死了（§三）。所以这是一次推广，不是另起炉灶。

不在本文范围：

- 网络栈本身（传输、分帧、鉴权、存活）：见网络栈稿。
- pydis 等新框架本身的实现：本文只规定它们要实现的契约（§十）。
- 独立于框架存活的服务（数据库、推理服务）：用普通客户端插件接入。
- 把远端代码下载到本机运行（插件分发）。
- 部署平台、插件市场、自动重启、操作系统沙箱（与需求 §8 一致）。

## 二、结论先说

1. **节点模型**。每个节点是一个框架实例，装上本框架的一组桥插件，就能和其他节点互联。没有代理、runner 这类特殊角色；宿主在本机拉起的子进程，也只是同一台机器上的一个节点。
2. **三层**：框架（不改）、协议（对称，所有框架实现同一份）、网络栈（只送消息）。
3. **协议对称**：两端用同一套帧和操作。任何一边都能导出服务、调用对方、请求对方装插件、转发事件。
4. **桥本身是插件化的**。它拆成传输、身份、链接、功能（导出、导入、代装、事件）几类插件，由 loader 按配置管理，生命周期走原生门控。会话层、通道实现、编码是库，由这些插件调用（§4.3）。
5. **策略就是"装了哪些功能插件"**。一条链接上没装导入插件，就不导入；没装代装插件，就不接受对方装插件。默认什么都不装，也就是什么都不允许，不需要另设一套权限表。"rutis 当老大"是一种部署方式：节点为 rutis 装代装插件，rutis 不为节点装（§六）。
6. **桥把对面的东西变成本地原生的东西**：导入插件把对方导出的服务注册成本地原生服务，照常 `inject`、照常门控；代装插件把对方请求的插件装在本地框架里，作为自己的子插件。
7. **链接插件提供 `Peer#<对端>`**，所有功能插件和放在该节点上的行都依赖它。链接一断，`Peer` 撤销，依赖方按原生门控停下：导入的服务撤销，代装的插件随代装插件卸载。失联即失去租约，不需要外部进程去杀。重连就是新会话，依赖方随 `Peer` 重新出现而重启。
8. **放置写在行名里：`peer:<id>/<插件>`**。插件由目标节点自己解析：cordis 节点解析 npm 包，rutis 节点解析内置插件或 dylib，pydis 节点解析 Python 模块。
9. **服务带着形状过界**。导出服务时附上语言中立的形状（方法名、同步还是异步、属性），由各框架从自己的声明自动导出（Rust 的 derive、TS 的 `.d.ts`、Python 的 `inspect`）。有了形状，任意两种框架之间不靠构建期代码生成也能互通；类型化绑定只是可选的语法糖。
10. **会话层改成真正对称**：调用号以节点 id 为前缀，全局唯一，多跳链路上的同步重入也能路由；Rust 侧也能导出对象、接收取消信号。
11. **节点可以组成树**：一个节点可以再连别的节点。在一条链接上导入、在另一条链接上导出，就是把服务转出去。第二版里的"远端代理"在这里有了正确的形态：它就是远端机器上的一个 rutis 节点。
12. **协议升到 v2，不兼容 v1**。现在所有端点都是我们自己的、同步发布的，两端一起升级；之后的新增能力走能力表。
13. **其他语言仍不进 rutis**（#107）。rutis 库里只维护 rutis 和 cordis 两侧的桥。协议对称、以线上格式为准，库外的框架（例如以后的 pydis）可以自己实现同一组桥插件接入，并通过同一套一致性测试。
14. **同步方法保持同步**；信任模型沿用：插件可信，网络和远端机器不完全可信。

## 三、现状：节点模型的雏形，但写死了

| 现在 | 在节点模型里是什么 | 写死或不对称的地方 |
| --- | --- | --- |
| `runner.mjs`：一个 Cordis Context；把 rutis 服务注册进去（`ctx.provide(name, hostProxy(...))`）；用导出 fiber 把 Cordis 服务导出给 rutis；`rows.*` 按需装插件；事件双向转发 | cordis 的桥 | 只能作为独立进程运行；只能被 rutis 控制；只接本地 socket；所有功能揉在一个脚本里 |
| `Process`、`Imports`、`Projection`、生成代码 | rutis 的桥 | "宿主服务"（`host:<名字>` 目标）和"投影服务"（槽位句柄通知）是两套机制 |
| 会话帧 | 对称协议的会话层 | 调用号前缀写死为 `rust:` / `node:`，各自只接受对方的前缀；Rust 不导出对象（"Rust does not export object references"），Node 也拒绝 Rust 的对象引用；Rust 不接收取消信号（"Rust receives no AbortSignal values"）；跨会话转发引用未实现 |
| 控制操作 | 框架操作 | 按角色分家：rutis→Node 只有 `mount`、`rows.*`、`emit`、`get`、`release`、`dispose`；Node→rutis 只有 `service`、`event`、`host:*` |
| `CordisRuntimePlugin` + `InteropResolver`（#109） | 本机默认节点：本机传输 + 链接插件 + 节点表的雏形。运行时已是插件，提供 `CordisRuntime` 服务，行依赖它；宿主服务按 `host_key` 注入；`RuntimeHandle` 供解析器查询 | 只有一个本机运行时，行不能选择挂到哪个运行时；对端只能是它自己拉起的 Node；宿主服务是运行时配置的一部分，改它要重启整个运行时 |
| 冻结的反方向（`server.rs`、`build/rust.rs`） | 被对称的桥取代 | 另一套机制 |

所以要做四件事：去掉会话层的不对称；把按角色分家的控制操作合成一套对称的框架操作；把 runner、`Process` 和 #109 的运行时插件推广成各框架里的一组桥插件；接上可替换的网络栈。

## 四、节点模型

### 4.1 组成

```text
                    rutis 节点 "main"（主）
           ┌────────────────────────────────────┐
           │ 内核 · loader · 插件 · 服务（不改）     │
           │ 桥插件：传输 · 身份 · 链接 · 功能        │
           └───────┬────────────────┬───────────┘
            网络栈（wss）      网络栈（本机 fd 3）
                   │                │
      ┌────────────┴─────┐   ┌──────┴──────────────┐
      │ rutis 节点 "mac"  │   │ cordis 节点 "js"     │
      │ 用户的 Mac         │   │ main 拉起的子进程     │
      │ 桥 · Rust 插件     │   │ 桥 · dsh 插件         │
      └────────┬─────────┘   └─────────────────────┘
        网络栈（本机 fd 3）
               │
      ┌────────┴─────────┐
      │ cordis 节点 "jxa" │
      │ mac 拉起的子进程   │
      │ 桥 · 自动化插件    │
      └──────────────────┘
```

### 4.2 三层

| 层 | 管什么 | 每个框架怎么实现 |
| --- | --- | --- |
| 框架 | 插件、服务、依赖门控、生命周期 | 各自的内核，不改；桥是其中的一组普通插件 |
| 协议 | 会话（调用、引用、取消、调用链、错误）+ 框架操作（服务、插件、事件） | 按本文 §五 实现的库；可以自己写，也可以绑定 Rust 的实现（§十） |
| 网络栈 | 传输、分帧、鉴权、存活、关闭原因 | 按网络栈稿实现的库：Rust 是 `rutis-channel`，JS 在 cordis 桥的包里 |

### 4.3 桥：一组插件

```text
传输插件（本机子节点 / WebSocket / …）    身份插件
                  ↘                      ↙
         链接插件（每个对端一个实例）→ 提供 Peer#<对端>
           ↙          ↓          ↓          ↘
       导出插件     导入插件     代装插件     事件插件
```

| 插件 | 做什么 | 依赖 | 提供 |
| --- | --- | --- | --- |
| 传输（`rutis-bridge/local`、`rutis-bridge/websocket`，测试用 `rutis-bridge/memory`） | 建立连接：拉起本机子节点、拨号、监听。内部是网络栈稿的连接器 | — | `Transport#<种类>` |
| 身份（`rutis-bridge/identity`） | 本节点的凭据；把对方的凭据映射成节点 id | — | `Identity` |
| 链接（`rutis-bridge/link`，每个对端一个） | 经传输建立会话、完成握手；作为拨号方时负责退避重连 | `Transport#<种类>`、`Identity` | `Peer#<对端>` |
| 导出（`rutis-bridge/export`） | 把列出的本地服务公告给对端，换值、撤销时随时更新 | `Peer#<对端>`、被导出的服务 | — |
| 导入（`rutis-bridge/import`） | 把对端公告的、列出的服务注册成本地原生服务 | `Peer#<对端>` | 导入的服务 |
| 代装（`rutis-bridge/host`） | 接受对端的 `plugins.*`，在本地装载；装出来的插件都是它的子插件 | `Peer#<对端>` | — |
| 事件（`rutis-bridge/events`） | 按列出的事件名和方向转发 | `Peer#<对端>` | — |

- **命名**：英文统一用 peer（对等方），因为协议对称，两端互为对等方。不用 node，是为了避开 Node.js：`node:` 是 Node 内置模块的前缀（例如 `node:fs`），仓库里的 `node` 也一直指 Node.js。中文仍然叫"节点"。
- **各框架用同样的名字和配置项**：rutis 里是内置插件的名字，cordis 里是桥包的子路径，pydis 里是模块名。配置写法因此在各框架间通用。
- **插件与库分工**：插件负责配置、生命周期和组合，库负责机制。一条链接的会话只归它的链接插件所有；功能插件经 `Peer` 使用会话，并登记自己负责处理的框架操作（随插件卸载自动注销）。

```rust
// 链接插件提供的服务（示意）
pub struct Peer { … }

impl Peer {
    pub fn id(&self) -> &PeerId;
    pub fn session(&self) -> &Session;   // 调用、引用
    /// 功能插件登记自己负责的框架操作（例如代装插件登记 "plugins.*"）。
    pub fn serve(&self, ops: &str, handler: Arc<dyn OpHandler>) -> Disposer;
}
```

- **未开的功能**：对端请求了这条链接上没装对应功能插件的操作，收到"本链接未提供此功能"的错误。这只是一次调用失败，会话照常继续。
- **依赖由配置决定**：功能插件依赖哪个对端的 `Peer`、链接插件依赖哪种传输，都写在配置里。而 rutis 的依赖声明在装载时就固定（内核 D32f），所以这些插件在 apply 里按配置生成一个声明了依赖的内层插件，原生门控照常生效。`runner.mjs` 里带 `inject` 的行包一层 `row:` 门控 fiber，用的就是这种写法。
- **组合插件**：`rutis-bridge/peer` 用一份简短的配置（对端、传输、地址、导出、导入、事件、是否代装）展开出上面那组插件，作为它的子插件。常见场景用它；需要细调时，再改用单独的插件。

### 4.4 链接断开时谁来收尾

| 发生了什么 | 结果 |
| --- | --- |
| 链接建立、握手通过 | 链接插件提供 `Peer`；功能插件启动：导出插件公告服务，导入插件注册服务，代装插件开始接受装载 |
| 对端撤销一个服务 | 导入插件撤销对应的本地服务；依赖它的插件按原生规则停下 |
| 链接断开（网络、心跳、对方进程结束） | `Peer` 撤销，依赖它的功能插件停下：导入的服务撤销，代装的插件随代装插件卸载；放在该节点上的行进入等待 |
| 重连 | 新会话、新的 `Peer`；功能插件重启，控制方按期望状态重新装载 |
| 改策略（例如改导出列表） | 只重启对应的功能插件，链接不断 |

两端各自按这张表收尾，各自写明自己看到的原因。

本机子节点的进程还由父节点的传输插件持有：进程退出状态作为链接的关闭原因（网络栈稿 §七）；进程不自动重启（需求 §7、#71）；子节点和父节点的链接结束后，子节点卸载全部插件并退出（现在 `runner.mjs` 末尾的 `dispose()` 就是这样做的）。

### 4.5 树形组合

节点可以再连别的节点。上图里，"mac" 是用户 Mac 上的 rutis 节点，它在本机拉起 cordis 子节点 "jxa" 跑自动化插件，自己再经网络连到 "main"。"main" 要用 "jxa" 的服务，有三种方式：

- 在 "mac" 上，用 jxa 链接的导入插件把服务导进来，再用 main 链接的导出插件导出去（需要跨会话转发引用，§5.1）；
- "main" 请求 "mac" 装一个 rutis 插件，由这个插件去用 "jxa" 的服务；
- 协议是对称的，两个节点也可以按部署直接建链接。

第二版里"远端跑一个代理，拉起 runner 并转发"的需求，在这里就是"远端跑一个 rutis 节点，装上传输插件、链接插件和代装插件"，不需要另造角色。

## 五、对称协议 v2

### 5.1 会话层

帧语义沿用[兼容层设计 §3](design-protocol-plugin-mount.md)，改成对称：

- **握手**：`hello { version: 2, id, framework: { name, version }, capabilities }`，双方都发。经网络的链接，`id` 必须等于连接器验证过的身份（网络栈稿 `ChannelInfo`），否则断开；本机子节点的 id 由父节点在启动时指定。
- **调用号**：`<节点 id>:<n>`，每一端只接受以对方节点 id 开头的调用号；引用的 `origin` 同理。节点 id 在一个部署里唯一，只含小写字母、数字和 `-`。调用号因此全局唯一，多跳链路上的同步重入也能按 `path` 路由，"两个 Node 端都有 `node:1`"的问题不再存在。
- **引用**：函数、异步结果、对象三种引用，两边都能导出。对象引用第一次授予时带上形状（§5.3）。
- **取消**：`cancel` 在两边都能落到被调方：JS 是 `AbortSignal`，Rust 是取消令牌，Python 是它的等价物。
- **跨会话转发**（能力 `forwarding`）：把会话 A 的引用交给会话 B 时，包成本地对象再导出，按（会话，引用号）保持身份；B 释放时连带释放 A 中的引用。树形组合需要它。

### 5.2 框架操作

框架操作仍走会话层的 `invoke`（目标为空），只是改成带命名空间的操作名。**每个操作两个方向都能发；收方由负责它的功能插件处理，没装这个插件就拒绝**（§4.3）。

| 操作 | 含义 | 由谁发、谁处理 | 取代现在的 |
| --- | --- | --- | --- |
| `services.announce { name, service, shape, version }` | 公告一个可导入的服务；`service` 是一个对象引用 | 导出插件发，导入插件处理 | Node→rutis 的 `service` 槽位通知；`mount` 里的 `provided` 宿主服务表 |
| `services.withdraw { name, version }` | 撤销公告 | 同上 | 同上 |
| 对象调用帧（带方法名的 `call`、`get`） | 调用服务方法、读属性 | 会话层直接处理 | `host:<名字>` 目标；按句柄的 `invoke`，以及 `get` 控制操作 |
| `plugins.describe(插件) → { schema, version, integrity }` | 查询插件 | 代装插件处理 | `rows.schema` |
| `plugins.load(key, 插件, config, isolate, inject)`、`plugins.update(key, config)`、`plugins.unload(key)` | 代对方装、改、卸插件 | 代装插件处理 | `rows.*`、`mount` |
| `events.forward { name, args }` | 转发通知事件；收方以 `parallel` 发出，等监听结束后返回 | 事件插件发，也由事件插件处理 | `event`、`emit` |

- **服务直接以对象引用公告**，原来的句柄体系并入引用体系：换值就是公告一个新引用，旧代理释放时按引用计数归还。实现时要保留兼容层设计 §4 的两条约束：换值通知按 `version` 排序；Cordis 服务要经导出 fiber 读取，调用产生的 effect 归导出 fiber（导出插件就承担这个导出 fiber 的角色）。
- 事件仍只转发通知类事件；同一条链接上，一个事件名只能有一个转发方向，防止回环（沿用现规则）。

### 5.3 服务形状

```json
{
  "methods": { "get": "sync", "put": "async" },
  "properties": ["size"],
  "objects": { "Handle": { "methods": { "close": "async" } } }
}
```

- 形状告诉调用方一个方法是同步还是异步。例如 cordis 消费 rutis 的服务时，代理据此决定阻塞等待，还是返回 Promise。
- 各框架从自己的声明自动导出形状：Rust 在导出的 trait 上加 derive；TS 用现有生成器从 `.d.ts` 生成形状清单，随节点的项目分发；Python 用 `inspect`。
- 没有形状的成员不过界，公告时报出来（与现在"不支持的成员在构建时警告"一致）。不靠运行时探测，因为 JS 里返回 Promise 的普通函数看不出是异步的。

### 5.4 能力与版本

- 能力表描述**实现能做什么**：`objects`、`signals`、`reentrant-sync`、`plugins`（能代装插件）、`events`、`volatile`、`forwarding`。**允不允许做**由装了哪些功能插件决定，不写在能力表里。
- 缺少需要的能力时，在使用前拒绝并写明缺哪一项，不降级。
- 不支持 `reentrant-sync` 的实现，在同步等待期间收到属于这条调用链的反向调用时，必须立即回 `SyncWaitCycle`，不得排队，因为排队就是死锁。
- v2 是一次干净的切换，不保留 v1。以后版本号只为不兼容的变更而升，新增能力走能力表。

## 六、策略：装了哪些功能插件

两个节点的配置（示意，写成 loader 的行）：

```yaml
# 节点 main
- name: rutis-bridge/websocket
  config: { listen: "127.0.0.1:7443" }          # 前置反向代理终止 TLS
- name: rutis-bridge/identity
  config: { peers: { mac: "sha256:…" } }         # mac 的 token 摘要
- name: rutis-bridge/link
  config: { peer: mac, transport: websocket, accept: true }
- name: rutis-bridge/export
  config: { peer: mac, services: [aimux, systemPrompt] }
- name: rutis-bridge/import
  config: { peer: mac, services: [notes] }
- name: rutis-bridge/events
  config: { peer: mac, out: [credentials/record-updated] }
# main 没给 mac 装代装插件：mac 不能往 main 装插件

# 节点 mac
- name: rutis-bridge/websocket
- name: rutis-bridge/identity
  config: { token_file: /etc/rutis/mac.token }
- name: rutis-bridge/link
  config: { peer: main, transport: websocket, dial: "wss://main.example.com/rutis" }
- name: rutis-bridge/export
  config: { peer: main, services: [notes] }
- name: rutis-bridge/host
  config: { peer: main }                          # 接受 main 装插件，只限本节点已安装的
```

- **默认什么都不装，也就是什么都不允许**。权限按连接器验证过的节点 id 生效，和谁先拨号无关。
- **"rutis 当老大"就是上面这种配置**：期望状态在 "main" 的 loader 里，节点为 "main" 装了代装插件。
- **开了代装，就等于把这个节点交给对方管**：对方能装你已安装的任何插件，包括导出插件，也就能拿到你的任何服务。代装只应该为信任的节点开。
- **改策略是热的**：改导出列表只重启导出插件，链接和其他功能不受影响。
- **导入的服务不能重名**：两个导入插件导入同名服务时，后启动的那个以冲突失败，错误写明来自哪两条链接。

## 七、rutis 侧：远程插件怎么用

- **`Peer`**：由链接插件提供，键为 `TypeKey::keyed_dynamic::<Peer>(id)`；链接结束就撤销。内核和 loader 核心都不改。
- **放置**：行名写成 `peer:<id>/<插件>`。目标节点必须为本节点装了代装插件，否则行以"节点 mac 没有为 main 开代装"失败。不带前缀的 npm 名照旧落在默认节点。
- **`PeerResolver`**：
  - 链接插件把会话登记到一张节点表里，解析器经这张表查询（解析器没有 ctx，用不了服务）。这就是 #109 的 `RuntimeHandle` 推广到多个对端；
  - 节点在线时，用 `plugins.describe` 取得 schema 和版本；
  - 节点离线时照样返回解析结果，只是 `schema: None` 并标记离线；行作为依赖 `Peer` 的 fiber 进入等待，而不是显示为 Unresolved（与 #109 的 `InteropResolver` 在运行时未就绪时的做法一致）；
  - 链接建立后、提供 `Peer` 之前，先用 loader 的公开 API（`entries()` + `reload(id)`）修正离线时解析的、或版本已变的行，再放行。这些行此时都在等待，`reload` 只替换解析结果、不触发启动，所以每行只启动一次。
- **`PeerRow`**：行插件 apply 时经 `Peer` 发 `plugins.load`，disposer 发 `plugins.unload`；如果链接已断，视为成功，因为对端已随代装插件卸载。只改易变字段的更新走 `plugins.update`。
- **导入的服务**：由导入插件注册，同时登记进 loader 的服务名目录，Rust 行可以 `inject` 它们。生成的类型化绑定包在这些无类型代理外面。
- **默认节点**：由 `rutis-bridge/local` 传输插件拉起的本机 cordis 子进程，加上一条到它的链接。子节点启动时只带三样插件：本机传输、到父节点的链接、为父节点开的代装。导出、导入、事件这些功能插件，由父节点按需代装上去。生成的类型化挂载（例如 rutis-dsh 的 web 和 agent）改为在这套插件上组合出来的语法糖。
- **配置**：在 "main" 求值（包括 `!!js` 表达式），在目标节点解释。表达式读到的环境变量、路径是 "main" 的，插件实际读写的环境是节点的。
- **其他规则**：`isolate` 的共享标签只在同一个节点内生效；代装插件默认拒绝 `file:` 形式和绝对路径的插件名（默认节点除外，因为 dsh profile 会把相对路径改写成 `file://` URL）。
- **rutis-dsh**：profile 里的行可以改名放到节点上。彼此有 Cordis 依赖的插件，放在同一个节点，或者靠树形转发（N4）。
- **#109 是起点**：`CordisRuntimePlugin` 已经把本机这一半做成了插件：运行时提供服务、行依赖它、进程崩溃时撤销服务、不自动重启。推广的方向是：`CordisRuntime` 变成 `Peer#<id>`；宿主服务列表交给导出插件，可以单独修改而不重启运行时；`RuntimeHandle` 变成节点表；行可以用 `peer:` 选择挂到哪个节点（#109 设计 §3 留待"有需求时再做"的那一项）。

## 八、同步、取消与故障

**同步方法保持同步**。放置是配置，方法形状是类型的一部分，不能随放置改变。代价是每次同步调用至少阻塞一个 RTT。死链接由网络栈的心跳兜底；同步调用的次数和耗时作为指标暴露，不加超时。需要截止时间的调用方，仍按边界规则 8 改用异步方法并自行设置超时。

取消：丢弃 future 即取消，`cancel` 落到被调方的取消信号上，两个方向都一样。

| 情况 | 结果 |
| --- | --- |
| 网络断开、心跳超时、对端机器宕机 | 两端的 `Peer` 撤销，依赖方按 §4.4 收尾；在途调用以 `Transport` 失败并写明原因，结果未知、不重试 |
| 本机子节点崩溃 | 父节点的传输插件以退出状态为原因结束链接；不自动重启 |
| 对端有序关闭 | 关闭原因随链接带到对端 |
| 同一节点 id 再次连上 | 新链接接管旧链接，旧会话以 "replaced by a new connection" 结束 |
| 新会话 | 旧引用一律报 "session closed"；功能插件重启，控制方重新装载，取得新对象 |

谁拨号由部署决定：通常是工作节点拨主节点，方便穿过 NAT；重连和退避由拨号方的链接插件负责（网络栈稿 §九）。

## 九、安全

信任模型：**插件可信，网络和远端机器不完全可信**（沿用 #49 的判断，不防恶意插件）。

| 方面 | 规则 |
| --- | --- |
| 传输 | 非回环地址只走 TLS，可以由前置反向代理终止 |
| 身份 | 每个节点一份凭据（token 或客户端证书），由身份插件提供和校验，得到节点 id；握手里的 `id` 必须与之一致 |
| 授权 | 装了哪些功能插件就是授权（§六），默认什么都不装。协议是对称的，所以两个方向都要防：被攻破的工作节点不能往主节点装插件，因为主节点没为它装代装插件 |
| 代装 | 只能装本节点已安装的插件；开代装等于交出这个节点的控制权 |
| 资源 | 消息大小上限（网络栈稿 §九）；不设调用数、引用数配额 |
| 数据外流 | 放到远端的行，其配置（求值后，可能含密钥）会发到远端机器 |

被攻破的一方能做的，限于对端为它装了的功能插件允许的事：调用对方导出的服务；在对方开了代装时，装对方已安装的插件。

## 十、其他框架：要做什么才能接入

按 #107，rutis 库里只做 rutis 和 cordis 两侧。下面是库外的框架接入时要实现的契约，rutis 不为它们维护代码。

1. **网络栈**：至少实现本机通道（继承 fd 或 Unix socket）。要能被远程直连，再实现 WebSocket 绑定（网络栈稿 §九）。
2. **协议 v2**：会话层和框架操作（§五）。
3. **桥插件组**：按 §4.3 实现同一组插件，名字和配置项与其他框架保持一致。
4. **形状导出**：从本语言的声明自动生成（§5.3）。
5. **通过协议一致性测试**（§十一）。

各框架的情况：

- **rutis**：Rust 插件可以放在远端的 rutis 节点上（内置插件，或 Linux 上的 dylib）。rutis 之间的类型化访问，可以共享 trait 所在的 crate，再用 derive 生成代理。
- **cordis**：现有的 `@arcships/rutis-interop` 拆成一组普通的 cordis 插件。任何 cordis 应用（例如在另一台机器上跑的完整 dsh）在配置里加上这几行就是一个节点。宿主拉起的子进程只是一个预装了三样桥插件的最小 cordis 应用。cordis 消费 rutis 服务时，可以从 Rust 的形状生成 `.d.ts`（冻结的 `build/rust.rs` 做过类似的事）。
- **pydis**（库外；#107 定为"有真实插件时再说"）：如果要做，同步等待期间的重入可以用"I/O 线程 + 主线程按调用链执行反向调用"实现，与 Node 侧现在的做法同构。#107 引用的 runner 移植调研（`plan/analysis/multilang/python.md`）可以直接参考。
- **PowerShell、Bash、AppleScript**：#107 决定不在 rutis 内做。如果在库外做成节点，可以只实现链接、导出这几样插件，在能力表里如实声明做不到的；不想实现网络栈的，就做成本机子节点，挂在同机的 rutis 节点下面（§4.5）。

**实现策略**：协议以线上格式为准，不以某个库为准。一个框架可以按规范自己实现会话层和网络栈，也可以绑定 Rust 的实现（Node 用 N-API，Python 用 PyO3），只要通过一致性测试即可。绑定的好处是复杂的会话逻辑只有一份；代价是要为各个平台发布预编译的二进制。pydis 走哪条路，由它自己决定。

## 十一、协议一致性测试

一个 Rust 写的测试驱动扮演对端，经本机通道（以及 WebSocket，如果被测节点支持）连上被测节点。被测节点按 §4.3 装好标准的桥插件，两个方向都测：

- 公告带形状的服务，被测节点导入后能按原生方式使用（由被测框架的固定测试插件报告）；
- 导入被测节点的固定测试服务：同步和异步调用、三种引用的往返与释放、取消落到被调方、错误对象图（含 `AggregateError`）；
- 用 `plugins.load` 装被测框架的固定测试插件：回显、可换值的计数器、回调、启动即失败；
- 事件转发；
- 链接断开后，导入的服务撤销、代装的插件卸载（由固定测试插件报告自己的清理）；
- 策略：没装导出插件时对端看不到服务；没装代装插件时 `plugins.load` 被拒；卸掉导出插件后服务撤销，但链接不断。

每个框架随一致性测试提供同一套固定测试插件的本语言版本。先对 rutis 节点（进程内经 memory 通道，以及独立进程）和 cordis 节点跑通；pydis 接入时同样要通过。

## 十二、不采用的方案

| 方案 | 不采用的原因 |
| --- | --- |
| 一个大的桥插件（本版初稿） | 策略只能另写一套权限配置；改策略就得重连；加一种传输要改桥本身；不能由 loader 分层、覆盖、热改 |
| 代理 + runner（第二版） | 远端成了只会转发的特殊角色；远端的插件不在一个完整框架里，也不能主动使用别的节点的服务。节点模型里，它就是"远端的一个 rutis 节点" |
| socketpair 桥接、按顶层字段分流（第一版） | 见网络栈稿 §十四 |
| 保留主从角色的协议（`rust:` / `node:`） | rutis 连 rutis、cordis 消费 rutis 服务都没法表达；控制方向应该由装了哪些功能插件决定 |
| 每条链接自动导出全部服务 | 违背最小授权；不同链接导入同名服务时会冲突 |
| 运行时探测方法是否异步 | 不可靠：JS 里返回 Promise 的普通函数看不出来 |
| 会话恢复、失联宽限期 | 收益小，而且违背"插件在谁的上下文里，就由谁管" |
| 远程时把同步方法生成为异步 | 放置是配置，类型不能随放置变化 |
| gRPC / protobuf、HTTP 请求/响应 | 需要 IDL，违背"不手写契约"；不对称，反向调用和同步重入难以表达 |

## 十三、分阶段

| 阶段 | 内容 |
| --- | --- |
| D1 | 网络栈稿 D1：通道层纯重构，线格式不变 |
| N1 | 会话层对称化：节点 id 调用号、Rust 导出对象、取消令牌、对象形状。现有测试改用新调用号后全部通过 |
| N2 | 框架操作 v2 与桥插件组（rutis、cordis 两侧）：链接、导出、导入、代装、事件插件和 `rutis-bridge/peer` 组合插件；本机传输插件与默认节点（从 #109 的 `CordisRuntimePlugin` 推广而来）；`services.*` 取代 `host:` 和槽位通知，`plugins.*` 取代 `rows.*` 和 `mount`；生成代码改为建立在这组插件上的语法糖 |
| N3 | 网络栈稿 D2–D3；WebSocket 传输插件与身份插件；rutis 侧的 `peer:` 放置、`PeerResolver`、`PeerRow`；远程 cordis 节点、远程 rutis 节点 |
| N4 | 树形组合：跨链接转出服务（转发引用）、多跳同步重入 |
| N5 | 协议一致性测试套件；pydis 接入 |
| 以后 | 二进制编码；从 Rust 的形状生成 `.d.ts`；Windows 上的通道 |

N3 的验收（远程插件可用）：

- 远程 cordis 节点上的行：装载、改配置（易变字段就地提交，其他字段重启）、卸载；"main" 导出的服务被节点上的插件原生 `inject`；节点导出的服务被 rutis 行 `inject`；同步、异步、双向回调、取消都能工作。
- 远程 rutis 节点上的 Rust 插件同上。
- 半开连接在心跳超时内被发现，两端的 `Peer` 撤销并按 §4.4 收尾；重连后行只启动一次，旧引用报 "session closed"。
- 本机子节点崩溃：错误带退出状态，不自动重启。
- 策略生效：没装导出插件的服务对端看不到；没装代装插件时 `plugins.load` 被拒；改导出列表不断链；节点 id 与凭据不符时连接被拒。
- 在被同步调用阻塞的 `current_thread` 运行时上，经远程节点回调宿主的同步调用能够完成。

## 十四、与现有需求和决策的关系

- **"rutis 当老大"保留**，作为默认的部署方式（§六），不再是协议里的角色。
- **需求 §8**：#107 已写明"其他语言不在 rutis 内做"，本设计保留这一条；要改的是把"远程 peer"移入范围。"重连恢复""自动重启"仍然不做。
- **#71 不变**：不提供单独的强制终止；同一节点内的插件共享进程和故障；卸载、终止、超时分别报告；进程外运行不是沙箱。
- **内核与 Cordis 不改**：桥插件只用各框架的公开 API。
- **冻结的反方向**：`server.rs`、`build/rust.rs` 保持冻结、不扩展。对称的桥落地后（N2），"cordis 应用使用 rutis"有了正式做法，届时建议删除那套代码。这一步需要你拍板。
- **双核决策不变**：不嵌入 JS 引擎；JS 插件仍在真实的 Node 和 Cordis 里运行。

### 与 #107 决策记录的关系

#107 第五节的结论，有的保留，有的被本设计修订。修订的几项，#107 不做的理由是"只是给其他语言铺路"；本设计要做它们，理由是远程 peer 和协议/通道解耦，与其他语言无关。

| #107 的结论 | 本设计 | 理由 |
| --- | --- | --- |
| PowerShell、Bash、AppleScript/JXA 不在 rutis 内做 | 保留 | — |
| Python（min_cordis）库外、以后再说 | 保留：rutis 不做，协议允许库外实现接入 | — |
| 反方向（Cordis 宿主挂载 rutis）继续冻结 | 旧实现继续冻结；协议本身不再区分方向，cordis 节点能否使用 rutis 的服务、能否往 rutis 装插件，由 rutis 为它装了哪些功能插件决定，默认都不开 | rutis 连 rutis、远程 peer 的服务双向导入，都需要对称的会话层 |
| 中立接口描述不做 | 修订：做服务形状（§5.3），只描述同步/异步和属性，不做代码生成 | 对称的动态导入要知道方法是同步还是异步，rutis 连 rutis 也需要 |
| 启动方式抽象不做 | 修订：做协议与通道解耦（网络栈稿） | 远程 peer 要走网络 |
| `node:` 前缀放宽不做 | 修订：调用号以节点 id 为前缀（§5.1） | rutis 连 rutis 时两端都不是 `node`；多跳路由需要全局唯一的调用号 |

修订的几项需要在评审时确认；确认后，在 #107 的决策记录里追加一节，说明这些结论被本设计修订。

## 十五、风险，以及以后可以回头改的取舍

| 取舍 | 代价 | 什么时候重新考虑 |

| 桥拆成多个插件 | 配置项变多，排错时要看几层插件的状态 | 常见场景用组合插件 `rutis-bridge/peer`；内核的 Pending 原因会写明缺的是哪一层 |
| 形状是必需的 | 没有形状的成员不能跨节点使用 | 需要时在插件的声明里补上，不引入运行时探测 |
| 每种语言都要实现协议 | 复杂的会话逻辑会有多份 | 一致性测试兜底；也可以绑定 Rust 的实现（§十） |
| 失联即卸载 | 网络抖动时，远端插件会重启 | 真有插件需要扛住短暂断线时，再评估宽限期 |
| 放置写在行名里 | 换节点会重建 fiber | 需要跨节点迁移并保持身份时，再加独立的放置字段 |
| 树形转发 | 多一跳的开销和实现复杂度 | 放在 N4 单独做，先满足直连 |
