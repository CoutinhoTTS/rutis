# 挂载 Cordis 插件：崩溃与性能实验

2026-09-29，Linux、16 核、Node 26.8.1、Cordis 4.0.4。装置在 [`examples/interop-experiments`](../examples/interop-experiments)，插件是 `interop/node/test/fixtures/fragile.ts` 和 `bench.ts`，通过生成的绑定按正常方式挂载。

```sh
cargo run -p interop-experiments --bin crash
cargo run --release -p interop-experiments --bin bench
```

## 1. Node 进程崩溃或卡住

每个场景都在 rutis 侧挂载插件，再挂一个 `injects` 该服务的 rutis 插件作为使用方。

| 场景 | 进行中的调用 | 之后的调用 | 挂载插件 / 服务 / 使用方 | 卸载挂载 |
| --- | --- | --- | --- | --- |
| 空闲时 SIGKILL | — | 立即 `Transport("peer disconnected")` | 仍是 Active / 仍注册 / 仍 Active | 返回错误；使用方此时才停止 |
| 同步调用中 `process.exit(17)` | 立即同上错误 | 同上 | 同上 | 同上 |
| 异步调用等待中 SIGKILL | 约 6 ms 后同上错误 | 同上 | 同上 | 同上 |
| 定时器里抛异常 | — | 同上（整个 Node 进程退出） | 同上 | 同上 |
| 未处理的 Promise 拒绝 | — | 同上（整个 Node 进程退出） | 同上 | 同上 |
| 同步方法占住事件循环 2 s | 异步调用可用 `timeout` 取消；同步调用一直等到循环恢复 | 恢复后正常 | 正常 | 正常 |
| 进程冻结（SIGSTOP） | 异步调用可用 `timeout` 取消 | — | — | 一直等待，恢复后才完成 |
| 插件 `apply` 中退出 | — | — | 挂载约 137 ms 后 Failed，错误为 `peer disconnected` | — |
| 崩溃后卸载、重新挂载 | — | 正常 | 新挂载 Active，使用方重新启动 | — |

结论：

1. **崩溃后 rutis 侧没有感知**。Node 进程已经退出，但挂载插件仍是 Active，服务仍然注册，依赖它的 rutis 插件继续运行，只是每次调用都失败。这与 rutis 的依赖门控不一致：提供方不在了，使用方应当停下来等待。只有应用主动卸载挂载后，使用方才停止；重新挂载后一切恢复。
2. **调用不会挂死**。进程退出后，进行中和之后的调用都立即（毫秒级）返回 `Transport` 错误。
3. **诊断信息不足**。错误只有 `peer disconnected`，不包含退出码或信号；卸载时的错误同样丢失了退出状态。唯一的线索是继承到 rutis 进程 stderr 的 Node 输出（例如异常堆栈）。
4. **Node 默认规则：一个插件未捕获的异常或拒绝会结束整个 Node 进程**，同一挂载（同一组）里的其他插件一起停止。这与原生 Node 应用的行为一致，只是影响范围限定在该挂载内。
5. **卡住时只有异步调用能自保**。同步调用没有超时，会阻塞调用线程直到 Node 恢复；卸载也没有超时，进程冻结时会一直等待，没有强制结束的兜底。

以上缺口都可以在兼容层补上，不需要改动 rutis 内核：监听连接断开后撤销投影的服务（使用方按原生规则回到等待），错误中带上退出码 / 信号；卸载超时后强制结束 Node 进程；同步调用可选超时。

### 修复后（结论 1、3）

连接断开后兼容层撤销所有投影的服务；错误和卸载结果带上进程的结束方式。重跑后：

| 场景 | 调用错误 | 服务 / 使用方 |
| --- | --- | --- |
| 空闲时 SIGKILL | `Cordis process exited with signal: 9 (SIGKILL)` | 已撤销 / 停止等待（Pending） |
| 同步调用中 `process.exit(17)` | `Cordis process exited with exit status: 17` | 同上 |
| 异步调用等待中 SIGKILL | `… signal: 9 (SIGKILL)`，约 4 ms | 同上 |
| 定时器异常 / 未处理拒绝 | `… exit status: 1` | 同上 |
| `apply` 中退出 | 挂载 Failed：`… exit status: 3` | — |

挂载插件本身仍为 Active，只是不再提供服务；应用卸载后重新挂载即恢复。回归测试：`crates/rutis-interop/tests/projection_lifecycle.rs::a_crashed_process_withdraws_its_services`、`process_exit.rs`。结论 5（卡住时没有超时）尚未处理。

## 2. 调用开销

release 构建，每项预热后测量。

| 操作 | 均值 | p50 | p99 |
| --- | --- | --- | --- |
| 挂载（启动 Node + apply） | 129 ms | 124 ms | 128 ms |
| 同步方法，无参数 | 46 µs | 43 µs | 86 µs |
| 异步方法，无参数 | 71 µs | 71 µs | 125 µs |
| 回传字符串 1 KiB | 55 µs | 53 µs | 169 µs |
| 回传字符串 64 KiB | 265 µs | 241 µs | 680 µs |
| 回传字符串 1 MiB | 3.9 ms | 3.8 ms | 4.6 ms |
| 接收 10 行记录 | 77 µs | 75 µs | 106 µs |
| 接收 1,000 行记录 | 2.7 ms | 2.7 ms | 3.1 ms |
| 接收 10,000 行记录 | 23 ms | 23 ms | 25 ms |
| 发送 1,000 行记录 | 1.6 ms | 1.6 ms | 2.0 ms |
| 活对象读属性 | 32 µs | 30 µs | 57 µs |
| 活对象调方法 | 51 µs | 47 µs | 121 µs |
| 回调（Node 调 Rust 闭包） | 43 µs / 次 | | |

吞吐（无参数调用）：

| 方式 | 次/秒 |
| --- | --- |
| 异步，串行 | 11,200 |
| 异步，8 并发 | 62,800 |
| 异步，64 并发 | 65,000 |
| 同步，8 线程 | 87,300 |

结论：

1. **每次跨边界约 30–70 µs**。服务级调用（读写凭据、文件、工作区）可以忽略这个开销；循环里的细粒度调用会累积，例如逐条调用 10,000 次约 0.5 s，应改成批量方法或在一次调用里完成。回调同理，每次回调也是一次往返。
2. **并发时吞吐约 6.5 万次/秒**，单个 Node 进程的事件循环是上限。
3. **大批结构化数据偏慢**：10,000 行约 23 ms，约 2.3 µs/行，同等大小的单个字符串只需约 4 ms。拆分测量显示，Node 侧编码 10,000 行约 6 ms，其中 `JSON.stringify` 只占 0.7 ms，其余是逐个元素检查是否含有引用。这是兼容层自身的实现开销，有优化空间（一次遍历判定整块数据），目前没有做。
4. **挂载约 125 ms**，主要是启动 Node 和加载 TypeScript，适合应用启动时挂载，不适合按请求临时挂载。
