# #62 / #63 事件派发性能样本

日期：2026-09-27。实现分支：`feat/event-keys-and-sync-dispatch`，rutis 0.4.0（该开发版本最终以 0.5.0 发布）；旧版基线为 main `603f8220b049c6ad26e82f258fd72f214b8575fe`（0.3.0）。

环境：Linux x86_64，Intel Core Ultra X7 358H，rustc 1.98.1，release 默认优化，Tokio 两个工作线程。以下样本将进程固定到 CPU 0；没有固定 CPU 频率，也没有统计置信区间，不能把几 ns 的差异当成跨机器的结论。

## 运行

```sh
# 本分支接口：普通同步监听器、同步 waterfall、前缀数量变化。
taskset -c 0 cargo bench -p rutis --offline --bench events

# 同一二进制同时链接新旧实现，使用完全相同的 keyed 接口和依赖。
RUTIS_BENCH_CPU=0 bash tools/compare-event-dispatch.sh
```

`taskset` / `RUTIS_BENCH_CPU` 是 Linux 的可选 CPU 绑定；省略后也可以运行。依赖需预先在 Cargo 缓存中。`RUTIS_BENCH_ITERATIONS` 可调整第一个基准的迭代次数，默认 100000，先预热 1000 次。

新旧对比由 [探针](probes/compare-exact-dispatch.rs) 执行：每个监听器数量取七轮、每轮 500000 次派发的中位数，新旧执行顺序交替。使用保留的 `serial_keyed` / `on_keyed` 包装是为了让两版测试代码一致，不推荐新业务继续使用弃用入口。

## 同步派发

监听器都是最小空回调：bail 返回 None，waterfall 调用 next；终点返回 u64。以下为单次基准的平均 ns/op。

| 精确监听器数量 | bail_sync | waterfall_sync |
| --- | ---: | ---: |
| 0 | 412.8 | 420.5 |
| 1 | 475.0 | 543.8 |
| 8 | 971.8 | 1085.2 |
| 64 | 4345.7 | 5248.2 |

实例键的无监听器 waterfall_sync 为 458.6 ns/op。空链没有 future / spawn，也不装箱终点结果，但仍需要关闭 / 代次检查、线程重入保护和 fiber 在途登记。

## 前缀订阅

静态键 `room/hit` 有一份精确异步监听器；存在前缀时，第一份匹配 `room/`，其余都不匹配。所有回调返回 None。这里没有 emit 排队或业务 IO。

| 前缀注册数量 | serial ns/op |
| --- | ---: |
| 0 | 94.1 |
| 1 | 568.7 |
| 8 | 563.2 |
| 64 | 702.6 |
| 1024 | 2309.9 |

前缀派发包含扫描、快照合并、模式命中计数和卸载等待保护；只对命中的订阅检查 owner 存活。少量前缀的主要成本是生命周期保护，而非字符串比较。首版使用线性扫描；需要更多吞吐场景的数据后，再在 #43 中决定是否增加索引或缓存。

## 无模式时的新旧精确派发

下表使用同一动态名字、同一二进制中的两版 serial_keyed，没有模式、观察器或业务回调工作。七轮中位数（ns/op）：

| 精确监听器数量 | 0.3.0 | 0.4.0 | 差异 |
| --- | ---: | ---: | ---: |
| 0 | 55.2 | 58.5 | +5.9%（+3.3 ns） |
| 1 | 112.6 | 97.8 | -13.1% |
| 8 | 273.3 | 262.7 | -3.9% |
| 64 | 1589.7 | 1605.5 | +1.0% |

实现中避免给精确订阅增加原子计数，并将诊断元数据移出常用回调字段；模式选取与实际调用才计数。异步适配器在 future 内调用用户监听器，因此保留原先一次轮询 panic 捕获，避免重复捕获的开销。空链仍多出总线身份校验与模式检查；表中有正负差异，不能宣称所有路径“完全没有性能回退”。这些是代表性本机样本，不是硬性 CI 门槛。

本批没有完成 #43 的服务读取、装载 / 驱逐、并发吞吐和 emit 积压基准，也没有引入背压策略。既有同键 emit 保序、跨键并发和等待取消语义由回归测试确认。

## emit 积压、服务读取与生命周期（#43，2026-10-02）

环境：macOS，Apple M4 Max，rustc 1.98.1，release，Tokio 两个工作线程；未绑核，单次样本。

```sh
cargo bench -p rutis --bench events    # 含 emit 接收与排空
cargo bench -p rutis --bench runtime   # 服务读取、插件装载 / 卸载
```

| 项目 | ns/op |
| --- | ---: |
| emit 接收，无监听器 | 15.5 |
| emit 接收，同键 1 个监听器 | 560.0 |
| emit 排空，同键 1 个监听器（每个事件从接收到处理完） | 974.8 |
| `ctx.get` | 82.2 |
| `ctx.require`（已声明依赖） | 108.7 |
| 插件装载 + 卸载 | 27162.6 |
| 带依赖的插件装载 + 卸载 | 24768.7 |

- **emit 接收**：调用方只付登记与入队（spawn）的成本；无监听器时不入队。同键 1 个空监听器时，一条链大约每秒处理一百万个事件，慢监听器则按自身耗时串行积压。
- **积压可观测**：`Ctx::diagnostics().event_backlogs` 按事件键给出已接收未完成的 emit 数量（含正在执行的一个）及最早一个已等待的时长，按等待时长排序。记录积压不改变派发：对 emit 接收的对比（同键 1 个监听器，新旧实现各 7 轮）中位数为 1113 ns（旧）与 947 ns（新），差异在噪声内。
- **服务读取与生命周期**：读取在百纳秒内；一次插件装载到卸载约 25 µs，带依赖的插件与无依赖的插件相当（依赖已就绪时）。

### serial / parallel / waterfall

在运行时任务内调用（插件通常如此），监听器为空回调：serial 每个都返回 None（全部执行），waterfall 每个都调用 next 到达终点。两次运行一致，取其一：

| 精确监听器数量 | serial | parallel | waterfall |
| ---: | ---: | ---: | ---: |
| 0 | 25.1 | 25.1 | 97.7 |
| 1 | 122.3 | 609.6 | 212.3 |
| 8 | 546.4 | 3555.5 | 677.9 |
| 64 | 3941.9 | 24129.6 | 5032.8 |

- **serial / waterfall**：在调用方任务内依次 await，不 spawn；每个监听器约 60–80 ns。waterfall 多出链式 `next` 与终点调用。
- **parallel**：每个监听器 spawn 一个 Tokio 任务，监听器可在多个工作线程上真正并发，一个监听器 panic 不影响其他；代价约每个监听器 0.4 µs。监听器只做很少工作时 serial 更便宜；监听器有 IO 或较重计算时，并发收益远大于这部分开销。
- **在运行时外调用**（`block_on`）时，parallel 每次还要跨线程唤醒调用方：同样 1 个监听器约 8 µs。基准因此在任务内测量。
- 如需降低 parallel 的固定开销，可在调用方任务内并发轮询（不 spawn），代价是失去多线程并行；本版不改。

### 背压：本版不引入

结论：同键 emit 保持“触发即忘、按发射序串行、无上限排队”的现有语义，不增加队列上限、丢弃或阻塞策略。

- **语义不变**：emit 的契约是触发即忘与同键保序；任何上限都必须在“丢弃事件”“让 emit 失败”或“让 emit 等待”之间选择，三者都会改变现有调用方的行为，而且没有一种对所有事件都正确。
- **已有替代**：需要等待处理完成的调用方使用 `parallel` / `serial`，天然受处理速度约束；监听器中的慢工作应 spawn 到自己的任务或有界队列（开发手册“选择分发方式”）。
- **可观测先行**：积压现在可以在诊断中看到并据此告警；出现真实的积压场景后，再以 opt-in 的形式（例如带上限的 emit 变体）补充，默认行为不变。
- **前缀订阅索引**：线性扫描在 1024 个前缀时约 1.5 µs/次，暂不增加索引或缓存。
