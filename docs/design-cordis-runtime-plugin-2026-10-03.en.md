# Make the Cordis Runtime a rutis Plugin (2026-10-03)

Based on the [requirements](requirements-protocol-plugins.en.md) (rutis is the host), P6 of the [loader design](design-rutis-loader-2026-10-02.en.md), P6 (`InteropResolver`, #101 / #104 merged), and the [decision record](decision-multilang-2026-10-03.en.md).

Status: implemented; see #109.

## 1. Problem

P6 made each JS plugin a loader row, and each row is a rutis plugin. But the shared Node process and Cordis Context are not plugins; they live in an `OnceCell` inside `InteropResolver`:

| Current behavior | Consequence |
| --- | --- |
| Process starts on first `resolve` and lives until the Resolver is dropped | Process lifecycle is outside rutis management; it has no fiber and is absent from diagnostics. |
| After a process crash, rows retain an invalid `Arc<Process>` | No plugin enters a failed state; rows see a `Transport` error only on their next call. |
| Host services are passed once through `with_hosts(Vec<Host>)`, after their dispatchers have already been captured | Host services do not participate in dependency gating; revocation or replacement is not followed by the JS side. |
| A row factory captures `Arc<Process>` directly | The dependency between rows and runtime is implicit and absent from the `inject` graph. |

Static mounts generated by `build.rs` do not have these problems because each mount is itself a plugin: it starts the process in `apply`, cleans it up in an effect, and declares host services in `injects`. This design makes the dynamic path follow the same model.

## 2. Design

```text
root
 ├─ CordisRuntime (plugin)      apply: Process::mount(anchor, hosts) → provide CordisRuntime service
 │    injects: host services    effect: process.dispose()
 └─ LoaderPlugin
      ├─ row "@x/a" (JsRow)     injects: CordisRuntime → apply: runtime.load_row(…)
      └─ row "@x/b" (JsRow)     injects: CordisRuntime
```

**`CordisRuntime` plugin** (in rutis-interop, Unix only, no loader dependency):

- **Configuration:** `node_package`, `anchor`, and a list of host services (name and method declarations). The application provides each host service as `dyn HostDispatch` under `host_key(name)`.
- **`injects`:** the `TypeKey` for each host service. If a service is not ready, the runtime remains `Pending`. If a host service is revoked, the runtime unloads and waits again under native rules. This matches §5 semantics for static mounts: revocation restarts the entire runtime; it does not replace a service in place.
- **`apply` steps:**
  1. Resolve host services with `ctx.require_as` and build `Host` values.
  2. Call `Process::mount(.., Mount { anchor, hosts, .. })`.
  3. Register a cleanup effect (`process.dispose()`) before providing the `CordisRuntime` service containing `Arc<Process>`.

  Cleanup therefore revokes the service first, lets rows unload, and closes the process last.
- **Crash handling:** start a task during `apply` that waits for `process.closed()`. If the process did not exit through `dispose`, revoke the service with the `Disposer` returned by `provide`.
  - Rows lose their dependency and return to `Pending` under native rules.
  - The runtime plugin itself stays `Active` but no longer provides the service, matching “services after a crash” in §6 of the static mount design.
  - The application decides whether to restart it, for example by calling `restart` on its fiber. The compatibility layer does not restart automatically.
  - Diagnostics show that the runtime service is missing, and row `Pending` causes point to it.

**Rows (`JsRow`):**

- Add `TypeKey::of::<CordisRuntime>()` to `injects`. During `apply`, get the process through `ctx.require`; the factory no longer captures it.
- Forward volatile updates through this service as well.
- Dependency ordering ensures rows unload first and the runtime closes afterward.

**Resolver:**

- Name resolution (`resolve_entry`) already happens in Rust and does not need a process.
- Only schema lookup (`row_schema`) needs Node. The Resolver holds a runtime plugin handle (`CordisRuntimePlugin::handle()`, internally a watch channel):
  - If the runtime is starting, wait until it is ready and fetch the schema.
  - If there is no runtime (waiting on host services, startup failed, or process exited), do not wait. Return a result without a schema, record the reason in `meta.schema`, and do not cache it, so `Loader::reload` can fill it in later.
  - Reconciliation therefore never blocks on the runtime. Rows still resolve normally and wait for the runtime through dependencies.
- The application installs the runtime plugin before reconciliation; it is infrastructure at the same level as `LoaderPlugin`.

**Application usage:**

```rust
root.provide_as::<dyn HostDispatch>(host_key("systemPrompt"), Arc::new(prompts))?;
let runtime = CordisRuntimePlugin::new(node_package, anchor)
    .host("systemPrompt", json!({ "get": "sync" }));
let resolver = Chain::new().with(InteropResolver::new(runtime.handle()));
root.plugin(runtime);
root.plugin(LoaderPlugin::new(resolver, options)).await?;
```

## 3. Unchanged behavior

- Static mounts and `build.rs` code generation are unchanged.
- The protocol, `runner.mjs`, and row control operations (`rows.*`) are unchanged. Only ownership on the Rust side changes.
- Multiple runtime instances: each `CordisRuntime` is a separate Node process and Context. For isolation, mount multiple runtimes using distinct service keys (`TypeKey::keyed`). Selecting which runtime a row uses is deferred until there is a need.
- The reverse direction (Cordis hosting rutis plugins) remains frozen.

## 4. Acceptance

Add the following coverage to `crates/rutis-loader/tests/interop_rows.rs` (#109 implemented these):

1. When the runtime plugin unloads, rows unload first and the process exits last.
2. After killing the Node process, the runtime revokes its service; rows return to `Pending` and diagnostics identify the missing runtime. Restarting the runtime fiber recovers the rows.
3. If a host service is absent, the runtime and rows wait. Providing it starts them all; revoking it stops them all.
4. If runtime `apply` fails, `resolve` does not hang. Rows resolve without a schema and wait on their dependency.
5. All existing P6 tests pass.

## 5. Open questions

- After a crash, should the runtime only revoke its service and remain `Active` (matching static mounts, chosen here), or should it enter `Failed`? The latter requires a core API for plugins to report their own failure, conflicting with “do not change the core for compatibility,” so it is not chosen.
- Should the handle live on `CordisRuntime` or be exposed as a service? This depends on whether the Resolver will become plugin-provided; discuss separately.
