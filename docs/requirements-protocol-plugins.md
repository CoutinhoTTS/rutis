# rutis 挂载 Cordis 插件：需求

## 1. 目标

**以 rutis 为中心，让 rutis 应用跨进程挂载和使用现有的 Cordis（Node）插件。所有兼容工作都在兼容层完成，rutis 内核不为兼容而修改。**

- Cordis 插件仍在真实的 Cordis 中运行，源码不改；rutis 侧通过自动生成的 Rust 类型、按 rutis 原生方式使用它。
- 一次挂载可以是一组彼此依赖的 Cordis 插件（已发布插件通常设计成组合使用），组内依赖按 Cordis 原生规则解析。
- **依赖是双向的**：rutis 插件可以依赖被挂载插件提供的服务；被挂载的 Cordis 插件也可以按原生方式（`inject` / `ctx.xxx`）依赖 rutis 应用提供的服务，例如宿主把 llm、存储等能力交给插件使用。两个方向都遵守各自框架的依赖门控和清理顺序。
- 兼容层是外挂库（`crates/rutis-interop`、`interop/node`），不是另一个宿主，也不是新的插件框架。
- 由 rutis 做宿主：dsh 的完整 web 界面也通过本兼容层挂载运行（`crates/rutis-dsh`），模型调用由 rutis 应用提供的服务承担。原先由 dsh 做宿主、经 `rutis-cordis` + `host/` 使用 Rust 的旧桥已移除（[#83](https://github.com/arcships/rutis/issues/83)）。`rutis-interop` 中 Cordis 应用挂载 rutis 插件的实现冻结，不再增加能力。注意区分：rutis 应用向它挂载的 Cordis 插件提供服务，属于本需求的主方向，不在冻结范围内。

## 2. 使用方式

```text
rutis 应用
    |
ctx.plugin(生成的挂载插件)       <- 构建时由原 TS 插件自动生成
    |
兼容层（Rust） <==== Unix socket ====> 兼容层（Node）
                                            |
                                     真实 Cordis + 原 TS 插件
```

| 参与者 | 应做的事 | 不应承担的事 |
| --- | --- | --- |
| rutis 应用开发者 | 选择插件、配置，挂载生成的插件，按 rutis 方式读取服务、订阅事件 | 编写通信协议、手写桥接代码或维护生成文件 |
| Cordis 插件作者 | 按 Cordis 原生方式编写插件 | 为跨进程改写业务；只需遵守 §5 的边界规则 |

## 3. 约束

| 项目 | 要求 |
| --- | --- |
| rutis 内核 | 不为兼容而修改；只使用 rutis 已有的公开 API |
| Cordis | 只使用公开 API（含 `internal/*` 钩子）；不改源码、不 fork、不 monkey patch、不提上游提案 |
| 插件源码 | 原 TS 插件及 rutis 消费者的业务源码不因跨进程而改写 |
| 类型绑定 | 普通 Cargo 构建时自动生成；不手写契约、不维护 IDL |
| 方法形状 | 同步方法仍是同步方法，异步方法仍返回 Future；这是接口契约 |
| 实现取舍 | 公开 API 覆盖不了的能力记为"做不到"，写明场景与原因；不为追求无差别而扩大实现范围 |

## 4. 框架契约与语言栈差异

兼容层只严格保留**框架契约**。由 JS / Rust 语言栈造成的行为差异可以妥协，改写成 §5 的边界规则。

| 类别 | 内容 | 处理 |
| --- | --- | --- |
| 框架契约（必须保留） | 服务方法的同步 / 异步形状、参数与返回值、业务错误（含 AggregateError 的 errors / cause） | 保留 |
| 框架契约（必须保留） | 插件的装配、依赖就绪、卸载清理；卸载期间仍可调用服务 | 保留 |
| 框架契约（必须保留） | 对象身份：已取得的服务对象、回调、异步结果不会被替换成别的对象或快照 | 保留 |
| 框架契约（必须保留） | 事件返回值的含义（例如 rutis 的 `Some(false)` 与 Cordis 的 `false` 含义不同） | 显式转换；无法转换时报不兼容 |
| 语言栈差异（可妥协） | Cordis `emit` 返回时同步监听已执行完 | 跨边界统一采用 rutis 的"发出即忘" |
| 语言栈差异（可妥协） | JS async 函数调用时立即执行同步前半段 | 跨边界不保证 |
| 语言栈差异（可妥协） | Cordis 两侧监听逐个交错排序 | 跨边界按组转发 |
| 语言栈差异（可妥协） | `bail` 把返回的 Promise 本身当作短路值 | 跨边界先等待结果再判断 |
| 语言栈差异（可妥协） | waterfall 的 next 可多次调用 | 跨边界只能调用一次，违反时报错 |
| 语言栈差异（可妥协） | 服务换值与读取之间的即时性 | 换值后 rutis 侧由兼容层替换代理，允许短暂读到旧对象 |

## 5. Cordis 插件的边界规则

接入 rutis 的 Cordis 插件需要遵守以下规则。能检测的违规，在挂载时或运行时明确报错，不静默降级。

1. **服务**：通过 `ctx.provide` / 属性赋值发布和换值。直接 `ctx.set` 换值不产生通知，rutis 侧在下一次调用该服务后才会切换到新对象。
2. **跨边界事件**：`emit` 只是通知，不保证 `emit` 返回时 rutis 侧已执行；需要等待或需要结果时用 `parallel` / `serial` / `bail`。
3. **事件顺序**：只在同一侧内保证原生顺序；另一侧的监听作为一组在固定位置执行，不支持依赖跨侧交错顺序的写法。
4. **中间件链**：waterfall / bail 链不跨侧交错；对方一组作为一个整体环节参与。
5. **框架内部事件**：`internal/*` 不跨边界。
6. **同步等待**：同步方法不能在执行中等待需要 Node 事件循环推进的结果（定时器、Promise）；这类等待返回 `SyncWaitCycle` 错误。
7. **宿主提供的服务**：rutis 提供给插件的服务在 Cordis 侧是按接口生成的代理对象，按接口调用与原生一致；但它不是插件声明的那个类的实例，`instanceof` 判断不成立。
8. **事件循环**：插件不得长期阻塞事件循环或卡死；兼容层不为调用加超时。rutis 侧需要超时时用异步方法并自行设置超时（超时即取消），卸载的等待时间由应用决定。未捕获的异常 / 拒绝会结束整个 Node 进程，同一挂载的服务随之撤销。

## 6. 验收

- 以真实插件驱动：先用 npm 上已发布的 dsh 官方插件建立基线，按 L0–L4 分级（口径同 dsh 桥设计 §九），按实际缺口逐步覆盖；每接通一个插件算一次交付。
- 每项能力都有跨进程自动化测试，并与 Cordis 原生行为对照；§4 中可妥协的差异按 §5 的规则验收。
- 被挂载的插件依赖 rutis 应用提供的服务时，按原来的依赖与服务读取方式取得这些能力；服务未就绪时插件保持等待，服务撤销时插件按原生规则停止。
- 远端退出、通信中断和失效引用明确失败，不返回伪成功，不自动重试副作用。

## 7. 首版决策：停止、进程共享与权限

决策记录（[#71](https://github.com/arcships/rutis/issues/71)）。以下均为首版的产品边界，行为与当前实现一致。

| 事项 | 首版结论 | 应用看到的行为 |
| --- | --- | --- |
| 强制终止卡死的插件 | 不提供单独的强制终止操作 | 正常卸载会等待插件完成清理，兼容层不加超时（§5 规则 8）。挂载被完全释放时，Node 进程以 SIGKILL 结束；只结束 Node 进程本身，插件自己启动的子进程不由兼容层回收。需要截止时间的应用自行给卸载加超时，超时后释放挂载。 |
| 多个插件共享进程 | 同一个挂载（含组合挂载）的插件共享一个 Node 进程；不同挂载各自一个进程 | 进程崩溃或退出时，该挂载提供的全部服务撤销，依赖这些服务的 rutis 插件按原生规则停止；其他挂载及不依赖它们的功能不受影响。需要隔离的插件放进不同挂载。 |
| 卸载、终止与超时的区别 | 三者分别报告 | 正常卸载成功即成功；进程非正常结束时，卸载与调用返回 `Error::Transport`，并说明进程如何结束（例如被信号终止）；调用超时由应用通过丢弃 future 取消，Cordis 侧收到 `AbortSignal`，结果未知时不报告为未执行。 |
| 系统权限 | 进程外运行不是沙箱 | Node 进程以 rutis 应用的同一用户和权限运行，继承其环境变量，可访问同样的文件与网络。只挂载可信插件。 |

## 8. 不在范围内

- 修改 rutis 内核或 Cordis。
- 为追求与原生无差别而建设的机制：共享内存版本页、跨框架统一事件队列、分布式 GC。
- 部署平台、插件市场、自动重启、重连恢复、操作系统沙箱。
- 其他语言的接入。2026-10-03 调研后定为**不在 rutis 内做**：rutis 只做与同范式的 Cordis 之间的挂载（rutis 为宿主，反方向保持冻结）。PowerShell、Bash、AppleScript 等没有 Cordis 范式的语言，以及 min_cordis（Python），确有需求时在 rutis 之外以普通插件实现，只用 rutis / rutis-interop 的公开 API。理由见[决策记录](decision-multilang-2026-10-03.md)。

历史需求与方案见 [#66](https://github.com/arcships/rutis/issues/66)—[#70](https://github.com/arcships/rutis/issues/70)、[旧设计](design-protocol-plugins-2026-09-25.md)，以及 [#74](https://github.com/arcships/rutis/pull/74)（内核事件队列，已停止推进）；它们不作为本需求的依据。
