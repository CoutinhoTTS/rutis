# rutis / Cordis 跨进程插件：需求

## 1. 目标

**rutis 应用能够跨进程挂载和使用现有 Cordis 插件；Cordis 应用能够跨进程挂载和使用现有 rutis 插件。插件保留所属语言、框架的原生写法和行为。**

“任意插件”是兼容目标，不能预先改成“按协议重写过的插件”或“只提供异步 JSON 方法的插件”。范围覆盖插件装配、Context、依赖、服务对象、事件和生命周期。插件内部仍使用原框架及语言运行时。

## 2. 使用方式

```text
rutis 应用                                  Cordis 应用
    |                                           |
原生插件入口                                 原生插件入口
    |                                           |
挂载 Cordis 插件                              挂载 rutis 插件
    |                                           |
另一进程：Cordis + 原 TS 插件                 另一进程：rutis + 原 Rust 插件
```

| 参与者 | 应做的事 | 不应承担的事 |
| --- | --- | --- |
| 应用开发者 | 选择插件包、配置、运行位置及依赖连接 | 编写通信协议、手工维护每个插件的桥接层 |
| 插件作者 | 按 rutis 或 Cordis 原生方式编写插件 | 为跨进程场景改写业务、增加协议专用插件入口 |
| 使用服务的开发者 | 使用本语言的类型、Context、服务和事件 API | 使用字符串 RPC、对象编号或手工远端引用管理 |

应用可以由任一框架构建，不要求另建一个宿主产品。

## 3. 已确认的约束

| 项目 | 要求 |
| --- | --- |
| 装配差异 | 允许指定包、运行位置，并自动生成目标语言绑定 |
| 插件源码 | 提供者、消费者的既有业务源码不因跨进程而改写 |
| 类型绑定 | 自动集成到安装／构建和挂载流程；无需单独运行生成器、维护生成文件或逐插件手写契约与适配器 |
| 同步性 | 同步属性、同步方法和同步事件仍同步；异步接口保持异步 |
| 接入方式 | 外挂库或适配插件；修改框架内核不是默认授权 |
| 实现取舍 | 优先复用原框架；不增加没有对应需求的机制或备用实现 |

跨语言绑定可以体现目标语言的语法习惯；这不等于允许改变原插件已有接口、删除能力，或给原来的同步调用增加 `await`。

## 4. 能力要求

| 能力 | 必须保持的使用体验 |
| --- | --- |
| 插件装配 | 使用原生插件入口；配置校验、初始化、子插件、更新和卸载遵守所属框架规则 |
| Context 与作用域 | 插件收到真实的原生 Context；跨边界的依赖解析、隔离、上下文关联和拦截行为保持原意 |
| 依赖 | 必需、可选依赖及可用性变化通过原生机制生效；业务不轮询远端服务 |
| 服务 | 使用原生提供、读取方式及本语言类型；保留同步/异步方法、属性读写和业务错误 |
| 对象 | 返回的有状态对象可以继续调用、传回和传递；身份、状态及有效期不能被一次序列化替代 |
| 回调 | 支持原接口中的同步/异步回调、保存回调及回调中的反向调用，遵守原有有效期 |
| 事件 | 使用原生事件入口；覆盖通知、等待、短路、waterfall、once、注销、顺序和作用域过滤 |
| 其他接口形状 | 插件已有的迭代、流等公共能力不能因上一版设计未覆盖而直接排除 |
| 生命周期 | 资源由原生所有者管理；依赖撤销和插件卸载包含跨进程的消费者与清理关系 |
| 故障 | 远端退出、通信中断和失效引用得到明确失败；不能返回伪成功，也不能自动重复副作用 |

两框架原本不同的语义需要逐项映射。名称相同不能作为等价依据，例如 Cordis 与 rutis 的 `emit` 完成时机不同。

## 5. 原生体验的判定

| 场景 | 验收依据 |
| --- | --- |
| 首次接入 | 配置插件包、依赖与运行位置后，正常安装／构建及启动自动完成绑定生成、所需编译和原生注册 |
| rutis 挂载 Cordis 插件 | 原 TS 插件在 Cordis 内执行；Rust 通过自动绑定和 rutis 原生入口使用其能力 |
| Cordis 挂载 rutis 插件 | 原 Rust 插件在 rutis 内执行；TS 通过自动绑定和 Cordis 原生入口使用其能力 |
| 远端插件反向依赖应用 | 远端插件按原来的依赖与服务读取方式取得应用提供的能力 |
| 同步调用包含回调 | 调用、回调及返回均保留同步形状，不能仅验证没有反向调用的简单方法 |
| 本地和远端监听混合 | 顺序、短路、续延、注销和可见范围符合明确的原生语义映射 |
| 依赖撤销与卸载 | 依赖方按原生顺序退出，关闭期间需要的服务仍可用，清理完成后释放资源 |

不要求通信延迟、进程地址空间与本地执行相同；但不能据此把可变对象改成陈旧快照，或省略原生行为。遇到无法保留的接口，必须说明具体场景、技术原因及所需取舍，不能通过重新定义“支持范围”宣告完成。

## 6. 工作范围

本轮聚焦 Rust/rutis 与 TS/Node/Cordis 的双向互操作。其他语言在这一机制成立后接入。

部署平台、插件市场、升级回滚、自动重启、重连恢复、操作系统沙箱和性能专项不属于本轮需求。强制杀进程及复杂进程调度不是原生使用体验的前置条件。

交付应包含两种应用方向的接入文档与可运行示例。示例必须使用普通插件，不能要求先把样例改写成协议专用插件。

## 7. 依据与设计入口

用户最新确认优先于历史 issue 和旧方案：双向挂载任意现有插件、保留完整 Context 能力、允许自动生成绑定、同步保持同步、优先纯外挂。

当前设计及可行性核对见[跨进程挂载设计](design-protocol-plugin-mount.md)。历史来源为 [#52](https://github.com/arcships/rutis/issues/52)、[#46](https://github.com/arcships/rutis/issues/46)、[#47](https://github.com/arcships/rutis/issues/47)、[#48](https://github.com/arcships/rutis/issues/48) 和 [#59](https://github.com/arcships/rutis/pull/59)；新跟踪入口为 [#66](https://github.com/arcships/rutis/issues/66)。历史材料中的异步限定、手写协议和额外平台需求不覆盖本文。
