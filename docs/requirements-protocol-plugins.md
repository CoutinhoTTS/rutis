# 协议插件：产品定义与需求

## 1. 产品目标

让开发者在同一个应用中组合使用不同语言编写的插件。插件可以运行在不同进程，但在应用中仍表现为普通插件：提供服务、依赖其他服务、订阅事件，并随应用管理其生命周期。

**应用开发者决定插件在哪里运行；业务插件按原来的方式使用服务。**

协议接入以外挂库或适配插件提供。使用者不需要修改 rutis 或 Cordis，也不需要自行编写跨进程通信逻辑。

## 2. 使用者与职责

| 使用者 | 职责 | 获得的能力 |
| --- | --- | --- |
| 应用开发者 | 选择插件、配置依赖和运行位置，管理加载与卸载 | 在一个应用中组合 Rust 与 TS 插件 |
| 插件作者 | 使用所属框架编写业务功能，声明提供和依赖的服务 | 同一份插件代码可以用于本地或跨进程组合 |
| 服务接口维护者 | 定义服务的公共接口及跨语言绑定 | 不同语言的插件按同一契约协作 |

应用由开发者使用 rutis 构建。产品为该应用提供接入能力，不要求另行建设一个宿主产品。

## 3. 核心概念

| 概念 | 业务含义 |
| --- | --- |
| 插件 | 应用可加载、配置、卸载的功能单元；保留所属框架的普通插件形式 |
| 服务 | 插件对外提供的业务能力；其他插件通过依赖声明取得和使用 |
| 服务对象 | 服务创建或返回的可继续使用的业务实体，例如连接、会话、任务；可以保有状态 |
| 事件 | 插件之间的业务通知或异步协作入口 |
| 公共契约 | 对服务方法、数据、对象、事件及错误的共同约定 |
| 运行位置 | 插件所在的进程；由应用配置，不由业务调用代码决定 |

```text
开发者的应用
    |
    +-- 选择插件、配置、依赖与运行位置
    |
    +-- Rust / rutis 插件 <---- 服务与事件 ----> TS / Cordis 插件
              |                                      |
         保留原生用法                            保留原生用法
```

## 4. 主要使用场景

| 场景 | 开发者操作 | 期望结果 |
| --- | --- | --- |
| 引入另一种语言的能力 | 在应用中加入插件并配置所需服务 | Rust 可以使用 TS 服务，TS 也可以使用 Rust 服务 |
| 调整运行位置 | 将某个插件从本地组合改为另一进程运行 | 提供者和消费者的业务源码不变，只调整应用装配 |
| 使用有状态资源 | 获取连接或会话，连续调用其方法，必要时传回原服务 | 后续操作作用于同一个业务对象，状态不会因跨进程丢失 |
| 订阅业务变化 | 使用原生事件 API 登记监听、发布事件或等待处理结果 | 无需学习另一套协议事件 API |
| 依赖暂时不可用 | 加载缺少服务的插件，随后提供服务 | 插件按原生依赖规则等待并开始工作；不要求业务轮询 |
| 移除功能 | 卸载插件或移除其依赖 | 依赖它的功能按原生规则退出，相关资源完成清理 |
| 远端异常退出 | 插件所在进程断开或崩溃 | 相关能力明确变为不可用，依赖方得到失败，其他无依赖功能继续工作 |

## 5. 功能要求

### 5.1 插件接入与服务使用

- 首批同时支持 Rust/rutis 与 TS/Node/Cordis，双向提供和消费服务。
- 使用各自框架的普通插件入口、依赖声明和服务读取方式；保留服务名称、业务类型及方法签名。
- 跨语言所需的接口声明和适配集中维护，普通业务代码不包含通信、对象编号或远端引用管理。
- 同一公共接口可以由本地实现或远端实现提供。切换位置不要求改写业务插件。
- 插件按配置加载；服务满足使用条件后才对依赖方可用。加载失败须说明原因，并清理本次加载建立的资源。

### 5.2 服务对象与回调

- 服务可以返回有状态对象。消费者能够继续调用、重复取得以及传回原创建方，保持约定的对象身份和状态。
- 支持公共接口声明的异步回调。被调用服务可以在一次业务操作期间调用回调，回调也可以继续调用其他服务。
- 对象和回调的有效期遵守公共接口及所属插件的生命周期；失效后明确报错，不悄悄连接到另一个实例。
- 资源归属保持原生含义：属于消费者的资源随消费者清理，属于提供者的资源随提供者清理。

### 5.3 事件协作

- 支持原生的监听、一次性监听、注销，以及并行和串行的异步分发。
- 保留各自框架已支持的监听顺序、结果处理、错误处理、作用域和清理行为；不同框架原有差异须有明确的互操作约定。
- 事件可携带声明的数据和服务对象。普通本地事件的使用不受跨进程接入影响。
- 插件初始化期间可以登记和使用事件；合法的业务初始化流程不能因通信装配而无法完成。

### 5.4 依赖与生命周期

- 必需依赖、可选依赖、配置和卸载继续遵守原生框架的行为。
- 必需服务失效时，依赖方停止使用；运行进程仍存活且依赖恢复时，按原生规则重新装载。
- 旧实例留下的对象、回调和后台工作不能冒充新实例，或修改新实例的资源。
- 正常卸载允许业务完成关闭、提交或释放操作；清理所需的服务和资源不能被提前销毁。
- 对外报告的卸载结果反映实际完成情况。等待超时不等于插件已经停止，清理失败不能报告为成功。

### 5.5 兼容与错误

- 公共契约具有版本，并明确哪些变化兼容；加载前检查所需接口与能力是否匹配。
- 参数、结果和对象使用须满足契约；不支持的接口明确拒绝，不以缺失数据或成功默认值替代。
- 业务错误通过公共接口返回；通信中断与服务不可用应能和业务错误区分。
- 若断连后无法确定一次操作是否已执行，应如实报告；不自动重复可能产生副作用的操作。
- 进程隔离不代表权限隔离。文档须说明插件能够访问的系统资源以及进程退出的影响范围。

### 5.6 开发交付

- 提供正式的应用接入入口和可运行示例，覆盖配置、双向服务、对象、事件与卸载。
- 提供分别面向应用开发者、插件作者和接口维护者的文档，说明支持范围、兼容规则与常见错误。
- 应用接入不以部署平台、管理平台或进程监督系统为前提。

## 6. 原生使用体验的边界

“原生使用体验”要求业务源码、公共接口和已支持行为一致，不要求跨进程执行具有相同的速度或共享内存特性。

| 承诺 | 边界 |
| --- | --- |
| 普通插件代码和调用方式保持一致 | 应用装配、运行位置及接口绑定可以不同 |
| 异步结果、业务状态、依赖与资源归属保持一致 | 存在通信延迟和远端不可用；不保证等待前的同步副作用时机 |
| 服务对象保持契约约定的身份 | 不保证代理与原对象具有相同内存地址或语言反射行为 |
| 声明支持的事件与作用域有明确行为 | 不自动传输任意闭包、完整 Context 或共享内存引用 |

首批支持异步服务接口。不将同步读取远端可变状态伪装成本地读取。已有同步接口若需调整，须作为公共接口的独立变更处理，本地与远端共同采用，不能只要求远端消费者改写。

任何无法保持的已承诺原生行为，都必须明确提出需求取舍；不能通过临时缩小“支持接口”的定义宣告完成。

## 7. 首版范围

| 类别 | 范围 |
| --- | --- |
| 首版必需 | 本机 Linux 下的 Rust/rutis 与 TS/Node/Cordis；双向异步服务、状态对象、调用期间回调、异步事件、原生依赖与清理、契约校验、开发入口和文档 |
| 不在首版 | 其他语言、跨机器网络接入、流式接口、长期保存的业务回调、任意第三方对象转交、同步跨进程事件和复杂事件流程 |
| 不作为本产品首版交付 | 部署升级与回滚、代码热替换、自动进程重启与重连恢复、插件市场、管理平台、性能专项、操作系统沙箱 |
| 待确认 | 是否需要强制终止卡死的插件进程；是否要求多个协议插件共享一个进程 |

外挂接入是当前产品边界。若原生公开 API 无法满足必需行为，应先明确无法实现的用户场景和可选取舍，不将修改内核作为默认解决办法。

## 8. 完成标准

1. 开发者按公开文档可以在自己的应用中完成双向接入，无需自建协议基础设施。
2. 固定的普通插件源码在本地与跨进程组合中均能完成业务场景；差异符合第 6 节。
3. 服务对象、事件、依赖变化及正常卸载符合各自框架的约定。
4. 不兼容、失效、断连和清理失败有明确结果，不产生伪成功或旧实例继续生效。
5. 每项已交付能力均有真实跨进程证据；未支持项与文档一致。
